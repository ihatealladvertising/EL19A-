# FND-000028 — `0x0AFF2` is a 4×4 all-zero UBYTE map with reader-backed axes `0x0E5CC`/`0x0E5C8` and query `U8[FFFF85A4]`; `0x0E5E8` is one of four all-zero 8-point selector curves sharing the same sink

**Status:** CURRENT
**Semantic layer:** input identity (query source and axis roles) and output identity at the first consumer (sink address only). Function identity and physical identity remain unresolved.
**Evidence grade:** Reader-Verified (call-site register sets read from the pinned LST, helper contracts read from code, byte-exact ROM payloads and axis contents)
**Confidence:** HIGH for addresses, extents, geometry, axes, clamp and sink; MEDIUM for the inline `0x0B002` table because its only reader is an inline indexed load rather than a helper call; UNRESOLVED for physical meaning, units, donor correspondence and the selector flags

## Scope

Target-side resolution of the dual-donor lead named in `CONTROL/PROJECT_DIRECTION_2026-11-26.md` §3 for the two objects that `WO70031` verified structurally but left semantically unresolved: `0x0AFF2` (4×4 UBYTE) and `0x0E5E8` (8×1 UBYTE). Reached under `WO70033`. Does not reopen any earlier endpoint boundary and does not characterise either object physically.

## Observations

1. **`0x0AFF2` reader and query.** `sub_22B44` is called at `0x5B3C0` inside the function entered at `0x5B33A`, with `r4 = 0x0AFF2` (`off_5B454`, `0x5B3AE`), `r5 = 0x0E5CC` (`off_5B458`, `0x5B3B4`) and `r6 = 0x0E5C8` (`off_5B45C`, `0x5B3BE`). The delay slot `0x5B3C2` `extu.b r0,r7` carries the query, loaded at `0x5B3BC` as `mov.b @(h'DB,gbr),r0` under `gbr = 0xFFFF84C9` (`0x5B340`–`0x5B342`), i.e. **`U8[0xFFFF85A4]`**, unsigned byte.

2. **`sub_22B44` drives both axes from that one query.** `0x22B48` `extu.b r7,r7`; `0x22B4A`–`0x22B52` search `r5` (`0x0E5CC`) through `sub_233CC` with `r4 = 3`; `0x22B58`–`0x22B60` repeat the search on `r6` (`0x0E5C8`) after reloading the first axis from the stack; `0x22B62`–`0x22B72` stack the two indices and tail-jump to `loc_231F8` with `r5 = 4`. `loc_231F8` (`0x231F8`–`0x2324C`) computes the byte offset `4*row + column` and interpolates through `sub_231C8` over the corner bytes. Axis roles are therefore `0x0E5CC` = axis1 (`r5`) and `0x0E5C8` = axis2 (`r6`).

3. **Axis payloads.** `0x0E5C8` = `00 01 02 03`; `0x0E5CC` = `0E 28 60 88` = 14 / 40 / 96 / 136. Both are 4-entry UBYTE and strictly ascending. The catalogue records both with `consumer_tables = [0x0AFF2]` and `shared_count = 1`.

4. **`0x0E5E8` is selected from four sibling curves.** At `0x5B560`–`0x5B57A` the shipped path chooses `r4` among `0x0E5D8` (`off_5B6E0`), `0x0E5E0` (`off_5B6E4`), `0x0E5D0` (`off_5B6E8`) and `0x0E5E8` (`off_5B6EC`) using `tst r6,r6` and `cmp/gt r2,r7` with `r2 = 1`, then calls `sub_22DF8` (`0x22DF8`) at `0x5B57E`. The per-call export records only the final literal, so the catalogue's single `0x0E5E8` row under-represents the group; `0x0E5D0`, `0x0E5D8` and `0x0E5E0` have no catalogue entry.

5. **The `0x0E5E8` query is computed, not a RAM byte, and the export's `r5 = 0x0FF` is wrong.** `0x5B540`–`0x5B55E` compute `r5 = clamp(((U32 product) >> 15) − 0x20, 0, 0xFF)` with a zero floor at `0x5B552`–`0x5B554` and a `0xFF` ceiling at `0x5B55A`–`0x5B55E`. `0xFF` is the ceiling held in `r2` (`0x5B556` `mov #-1,r2`; `0x5B558` `extu.b`), not the query. `sub_22DF8`'s contract (q ≥ `0xE0` returns element 7, else 8-point interpolation) is unchanged and agrees with `FND-000025`.

6. **Both lookups are numerically inert.** `0x0AFF2`–`0x0B001` is 16 × `0x00` (`sha256 374708fff7719dd5…`); `0x0E5E8`–`0x0E5EF` and the sibling curves at `0x0E5D0`, `0x0E5D8`, `0x0E5E0` are 8 × `0x00` each (`sha256 af5570f5a1810b7a…`). Every lookup result is `0` for any query, so the traced product is `0x0000` regardless of input.

7. **One shared first consumer.** Both call paths converge at `0x5B58C`–`0x5B590`: the lookup result is multiplied by `U8[0xFFFF2150+0x908]` (`0x5B3C8` on the 3-D path, `0x5B586` on the 2-D path) and the 16-bit product is stored to **`U16[0xFFFF115A]`** (`0xFFFF1054+0x106`, `r13 = 0xFFFF1054`). The 3-D path also stores its inline element to `U8[0xFFFF14E4]` (`0xFFFF1054+0x490`) at `0x5B3B2`–`0x5B3B6`.

8. **A second 4×4 table at `0x0B002` is read inline at `0x5B3B0`.** `off_5B44C` = `0x0B002`; `0x5B3AA` `add #-4` gives base `0x0AFFE`; `r0 = 4*r + c` with `r = clamp(U8[0xFFFF84C9],1,4)` and `c = clamp(U8[0xFFFF84CA],0,3)`, so elements address `0x0B002 + 4*(r−1) + c` across `0x0B002`–`0x0B011`, all `0x00`. This is a distinct object from the helper's `0x0AFF2` argument and has no catalogue entry.

9. **Donor declarations are geometry-only corroboration.** V6 `mTDATDDS` = `MAP 0x0AD5E REC_UBYTE_C COMP_0237_S` with `mTDATDN` (4 pts, 0–12750) and `mTDATDGP` (4 pts, 0–255); Juke `mTDATDDS` = `MAP 0x0C20E`, same axes. V6 `mTDATDPRE` = `CURVE 0x0CF36`, 8 pts, `FIX_AXIS 10…80 step 10`; Juke `mTDATDPRE` = `CURVE 0x11CC0`, same grid. Target axes (0/1/2/3 and 14/40/96/136) do not match either donor grid, and no donor coordinate equals a target address.

## Conclusion

`0x0AFF2` is a 4×4 UBYTE map read by `sub_22B44` at `0x5B3C0` against target axes `0x0E5CC` (14/40/96/136) and `0x0E5C8` (0/1/2/3) with the query `U8[0xFFFF85A4]`. `0x0E5E8` is a single member of a four-curve all-zero selector group read by `sub_22DF8` at `0x5B57E` with a shift-and-clamp computed query. Both feed one 16-bit product sink, `U16[0xFFFF115A]`. Both payloads are all zero, so neither lookup can change that product on this ROM.

The donor geometry correspondence (`mTDATDDS`, `mTDATDPRE`) is strengthened as a lead but is not evidence of target semantics: the axis domains differ, the donor coordinates differ, and no target-side function or physical identity was established. Both objects remain RAW/PROVISIONAL candidates with a now-verified axis and consumer structure.
