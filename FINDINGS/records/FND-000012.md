# FND-000012 — A GBR-relative displacement is not an address until the routine's own base is resolved

**Status:** CURRENT
**Semantic layer:** none (evidence-method finding; establishes no calibration identity)
**Evidence grade:** READER-VERIFIED (per-site base and pool-literal reads from the pinned LST)

Every `@(disp,gbr)` and `@(rN,gbr)` operand in the firmware. Worked instances in this record:

## Observation — the method

The same displacement byte occurs in dozens of routines against dozens of different bases. `@(h'AA,gbr)` is an offset, not an address: it resolves to `FFFF10FE` in one routine and `FFFFB552` in another. Reading a listed displacement as if it were a fixed-address reference produces false attributions in both directions — asserting a consumer that does not exist, and missing one that does.

**Resolution procedure (required for any GBR-relative operand):**

1. Take the function boundary as the **nearest preceding `rts`**, not a fixed line window. A window that crosses an `rts` adopts the previous routine's base.
2. Find the first `ldc rX,gbr` after that boundary, and walk back to the load that filled `rX`, then to its pool literal. The listing prints the resolved literal as a comment.
3. Apply the encoding's scaling: `mov.b` displacement is unscaled; `mov.w` is `disp×2`; `mov.l` is `disp×4` (the listing prints the scaled byte offset).
4. Watch for `mov.w` literals: they are **sign-extended** (`h'B4A8` → `0xFFFFB4A8`). A zero-extended read would yield `0x0000B4A8`, a different cell.
5. Watch for **alternate entries** into one body (`stc.l gbr,@-r15` followed by a fresh `ldc r0,gbr` mid-function). Each re-entry installs its own base; if every re-entry loads the same literal the address is unaffected, but that must be checked, not assumed.
6. `lds.l @r15+,gbr` restores a saved base — treat the base as unknown after it until the next `ldc`.
7. An operand whose index register is dynamic (`@(r0,gbr)`) needs the index propagated: `mov #imm`, `extu.b/w`, `shl*`, `add #imm`, `and/or/xor #imm`, `mov rX,rY`. This is the same blind spot recorded in `REC-000010`: a fixed-displacement census alone silently omits these stores.

## Conclusion

No claim of the form "address *X* is read/written at PC *P*" may rest on a listed `h'disp` alone. The base must be resolved per site. Applied to the instances above, the rule changes four previously recorded attributions (`REC-000013`) and invalidates one previously listed consumer set.

## Confidence

**HIGH.** Every base in the table was read directly from its pool literal at the cited address, and every boundary was taken as the nearest preceding `rts`. The procedure was validated on a case with a known answer: `0x0A19B8` resolves to `FFFF34E7` under `FFFF34B3`, matching the independent `FFFF34C1`-based readers of the same byte at `0x04C7F2`, `0x077BD6`, `0x08B38E` and `0x095094`.

## No-repeat notes

Do not re-derive these bases. Reuse the per-site tables in WO65865/WO65883/WO65886/WO65889/WO65892. Do not run a global GBR census again for the purpose of re-proving the rule.
