## Target reader and query

The Stage-16 listing identifies the enclosing routine as `sub_85AF4` (entry `0x85AF4`). At `0x85B02`, it installs GBR = `FFFF84B4`.

The lookup is conditional:
- `0x85B18–0x85B1E`: if `UBYTE[FFFF3614].bit7` is set, branch around this lookup.
- `0x85B20–0x85B26`: if `UBYTE[FFFF3615].bit7` is clear, branch around this lookup.
- On the lookup path, `0x85B28` reads `UBYTE[GBR+4] = UBYTE[FFFF84B8]` into R0.
- `0x85B2A` loads R4 = `0x0F10E` from literal pool word `off_85D30` at `0x85D30` (bytes `00 00 F1 0E`).
- `0x85B2C` loads R2 = `sub_22E10`.
- **Actual helper call:** `0x85B2E` `jsr @r2`; delay slot `0x85B30` zero-extends R0 into R5 before the helper executes. The query is therefore UBYTE[`FFFF84B8`], unsigned.
- Result R0 is copied to R2 at `0x85B32`.

No explicit ROM axis pointer is passed. The helper uses its fixed implicit query grid.

## Helper mechanics

`sub_22E10` tests query R5 against `0xF0`:
- For query `q >= 0xF0`, it returns `UBYTE[0x0F10E+15]` directly (return at `0x22E1E`, delay-slot load at `0x22E20`).
- For `q < 0xF0`, it branches to `loc_2350C`. Four shift/rotate pairs at `0x2350C`–`0x2351A` form a 4-bit interval index and fractional nibble. The byte path reads adjacent values at index and index+1 (`0x23532`–`0x2353A`) and calls `sub_231C8` for interpolation.
- The implicit grid is `0,16,32,…,224`, with element 15 as the terminal value for query `>=240`.

## Result destination and first consumer

- `0x85B34` loads R6 = `FFFF2150`; `0x85B36` loads offset `0x8A6`; `0x85B3A` stores the helper result at **UBYTE[`FFFF2150+0x8A6`] = UBYTE[`FFFF29F6`]**.
- `0x85B38` loads R4 = `FFFF371E`; `0x85B3C`–`0x85B40` also stage the same result at **UBYTE[`FFFF371E+0x90`] = UBYTE[`FFFF37AE`]**.
- First direct use after the lookup: `0x85B42` checks `UBYTE[FFFF99F0].bit6`. With that bit clear, `0x85B4A`–`0x85B52` reads `UBYTE[FFFF37AE]` and tests whether it is zero. A nonzero result bypasses the zero-result path; a zero result causes `0x85B5E` to set `UBYTE[FFFFA378+0x384] = UBYTE[FFFFA6FC]` to 1.
- With `FFFF99F0.bit6` set, the alternate branch reads `UBYTE[FFFF29F6]` at `0x85B74` and copies it to `FFFF37AE` at `0x85B7A`.

This is a software-state / zero-nonzero qualification path. The trace does **not** reach an injector command, fuel-pulse register, actuator endpoint or named physical fuel output. In this stock ROM every table value is nonzero (minimum `0x2D`), so the lookup's observed result is nonzero for every query.

## Semantic and donor boundary

The current Release 1 presentation “Cranking Fuel Value vs Coolant” and the donor fingerprint `mTSTNGTM` are hypotheses only. The exact target query source and lookup behavior are established, but they do not prove cranking, fuel, injector or coolant-compensation function.

The V6 donor A2L/HEX pairing remains unverified (WO65212 / WO70006). The user-reported matcher join is not independently reproducible from raw function-pair outputs in the repository. No donor name, physical units or conversion is assigned to EL19A `0x0F10E`.

## Conclusion and stop boundary

**Conclusion:** `0x0F10E` is a structurally verified 16×1 UBYTE lookup with a coolant-keyed query cell, fixed implicit grid and known internal result/staging path. The old cranking-fuel label is not established by this evidence. The first meaningful consumer is a zero/nonzero internal status qualification; no fuel-delivery endpoint is shown.

**Unknowns:** physical function and units of the curve; semantic meaning and producers of the gating bits; broader consumers of `FFFF29F6`/`FFFF37AE`; whether the donor `mTSTNGTM` fingerprint is correctly paired to an equivalent function.

**Stop:** no wider fuel, injector, AFR or actuator hunt; no re-investigation of `0x0F426` or `0x0F062`; no XML/catalogue/scope/workbook change; no donor name or conversion promotion.
