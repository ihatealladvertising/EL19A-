# REC-000026 — `0x0D856`/`0x0C2D6` are 64-element 128-byte 8×8 maps, and their reported companions are sibling lookups, not axes

**Status:** CURRENT
**Affected objects:** the two reported 8×8 UWORD map candidates `0x0D856` and `0x0C2D6`; their reported companion references `0x1100A`, `0x10954`, `0x0CD56`.
**Source evidence:** WO70009; FND-000024; WO70006 §§331–356 lead table and WO70009's reported lead; WO65060; REC-000021 (preserved, unaffected).

## Prior presentation / risk

Two prior non-record sources carried claims that would mislead a definition build:

1. **`CONTROL/WO70006.md`** lines 321–322 recorded the matcher lead as "8×8 UWORD; reported shared-call constellation includes `0x1100A` and `0x0CD56`" (and `0x10954`/`0x0CD56` for `0x0C2D6`), with "exact target axes, caller-to-symbol assignment and target query/output lineage still require EL19A verification".
2. **`CONTROL/WO70009.md`'s reported lead** restated the same geometry as "8×8 UWORD BE geometry (**128 elements / 256 bytes**)" and described `0x1100A`/`0x10954`/`0x0CD56` as "companion caller references" whose role as axes had to be tested.

The 256-byte reading is not merely arithmetically wrong (8×8 UWORD is 64 elements = 128 bytes); it would **overlap an already Verified object**. `0x0D856 + 256 = 0x0D956`, which runs 128 bytes past the start of the 16×16 UWORD BE table `0x0D8D6`–`0x0DAD5`. Publishing a 256-byte extent would therefore have produced a false address overlap in any catalogue or XML entry.

## Corrected interpretation

1. **Extents and storage.** `0x0D856`–`0x0D8D5` and `0x0C2D6`–`0x0C355`; **64 elements / 128 bytes each**, UWORD big-endian, 8 rows × 8 columns, row-major with a 16-byte row stride. Reader for both: `sub_22CF8`.
   - Geometry proof: `0x22D06`/`0x22D14` `mov #h'E,r4` selects an 8-entry UWORD axis (`sub_2340C` start byte offset 14, step −2), and the tail-jump `0x22D26` `mov #8,r5` is the column count, doubled at `0x232DE` `shll r5` into a 16-byte row stride. `loc_232D0` reads `mov.w @r4` / `@(2,r4)` / `@r5` / `@(2,r5)`.
   - Extent proof: `0x0D856 + 128 = 0x0D8D6`, exactly the start of the already Verified `0x0D8D6`–`0x0DAD5` 16×16 table; the preceding `0x0D656`–`0x0D855` table ends at `0x0D855`; the all-`0x8000` fill stops at `0x0D8D5`.
2. **Target axes are dedicated adjacent UWORD vectors, not the reported companions.**
   - `0x0D856`: rows `0x104BC` (`856,1024,1505,2314,3635,4096,5120,6144`), columns `0x104AC` (`640,768,832,896,928,960,1024,1152`).
   - `0x0C2D6`: rows `0xFDF0` (`7936,15872,23808,31744,39680,47616,55552,63488`), columns `0xFE00` (`2048,1792,1536,1280,1024,768,512,256`, strictly **descending**).
3. **The reported companions are sibling lookups in the same enclosing function.** `0x1100A` is a 32×1 UWORD curve (axis `0x10EEA`) via `sub_22FAC` @ `0x6B19E`; `0x10954` is a 16×1 UWORD curve (axis `0xF912`) via `sub_22F80` @ `0x6FC18`; `0x0CD56` is the 16×16 UWORD map with axes `0x0E2C9`/`0x0FEC0` via `sub_22D68` at `0x6B1B0` and `0x6FBD0`/`0x6FC34`/`0x6FC40`. None can serve as an axis of an 8-row grid, and `0x0CD56` occurs in **both** enclosing functions, so it cannot discriminate the pairing.
4. **Queries resolved.** `0x0D856`: rows `U16[FFFF143A]` (`FFFF1054+0x3E6`), columns `U16[FFFF13D8]` (`FFFF1054+0x384`). `0x0C2D6`: rows `U16[0x0A338] = 0x0000` (a ROM constant pointer `0xA324`, 32 zero bytes at `0x0A324`–`0x0A343`), columns `U16[FFFF13D8]` — the **same column cell** as `0x0D856`.
5. **Stock payloads are constant.** `0x0D856` is 64×`0x8000`; `0x0C2D6` is 64×`0x1000`. Because `0x0C2D6`'s row query is a constant zero, `sub_2340C` returns index 0/fraction 0 and the surface is read as **row 0 only** on this ROM.

## Reason and discriminating evidence

- The 128-byte extent is bounded on **both** sides by independently catalogued objects: `0x0D656`+512 = `0x0D855`, and `0x0D8D6` = `0x0D856`+128. A 256-byte reading is excluded by the catalogue, so the error is a fact about the ROM, not an arithmetic preference.
- Geometry is read from the helper's own argument immediates rather than inferred: `mov #h'E,r4` (8 UWORD entries) and `mov #8,r5` (8 columns), with `shll r5` making the 16-byte row stride that `mulu r5,r0` then applies to the row byte offset.
- The companion-role correction is discriminating because `0x0CD56` appears in both candidate functions while carrying 16×16 geometry; a shared, non-8-entry sibling cannot be an axis of an 8-row surface and cannot support a one-to-one symbol pairing.
- No donor name, unit or conversion is promoted. Donor `mTEHOSMAP` and `mMPAMBFAC` are both 8×8 `REC_UWORD_C` with two 8-point axes and share second-axis quantity `COMP_0065`, which is consistent with the shared `U16[FFFF13D8]` column query, but the constant payloads provide no discrimination and the V6 A2L↔HEX pairing remains NOT VERIFIED under WO65212.

## Disposition

- `WO70006.md` lines 321–322 are **not edited** (another lane's closed record); the correction is additive here and its reservation ("exact target axes … still require EL19A verification") is now discharged by FND-000024.
- `WO70009`'s reported "128 elements / 256 bytes" is superseded by 64 elements / 128 bytes for both objects.
- Six additive catalogue rows are supplied (`0x0D856`, `0x104BC`, `0x104AC`, `0x0C2D6`, `0xFDF0`, `0x0FE00`) with raw scaling and no donor names.
- `REC-000021`'s `0x0CD56`↔`0x0FEC0` linked-storage relationship is unchanged and is not duplicated or superseded here; the two new callsites (`0x6B1B0`, `0x6FBD0`/`0x6FC40`) use the documented argument roles.
- No Release 1 XML or scope-matrix edit.

## Confidence

**High:** extents, storage, 8×8 geometry, row stride, all four axes and their values, callsites, enclosing functions, gates, query cells, destinations, and the sibling-not-axis role of `0x1100A`/`0x10954`/`0x0CD56`.
**Unresolved:** physical function and units of either map; the interpolation contract for the descending `0xFE00` axis; ownership of the 128 zero bytes at `0x0C356`–`0x0C3D5`; donor symbol assignment.
