# REC-000018 — WO65910's `FFFF284E` gate is `FFFF34F0.bit4`, not `FFFF34E2.bit4`

**Status:** CURRENT
**Affected objects:** status mask memo `FFFF284E` (= `FFFF2150 + 0x6FE`); status byte `FFFF357A` bit2 (`FFFF34C1 + 0xB9`); gate byte `FFFF34F0` bit4 (`FFFF34C1 + 0x2F`)
**Related finding:** `FND-000012` (GBR-relative address rule), `FND-000013` (delay-slot publication)
**Source WO:** WO65922
**Reconciled source claims:** WO65910 §"Question"/"Answer" — the `FFFF284E` store is "gated by `FFFF34E2.bit4` (`@(h'2F,gbr)` + `tst #h'10`)"

## Previous interpretation

WO65910 recorded that the four-bit mask built at `0x078C0A`-`0x078C2E` is written to `FFFF2150 + 0x6FE` = `FFFF284E` "gated by `FFFF34E2.bit4`", citing the `@(h'2F,gbr)` + `tst #h'10` at `0x078C3C`/`0x078C3E`. It did not state which routine's base was resolved for that site.

## Corrected evidence

The gate site is inside **`sub_77608`**, which installs its own base at `0x07761C`-`0x07761E`:

```
0x07761C  mov.l off_77894,r0   ; h'FFFF34C1
0x07761E  ldc   r0,gbr
```

`off_77894` is `.data.l unk_FFFF34C1`, so `gbr = FFFF34C1` for the whole routine and

```
FFFF34C1 + 0x2F = FFFF34F0
```

`FFFF34E2` is `FFFF34B3 + 0x2F` — the same displacement under a **different** base, belonging to other routines in the `FFFF34xx` block. The gate's address as published does not exist on this path.

## Reason for change

A published report carries a wrong address for a gate that downstream lanes may reason from, and the class of error — resolving a GBR displacement against a base that belongs to other routines rather than the enclosing routine's own `ldc r0,gbr` — is exactly the one `FND-000012` exists to prevent. This lane's precedent (`REC-000013`) is to correct such attributions rather than leave them inside a superseded report.

## What does **not** change

- WO65910's classification of `FFFF3579.bit4` as an internal state flag with an empty consumer set stands.
- The `FFFF3579` access census (five accesses; readers at `0x05461E` and `0x078C0A`) stands; only the gate byte in the `0x078C3C` description is corrected.
- No calibration object, inventory entry, XML object, axis, scaling, unit or definition is affected. `FFFF284E`, `FFFF357A` and `FFFF34F0` are firmware RAM with no ROM image and no catalogue entry.
- WO65910's report is **not edited**.

## Standing rule reinforced

Before citing a `@(h'NN,gbr)` displacement as an address, resolve the enclosing routine's own `ldc rX,gbr` (nearest preceding `rts` as the boundary) and check the pool literal it came from — a displacement shared by several bases in the same block is not evidence of a shared cell.
