# REC-000022 — `0xED64`/`0xEDA0` are temperature-keyed thresholds on one shared query, and `sub_488BA`'s caller chain was misread

**Status:** CURRENT (additive correction; both source reports retained unedited)
**Affected objects:** ROM `0x0ED64`–`0x0ED73`, `0x0EDA0`–`0x0EDAF`; reader `sub_488BA`; caller `0x047B54` (`loc_47B54`)
**Supporting finding:** `FND-000018`
**Source reports:** WO65291 §3/§C (superseded statements), WO65038 §"Final candidate — EDA0" (upheld), WO64892 (upheld)
**Confidence:** HIGH — every statement below is instruction-anchored

## Corrections

### 1. Geometry and axis count — WO65291 §C "4×4 maps — require two axes"

- **Old:** `ED64`/`EDA0` are 4×4 UBYTE maps that "require two axes"; "No co-located axis pointers found in `sub_488BA` loads."
- **Current:** both are 16×1 UBYTE curves. Each is read once by the 1-D interpolator `sub_22E10` (`0x04893A`, `0x048948`), and **both calls are passed the identical query operand** — `U8[FFFF84B4+0x04]` = `FFFF84B8`, loaded at `0x048934` and again at `0x048946`, with no transform before either call.
- **Reason:** the "4×4" reading double-counted the `sizey="16"` curve as a two-dimensional grid; a 16-entry 1-D byte table has one dimension and one axis. There is no missing axis pointer because there is no second axis.
- **Discriminating evidence:** `mov.b @(4,r7),r0` at both `0x048934` and `0x048946`; `extu.b r0,r5` in both `jsr` delay slots (`0x04893C`, `0x04894A`); `sub_22E10` byte path via `loc_23532` with `table[idx]`/`table[idx+1]` only.

### 2. Caller chain — WO65291 §3 "sub_488BA called from 0x48928, 0x4892C, 0x4897E, 0x48982 … → sub_48C1E, sub_48D2E"

- **Old:** `sub_488BA` is called from the listed PCs, which are read as callers within a `sub_488BA` family that then flows into `sub_48C1E`/`sub_48D2E`.
- **Current:** `0x048928`, `0x04892C`, `0x04897E`, `0x048982` are **internal labels of `sub_488BA` itself**, not calls to it. The routine has exactly **one** external caller: `bsr sub_488BA` at `0x047BDA` inside `loc_47B54` (routine entry `0x047B54`, pointer table entry `0x0218F8`). `sub_48C1E` at `0x048C1E` is not a successor in a chain from inside `sub_488BA`; it is called **conditionally by that caller** at `0x047BF0`, only when `sub_488BA` returned non-zero and `UBYTE[FFFF11F3] == 0`. `sub_48D2E` is a sibling call at `0x047C0A`.
- **Reason:** the WO65291 text listed adjacent intra-routine branch targets as a call chain. A `bsr`/`jsr` census over the whole listing returns one hit for `sub_488BA`.

### 3. Output character — WO65038 "paired … both outputs are independently retained"

- **Upheld, with a boundary added.** WO65038's query, stack-staging (`var_28`) and paired-use trace is confirmed without change. What that report's boundary did not reach, and is now recorded, is that both results are used **only** as `cmp/gt` thresholds against `UBYTE[FFFF85A9]` and are never published: `0xED64`'s result is the strict threshold on the V1 paths, `0xEDA0`'s the soft threshold on the V2 paths, and the routine's entire outward product is `UBYTE[FFFF34D2].bit6` plus a 0/1 return.

## Not corrected

- `FND-000017`'s implicit UBYTE grid `0,16,…,240`: unchanged. `FND-000018` only adds that the grid indexes the coolant-temperature image and that entry 15 doubles as the `>= 240` clamp.
- WO64892's `sub_491BC` input contract: unchanged and now anchored to its producer.

## Consequential disposition

The provisional XML labels `Fuel Cut Bosch [S] (ED64)` / `Fuel Cut JECS [S] (EDA0)` with `Rpm_x25` scaling were already marked "unsupported (unproven donor/screenshot conversion)" in the Release 1 scope matrix. They are now **positively contradicted**: the query cell is the coolant-temperature image, and no RPM value is read anywhere in the reader or its caller path. The falling value shape is a temperature dependence.
