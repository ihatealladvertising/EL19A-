# REC-000023 — `0x0F01C` is a 16-byte curve on a coolant query, not a 32-byte rising object with no sensor join

**Status:** CURRENT (additive correction; both source reports retained unedited)
**Affected objects:** ROM `0x0F01C`–`0x0F02B` (curve), `0x0F02C`–`0x0F02F` (bin floor table), companion `0x0EE68`; reader `sub_48D2E`
**Supporting finding:** `FND-000019`
**Source reports:** WO65291 §§A/3 and its F01C row (superseded statements), WO65038 §"F01C" (upheld)
**Confidence:** HIGH — every statement below is instruction- and ROM-anchored

## Corrections

### 1. Extent and dimensionality — WO65291 "32 B (16×1 or 2×16)"

- **Old:** `0x0F01C` is a 32-byte object, "16×1 or 2×16", values `6C 6C 6C 6C 6C 64 60 5C 58 54 4C 3C 3C 3C 3C 3C 26 30 36 3E 00 02 0B 14 1C 25 30 40 50 61 71 81`.
- **Current:** `0x0F01C`–`0x0F02B` is a **16×1** UBYTE curve. `0x0F02C`–`0x0F02F` (`26 30 36 3E`) is a **separate 4-entry bin-indexed table**, loaded by `off_48FFC` at `0x048EFE` and indexed `mov.b @(r0,r5)` with `r0` = the 0–3 bin at `0x048F04`. `0x0F030` is a `0x00` terminator and `0x0F031`–`0x0F03F` is an unrelated 15-byte ascending ramp that this reader never loads.
- **Reason:** the 32-byte window spanned three distinct objects, so neither "16×1" nor "2×16" described it; there is no second 16-point plane at `0x0F02C` — those four bytes are a bin lookup, not a 16-point curve fragment.
- **Discriminating evidence:** only two code references reach the region — `off_48FE8` (curve, `0x048E5A`/`0x048E60`) and `off_48FFC` (`0x048EFE`); `mov.b @(r0,r5)` at `0x048F04` reads a single byte indexed by a register, not a table of points.

### 2. Value range and shape — WO65291 "F01C ~0x00–0x81 (0–129) rising"

- **Old:** the object's range is `0x00`–`0x81` and it is "rising", supporting a read as a restore/ramp-like schedule.
- **Current:** the curve is **strictly non-increasing**: 108,108,108,108,108,100,96,92,88,84,76,60,60,60,60,60 (`0x6C`→`0x3C`). The `0x00`–`0x81` range and the rising shape belong to the **`0x0F031` ramp**, which is not part of this object and is not read here.
- **Reason:** the reported range was computed over the 32-byte window rather than over the 16-byte curve.
- **Consequence:** any "restore/rising schedule" reading that rested on the rising shape is unsupported. (The owner-directed provisional `Rpm_x25` display is a separate presentation decision and is not changed by this record.)

### 3. Query and axis — WO65291 §"Query source: Not resolved" and "No sensor join found"

- **Old:** "Indices computed inside `sub_488BA`; no sensor join found"; F01C's axis "Not co-located".
- **Current:** both the `0xF01C` and `0xEE68` lookups take their query from `mov.b @(4,r7),r0` with `r7 = 0xFFFF84B4` (`0x048E5C`, `0x048E6A`), i.e. **`U8[FFFF84B8]`, the rescaled AN27 NTC coolant-temperature image**, with `extu.b` in the `jsr` delay slots (`0x048E62`, `0x048E6E`) and no other transform. The grid is the fixed `sub_22E10` grid (`FND-000018` §2).
- **Reason:** the query is a plain GBR-relative-free byte load four bytes into the `FFFF84B4` structure base, loaded two instructions before each call; it is not an index computed inside the helper.
- **Note:** WO66048 reached the same conclusion for the sibling `0xED64`/`0xEDA0` pair, so the whole four-table family has one coolant-temperature query domain.

### 4. Reader function — WO65291 §3 "read by single function `sub_488BA`"

- **Old:** `ED64`/`EDA0`/`EE68`/`F01C` are "all read by single function `sub_488BA`".
- **Current:** `0xED64`/`0xEDA0` are read in `sub_488BA`; **`0xEE68`/`0x0F01C` are read in `sub_48D2E`** at `0x048E70`/`0x048E60`. Both routines are separate entries called from the same `loc_47B54` step (`0x047BDA` and `0x047C0A`).
- **Reason:** the F01C pointer load PC `0x048E5A` lies inside `sub_48D2E` (`0x048D2E`–`0x04913C`), not `sub_488BA` (`0x0488BA`–`0x048C1C`), and `0x48FE8` is a pool address rather than a call PC.
