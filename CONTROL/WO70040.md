### 4.3 Pointer, call, query, helper, result and consumer path

The graph matches the closed report on every audited item:

- Pointer source `off_85D30` at `0x85D30`, bytes `00 00 F1 0E`, decoded pointer `0x0F10E`.
- Call `0x85B2E` `jsr @r2` with R4 = table pointer; helper EA `0x22E10` (`sub_22E10`).
- Delay slot `0x85B30` `extu.b r0,r5` makes the query unsigned UBYTE from
  `UBYTE[FFFF84B8]` loaded at `0x85B28`.
- Helper threshold `q >= 0xF0` → last element; otherwise interval index/fraction at
  `loc_2350C` and interpolation through `sub_231C8`; no explicit ROM axis pointer.
- Result R0 → R2 at `0x85B32`; stores at `FFFF29F6` (`0x85B34`) and `FFFF37AE`
  (`0x85B38`); precondition gates `FFFF3614.bit7 = 0`, `FFFF3615.bit7 = 1`;
  post-call selector `FFFF99F0.bit6`; first meaningful consumer reads `FFFF37AE`
  and performs a zero/nonzero qualification; alternate branch `0x85B6E` copies
  `FFFF29F6` to `FFFF37AE`.
- All five unresolved boundaries are present and unchanged: listing provenance,
  beyond-first-consumer, physical function/units, precondition-bit meaning and
  grid-endpoint wording.

No instruction was independently re-decoded, so none of these relationships was

### 4.5 Implicit-grid endpoint conflict

`axis_model` records `start: 0`, `step: 16`, `point_count: 16`,
`reported_last_coordinate: 224` (WO70013 wording `0,16,…,224`) and
`derived_index_15_coordinate: 240`. Arithmetic gives `0 + 16 × 15 = 240 = 0xF0`, which
is consistent with the reported `q >= 0xF0` terminal return; the report's `224`
notation remains a wording conflict. The exact Stage-16 helper instructions were not
available, so the conflict stays `unresolved` with the required discriminator recorded
(re-read `sub_22E10` / `loc_2350C` in the exact listing). The validator emitted exactly
one non-fatal warning for this conflict, as designed.
