## 1. Result

Every one of the 35 objects in `CALIBRATIONS/EL19A_WO65325_provisional_tiered_v1.xml` was read at exactly its declared extent from `EVIDENCE/VERSA f501.bin` (big-endian assembly of `uint16` rows, no reads past declared length) and given a verdict.

The hypothesis survives in substance:

- **No object is constant-like, sentinel-dominated, mis-addressed or empty.** The lowest distinct-value count in the inventory is 2 (`0x108B4`); every other row has ≥ 5 distinct values out of 8–256 samples. No payload reads as `00`/`FF` fill, and no declared extent falls outside the ROM.
- **Twin labels are correct wherever claimed.** All seven byte-identity claims in the file names verify byte-for-byte.
- **Axis geometry is correct wherever an axis is emitted** — 20 unique axis addresses, 49 axis instances, all non-decreasing at their *declared* lengths; the two `0x0FCFC`/`0x0FD3C` "descending" readings in §5 are an artefact of reading 16 entries where the file declares 8, not a defect.
- The hypothesis fails on one point: **9 of the 35 objects emit no axis child at all**, including four that WO65323 assigns a real ROM axis to. That is a structural defect of the emitted file, not of the payloads.

Verdicts: **34 keep** (23 clean, 7 needing only an annotation correction, 9 needing an axis table added; one of those 9 is also the demote) and **1 demote**, **0 drop**.

## 2. Method

- Strict attribute extraction from the file (an `awk` attribute reader over every `<table` line with nesting depth), so the declared address, `storagetype`, `sizex`/`sizey` and axis children drive the reads; nothing was inferred from names.
- Payload statistics: `od -An -v -tu1` over `n × width` bytes, values assembled in `awk` (`w=2` → `b1*256+b2`), counting distinct values, min and max.
- Axis checks: same read, then ascent test and duplicate-index report; sentinel terminals inspected as raw hex.
- Identity: `cmp` on the exact `od` byte ranges of each claimed pair.
- Field of record for axis ownership: `CONTROL/WO65323.md` §3.2–§3.3 rows.

## 4. Findings

### 4.1 Axis `0x109B4` is the four runtime curves' axis and is missing from the file

WO65323 gives `10206 / 10226 / 10CC2 / 10CE2 / 12D38` the shared axis `0x109B4` (16×1 UWORD). ROM `0x109B4` reads `0000 0038 0070 00A8 00E0 0118 0150 0188 01C0 01F8 0230 0268 02A0 02D8 0310 0348` = 0,56,…,840, strictly ascending, 16 entries.

This is confirmed *numerically*, not by naming: all four payloads terminate at `0x0348` = 840, exactly the axis terminal, and the curves stay below it point-wise. The file emits **no** axis child for any of the four, so in an editor they would fall back to an implicit index grid and mis-report every breakpoint. This is the file's most consequential defect.

### 4.2 The four curves are two payloads, and the cross-pairs are exact

- `0x10206` ≡ `0x10CC2` (byte-identical)
- `0x10226` ≡ `0x10CE2` (byte-identical)
- `0x10206` vs `0x10226` differ only in the first four entries: `0000 002A 005A 0094 00D4` vs `0000 001C 0046 0089 00E0`; entries 4–15 are identical, and entries 13–15 are `0348` in all four.

So "curve 1/2 + alternate 1/2" is consistent with `FFFF1E13.bit3` runtime aliasing over two distinct tables — the file's own names are not misleading — but the "alternate" labels should carry the identity explicitly rather than implying four independent calibrations.

### 4.3 `0xF3D6` and `0xF3DE` are the same table twice, including the axes

Both payloads are `FF FF 43 43 A8 C4 E0 FF` and both axes (`0xF3CE`, `0xF3C6`) are `00 01 02 1C 58 68 70 80`. Payload *and* axis are byte-identical; only the addresses differ. The "limiter-pair curve 1/2" naming overstates this: it is one table placed at two addresses, which is either a runtime-selected duplicate or a genuine pair with identical content. Keep both rows (distinct ROM addresses), but annotate as content-identical and do not present them as a complementary pair. Index 0 is `0xFF` and index 7 is `0xFF` — a raw `255` in a table whose other values are 67…224 is plausibly a sentinel/terminal marker; preserved as unknown.

### 4.4 The UWORD correction family is four identical payloads, not one twin pair

`0x0C756`, `0x0C956`, `0x119C4`, `0x11BC4` are all byte-identical (242 distinct values, `0x7F7F`–`0xB1A3`), sharing axes `0x0FCBC` (0–727) and `0x0FCDC` (0–2000). The file labels only `0x119C4` as a twin of `0x0C756`; `0x0C956` and `0x11BC4` are described as independent maps. WO65323 §3.2 already records them as "two exact payload pairs … keep separate", so keeping all four is right, but the twin annotations are incomplete. Conversely the file's negative cases hold: `0xB012`/`0xB112`/`0xB212` are all mutually different, and `0x9B2E` differs from `0x9C2E`/`0x9DAE`.

### 4.5 `0xE678`/`0xE688` are identical and carry no axis

Both read `00 12 12 12 2F 2F 2F 19 03` followed by seven `00` bytes, i.e. 9 meaningful entries and a 7-entry zero tail; the two objects are byte-identical. WO65323 assigns the implicit grid 0,16,…,240 and warns these must not be RPM airflow maps — the file honours the warning (no RPM axis, `[EXP]`, dashpot category) but emits no axis at all, so the grid is unrepresented. The zero tail means only the first 9 breakpoints are exercised; preserved as unknown, not interpreted.

### 4.6 `0x108B4` is a two-level vector — the only demote

16 declared entries hold exactly two values: `0x1900` (6400) × 6, then `0x1E46` (7750) × 10. Two distinct values is not a 16-point coefficient vector; it is one step between two coefficient sets, or a padding-filled block. WO65323 records it as "internal filter only, no units" from reader `sub_22E7C @ 0x5B5CE`. Its terminal value (7750) does not match the `0x109B4` axis terminal (840), so it is not on that grid either. **Demote `[HCP]` → `[EXP]`** and annotate as a two-level vector; the reader's selection rule is queued as WO65502.

### 4.7 Method caution: reading past a declared length fabricates a bad axis

Reading `0x0FCFC` and `0x0FD3C` as 16 U16 values (the length used by the neighbouring 16-row families) produced ranges "96–0" and "6144–0" with duplicates at indices 9–15, i.e. an apparent non-monotonic axis. At the *declared* 8 entries both are strictly ascending (`96,128,…,320` and `6144,8192,…,26624`) and match WO65323 §3.3 exactly. The trailing eight words are zeros belonging to the next block. Any future axis audit must bound reads by the declared `sizex`/`sizey`, never by the row width of a neighbouring family.

### 4.8 Sentinel and terminal checks

- `0x0FEC0` ends `FF FF` = 65535 ✔ as declared; the ladder is `0,2048,4096,8192,12288,16384,24576,32768,40960,49152,55296,57344,59392,61440,63488,65535`.
- `0x0E2C9` is exactly `0,16,24,32,…,128` (16 steps) ✔.
- `0x0F6F2` repeats `764` at indices 14 and 15 — non-decreasing, already recorded in WO65323 as a "repeated 764 tail"; keep.
- `0x0F406` is strictly decreasing `255 → 0` over 32 samples on the declared 0…248/8 grid ✔.
- `0x0B756` payload sits at `0x8008`–`0x8064`, i.e. offset-binary-adjacent to `0x8000` like the `0x0CD56` family, though its axes are unrelated; recorded as an observation only.

## 5. Discrepancies against WO65323 and WO65325

1. **Additive:** WO65325's closeout summarised "16 axis tables". The file actually contains **49 axis instances** over **20 unique addresses**; the 16-row families share axes (e.g. `0x0FCBC` appears 4×). No content error, only the count in the earlier summary.
2. **Additive:** WO65325's `[EST]` count of 3 is correct for objects but the header comment also contains the literal tags, so a naive grep of the file yields 4/25/9. Comment tags should be ignored by any automated audit.
3. **Additive:** WO65323 assigns `0x109B4` to the four runtime curves and a fixed grid to `0xA0F2`/`0xA8A2`/`0xE678`/`0xE688`; none of those five axes/grids is represented in the XML. The file is structurally balanced but not fully loadable as a definition.
4. **No contradiction** was found in any emitted axis address, range or identity claim.
