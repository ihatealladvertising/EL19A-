## Checkpoint 1 — reset fill and first slot-overlap review (2026-11-20)

### Source integrity and method

- Read-only listing used: `EL19A_Complete_Disassembly_ANNOTATED_V3_NEXT6_16_ALL_PENDING_ANNOTATIONS.lst`, 27,045,080 bytes; MD5 `99635224d16ab7705445e27bf233e549`, matching the identity already recorded in WO65062.
- Used targeted text searches/readback in that listing for `FFFF8684`, `FFFF889C`, `00008684`, `0000889C`, and the reset-fill value `0000264C`. This is a first-pass literal/comment search, not an exhaustive direct/GBR/indexed/computed-alias or block-transfer census.

### A. Reset initialization covers both slots

- WO65062 Checkpoint 9's reset trace establishes `Poweron_Reset (0x26BE) → sub_2AA4 (0x2AC2) → sub_275C`; `R7=FFFF8500`, `R4=0x264C`, and the loop's `bf/s` delay-slot store at `0x27F2` writes one U32 per index from `0x00` through `0xE7` inclusive.
- This produces the contiguous destination range `FFFF8500–FFFF889C` inclusive, stride 4 (232 longwords; end-exclusive `FFFF88A0`).
- `FFFF8684` is entry index `0x61`; `FFFF889C` is entry index `0xE7`. Both therefore receive the big-endian reset value `00 00 26 4C` on the established reset path, unless changed later.
- This proves reset initialization only. It does **not** prove either value remains intact when an exception later uses the corresponding VBR slot.

### B. `FFFF8684` is also used as byte state

- The listing contains 16 textual `FFFF8684` matches, including the RAM map row. The following exact-base byte operations are verified in the selected contexts:
  - `0x25E9C` loads `R11=FFFF8684`; `0x25EA8` reads `@R11`, `0x25EAC` ORs `0x80`, and `0x25EAE` writes the modified UBYTE back to `FFFF8684`.
  - `0x2721C` loads `R6=FFFF8684`; `0x27220` reads `@R6`, `0x27224` ORs `0x80`, and `0x27226` writes the modified UBYTE back to `FFFF8684`.
  - `sub_3975E`: `0x39766` loads `R6=FFFF8684` and `0x3976C` reads the base byte; `0x39772` tests bit `0x80`.
- These are actual accesses to the first byte of the candidate longword, not merely symbol-comment mentions. They establish that `FFFF8684` participates in ordinary byte-state operations and is **not established as a vector-only cell**. The functional meaning of the bit and whether those paths overlap any exceptional use remain unresolved.
- Other `FFFF8684` literal-base sites in the search include fixed nonzero-displacement operations (for example offsets `+3`, `+7`, `+9`, `+0x0A`, `+0x0F`) and a pointer load at `0x2661A`; they require separate EA/liveness treatment before being classified. Do not count them as writes to the four-byte slot without resolving each effective address.

### C. `FFFF889C` current bounded result

- The exact `FFFF889C` text search returned the RAM-map undefined-byte row; the target's presence as the final U32 destination is independently established by the reset-loop arithmetic above.
- The first-pass searches did not yet establish a later direct store, full-width overwrite, copy source/destination, or handler pointer for `FFFF889C–FFFF889F`. This is **not** a no-writer result: nonliteral aliases, indexed accesses, bulk copies and other computed destinations have not been exhausted.

### D. VBR / ROM-table distinction

- `0x1578–0x157C` loads `VBR=FFFF8504`; `0x157E` then executes `trapa #0x3E`. The TRAPA vector offset is `0x3E×4 = 0xF8`, so that instruction uses `FFFF85FC`, **not** either target in this WO (`+0x180` / `+0x398`).
- The ROM vector-table entries at offsets `0x180` and `0x398` contain `0x00000E08` and `0x00004304` respectively (WO65062 Checkpoint 19). Their ROM values do not prove corresponding longwords were copied into `FFFF8684` or `FFFF889C`.
- The post-`0x157C` live VBR duration/context and any later vector-slot installation path have not been fully resolved in this checkpoint.

### Checkpoint disposition

- `FFFF8684`: reset fallback is established; later base-byte bit7 writes are confirmed at `0x25EAE` and `0x27226`; a base-byte reader is confirmed at `0x3976C`. Current live vector-target value is unresolved.
- `FFFF889C`: reset fallback is established as the final U32 loop destination; subsequent overwrite/install and current value are unresolved.

## Checkpoint 2 — slot-byte alias and VBR-context reconciliation (2026-11-20)

### A. Exact byte overlaps in `FFFF8684–FFFF8687`

Reset entry remains `00 00 26 4C` at `FFFF8684–FFFF8687` from Checkpoint 1. A second pass on base-register uses resolved additional accesses that the exact `FFFF8684` text search alone did not expose:

- **Byte 0 (`FFFF8684`) — conditional set-bit writers:**
  - `INT_ATU02_ICI0A` (`0x25D5A`): `R11=FFFF8684` at `0x25E9C`; `0x25EA8` reads byte 0; `0x25EAC` ORs `0x80`; `0x25EAE` writes byte 0. This conditionally changes the reset byte `0x00` to `0x80`.
  - `INT_ATU12_IMI1AE` (`0x26F46`): `R6=FFFF8684` at `0x2721C`; `0x27220` reads byte 0; `0x27224` ORs `0x80`; `0x27226` writes byte 0. This is a second conditional writer of the same byte.
  - Base-byte reads/test-bit7 are also confirmed at `0x2689C`, `0x2693A`, and `0x3976C`.
- **Byte 1 (`FFFF8685`) — newly resolved conditional set-bit writer:**
  - In `INT_ATU02_ICI0A`, the alternate `R11=FFFF8684` path starts at `0x25EBA/0x25EBC`. The actual memory access is later: `0x25F4E mov.b @(1,r11),r0` reads `FFFF8685`; `0x25F50` ORs `0x80`; `0x25F52 mov.b r0,@(1,r11)` writes `FFFF8685`. This conditionally changes reset byte `0x00` to `0x80`.
  - The same R11 path reads `@(4,r11)` at `0x25F54` (= `FFFF8688`), outside the four-byte target. It must not be counted as a slot-byte access.
- **Byte 3 (`FFFF8687`) — read/clear operations:**
  - `INT_ATU12_IMI1AE`: reads `@(3,R13)` at `0x26FAE`, and on the relevant branch reads it again at `0x26FE8`, clears bit 7 at `0x26FEA`, then writes it at `0x26FEC`.
  - Reset/init helper `sub_28EE` contains a separate direct UBYTE RMW: `0x290E6` loads `R6=FFFF8687`; `0x290EA` reads it; `0x290EC` ANDs with `0x7F`; `0x290EE` writes it.
  - The reset fill sets byte 3 to `0x4C` (bit 7 already clear), so these clear operations do not alter the initial byte unless another path first sets bit 7. No set-bit writer to byte 3 was established in this pass.
- **Byte 2 (`FFFF8686`):** no direct literal access or fixed-displacement access to this byte was identified in the selected pointer-base contexts. This is not a global no-access proof.

### B. Function and vector-table contexts

- `0x25EAE` and `0x25F52` are inside `INT_ATU02_ICI0A`, whose entry is `0x25D5A`; the alternate ROM vector table at `0x20154` names that entry (relative offset `0x150` from VBR `0x20004`).
- `0x26FAE/0x26FEC` and `0x27226` are inside `INT_ATU12_IMI1AE`, entry `0x26F46`; alternate vector-table entry `0x20194` names it (relative offset `0x190` from VBR `0x20004`).
- These vector-table mappings identify the routines' interrupt-entry labels in the `0x20004` table; they are **not** the `VBR+0x180` slot under investigation and do not by themselves establish which VBR is active at every runtime execution.
- `0x290EE` is in `sub_28EE`, called by `sub_2AA4` at `0x2AC6` in the reset initialization chain. It clears bit 7 of byte 3. This does not establish the post-reset value of the vector longword beyond the actual byte operation.

### C. Correct VBR epochs — keep the two setup paths separate

- Conditional custom-VBR path: `loc_154E` reaches `0x157C` only after the `sub_33FE()` result comparison at `0x1558` and `FFFF83D3==2` at `0x1560`. `0x1578` loads `FFFF8500`, `0x157A` adds 4, and `0x157C` writes `VBR=FFFF8504`; `0x157E` then executes `TRAPA #0x3E`, whose slot is `FFFF85FC` (`VBR+0xF8`).
- Reset/alternate-table path is different: `0x26BA` sets `VBR=0x20004`, executes TRAPA at `0x26BC`, calls `sub_2AA4` at `0x26BE`, then `0x26C2` explicitly loads `R2=0` and `0x26C4` writes `VBR=0`. Therefore `0x26C4` is **not** a second setup of `FFFF8504`; do not conflate it with `0x157C`.
- WO65019 confirms the `0x157E` TRAPA target itself remains unresolved because `FFFF85FC–FFFF85FF` has no complete runtime longword in WO65020. No post-TRAPA VBR restore/handler-state join has been proven here. The period for which `FFFF8504` remains the live VBR is therefore unresolved.

### D. `FFFF889C` pointer-root and transfer review

- Exact direct-literal text search for `FFFF889C` still returns only the RAM-map row; reset initialization is the sole direct evidence tied to this exact address.
- A bounded scan of literal pointer comments in `FFFF88xx` found roots `FFFF8854` and `FFFF885C` only. The `FFFF8854` context writes at base+4 (`FFFF8858`), not the target.
- The reviewed `FFFF885C` contexts form pointer values `FFFF885C + index×0x80` (`0x43A9C–0x43AAA`; fallback construction at `0x43B30–0x43B4A`) and place them in descriptor fields. `FFFF889C` is `FFFF885C+0x40`, not reachable by that specific scale. These instructions do not establish a write to `FFFF889C`; this is a bounded result for the inspected roots, not a global exclusion.
- A **verified-capability / runtime-conditional potential writer** remains open from WO65062 Checkpoint 18 and Corrections 18a–18d: `sub_1C5C` copies packet bytes to a record-supplied destination after validating the destination/end interval against `FFFF8500–FFFFBD00`. The packet mailbox source, live state gate, packet destination bytes and length are not known; no actual write to either slot is claimed.
