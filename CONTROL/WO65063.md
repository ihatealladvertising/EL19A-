## Checkpoint 1 — reset fill and first slot-overlap review (2026-11-20)

### Source integrity and method

- Read-only listing used: `EL19A_Complete_Disassembly_ANNOTATED_V3_NEXT6_16_ALL_PENDING_ANNOTATIONS.lst`, 27,045,080 bytes; MD5 `99635224d16ab7705445e27bf233e549`, matching the identity already recorded in WO65062.
- Used targeted text searches/readback in that listing for `FFFF8684`, `FFFF889C`, `00008684`, `0000889C`, and the reset-fill value `0000264C`. This is a first-pass literal/comment search, not an exhaustive direct/GBR/indexed/computed-alias or block-transfer census.

### A. Reset initialization covers both slots

- WO65062 Checkpoint 9's reset trace establishes `Poweron_Reset (0x26BE) → sub_2AA4 (0x2AC2) → sub_275C`; `R7=FFFF8500`, `R4=0x264C`, and the loop's `bf/s` delay-slot store at `0x27F2` writes one U32 per index from `0x00` through `0xE7` inclusive.
- This produces the contiguous destination range `FFFF8500–FFFF889C` inclusive, stride 4 (232 longwords; end-exclusive `FFFF88A0`).
- `FFFF8684` is entry index `0x61`; `FFFF889C` is entry index `0xE7`. Both therefore receive the big-endian reset value `00 00 26 4C` on the established reset path, unless changed later.
- This proves reset initialization only. It does **not** prove either value remains intact when an exception later uses the corresponding VBR slot.

### B. `FFFF8684` is also used as byte state

- The listing contains 16 textual `FFFF8684` matches, including the RAM map row. The following exact-base byte operations are verified in the selected contexts:
  - `0x25E9C` loads `R11=FFFF8684`; `0x25EA8` reads `@R11`, `0x25EAC` ORs `0x80`, and `0x25EAE` writes the modified UBYTE back to `FFFF8684`.
  - `0x2721C` loads `R6=FFFF8684`; `0x27220` reads `@R6`, `0x27224` ORs `0x80`, and `0x27226` writes the modified UBYTE back to `FFFF8684`.
  - `sub_3975E`: `0x39766` loads `R6=FFFF8684` and `0x3976C` reads the base byte; `0x39772` tests bit `0x80`.
- These are actual accesses to the first byte of the candidate longword, not merely symbol-comment mentions. They establish that `FFFF8684` participates in ordinary byte-state operations and is **not established as a vector-only cell**. The functional meaning of the bit and whether those paths overlap any exceptional use remain unresolved.
- Other `FFFF8684` literal-base sites in the search include fixed nonzero-displacement operations (for example offsets `+3`, `+7`, `+9`, `+0x0A`, `+0x0F`) and a pointer load at `0x2661A`; they require separate EA/liveness treatment before being classified. Do not count them as writes to the four-byte slot without resolving each effective address.

### C. `FFFF889C` current bounded result

- The exact `FFFF889C` text search returned the RAM-map undefined-byte row; the target's presence as the final U32 destination is independently established by the reset-loop arithmetic above.
- The first-pass searches did not yet establish a later direct store, full-width overwrite, copy source/destination, or handler pointer for `FFFF889C–FFFF889F`. This is **not** a no-writer result: nonliteral aliases, indexed accesses, bulk copies and other computed destinations have not been exhausted.

### D. VBR / ROM-table distinction

- `0x1578–0x157C` loads `VBR=FFFF8504`; `0x157E` then executes `trapa #0x3E`. The TRAPA vector offset is `0x3E×4 = 0xF8`, so that instruction uses `FFFF85FC`, **not** either target in this WO (`+0x180` / `+0x398`).
- The ROM vector-table entries at offsets `0x180` and `0x398` contain `0x00000E08` and `0x00004304` respectively (WO65062 Checkpoint 19). Their ROM values do not prove corresponding longwords were copied into `FFFF8684` or `FFFF889C`.
- The post-`0x157C` live VBR duration/context and any later vector-slot installation path have not been fully resolved in this checkpoint.
