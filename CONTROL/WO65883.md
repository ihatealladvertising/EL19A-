## Question

## Where the truncation actually writes

The `0x0A8A2` LPF path lives in the single large function entered at `0x05FA86` (GBR = `FFFF8E54`; no `rts` occurs between `0x05FA86` and `0x06xxxx` through `0x064320`, so the base holds across the whole span):

```
0x063C10  mov.l @(0x2EC,gbr),r0   ; ULONG[FFFF8E54+0x2EC] = ULONG[FFFF9140]   <- LPF result
0x063C12  tst   r0,r0
0x063C14  bt/s  loc_63C54         ; zero/nonzero gate
0x063C18  ...                     ; nonzero -> UBYTE[FFFF9180]
...
0x06431C  mov.l @(0x2EC,gbr),r0   ; ULONG[FFFF9140] again
0x06431E  mov.b @r2,r14
0x064320  mov.b r0,@(0x4A,gbr)    ; UBYTE[FFFF8E9E]  <- byte truncation
0x064322..0x064328                ; neighbouring bytes @0x49/@0x48 -> FFFF8E9D/FFFF8E9C
```

So the LPF staging byte is `UBYTE[FFFF8E9E]`, and its LPF source is `ULONG[FFFF9140]`.

### Readers of `FFFF8E9E`

Only two, both inside the same function, both the zero/nonzero gate that drives a ±1 saturating counter:

```
0x062DB2  mov.b @(0x4A,gbr),r0 / tst r0,r0 / bf loc_62DDC   ; then @(0x108,gbr) = FFFF8F5C, @(0x106,gbr) = FFFF8F5A
0x062E02  mov.b @(0x4A,gbr),r0 / tst r0,r0 / bf loc_62E40   ; second gate in the same state machine
```

No torque-request, throttle-target, dashpot or actuator command is reached from either.

## Verdict

WO65859's **conclusion stands** (internal staging, no second consumer reaching a named output) but its **address label was wrong**: the staging byte is `UBYTE[FFFF8E9E]`, not `FFFF109E`, and the LPF source is `ULONG[FFFF9140]`, not `ULONG[FFFF1054+0x2EC]`.

**Classification: INTERNAL STAGING (counter gate only, no named output).** No calibration definition or name may attach to `FFFF8E9E` or `FFFF9140`.

### Reconciliation (additive — no edit to WO65838 or WO65859)

- **Old claim (WO65838/WO65859):** `ULONG[FFFF1054+0x2EC]` is truncated to `FFFF109E` at `0x06431C` and read by ten `@(h'4A,gbr)` sites, none reaching a named output.
- **Corrected claim:** the base of that function is `FFFF8E54`, so the truncation reads `ULONG[FFFF9140]` and writes `UBYTE[FFFF8E9E]` at `0x064320`; `FFFF8E9E` has exactly two readers (`0x062DB2`, `0x062E02`), both counter gates; the other eight sites read `FFFFB4F2`, `FFFF1DE2`, `FFFF350B`, `FFFF349E` (×4) and `FFFF3672`.
