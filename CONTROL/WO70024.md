The `0x0CD56` / `0x11FC4` identical hash is a **real** duplicate: the ROM contains the same 128-byte block at both offsets (verified byte-for-byte; exactly two occurrences at 2-byte alignment). This is a genuine limitation of a fixed 128-byte payload hash as a table identity, not a calculation error.

**Cross-reference sweep.** Joining the recorded addresses against the actual schemas (`table@storageaddress` for XML, `address` for the scope matrix and catalogue):

- **20/24** recorded target addresses exist in both EL19A XMLs and in the scope matrix; **12/24** also exist in `discovered_tables_catalog.csv`; **0/24** exist in `CF48D.xml`.
- **24/24** rows contain **at least one** displayed address that exists in the EL19A best-guess XML.
- The report nonetheless records `NO TARGET MATCH` for **24/24** and `IN SCOPE: unknown` for **24/24**.

**Cause.** `analyze_screenshots_v2.py` reads `table.get('address','')`, but the EL19A XML uses `storageaddress` (and `sizex`/`sizey`, `storagetype`, `endian`); the attribute is never present, so the address-match branch is unreachable. For scope and catalogue it calls `.iloc[0].get("name", "unknown")`, but those files have `baseline_name` / `address` columns and no `name` column, so every match degrades to `unknown`. These are deterministic schema-mismatch bugs, not isolated data errors.

## 8. Limitations

- This audit did not redo OCR and did not run either recovered script; it verifies structure, hashes, addresses and schema joins, not visual cell reading.
- "Address present in XML" is **not** proof of geometry or value agreement. It is used only to show that `NO TARGET MATCH` is a false negative at the object-identification level.
- Only the 128-byte payload window and the recorded address were checked; table extents, axes and conversions were not evaluated.
- Exact OCR byte reproducibility was not tested and cannot be guaranteed without the original environment.
- The four `UNKNOWN`-source rows need manual review; their target claims are internally inconsistent and were not resolved here.
- The 128-byte window is a fixed probe, not the table extent; duplicate 128-byte blocks exist (demonstrated at `0x0CD56`/`0x11FC4`), so the hash alone cannot identify a table uniquely.
