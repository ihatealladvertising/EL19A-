## Decision question

What writes or transfers supply UWORD `FFFF85B2` (also addressed as `FFFF859C+0x16`), the common query input reused by several otherwise distinct lookup families? Resolve a concrete producer path if static evidence supports one; otherwise establish the precise bounded writer/transfer boundary without inferring the field's physical meaning.

## Why this is high priority

The same UWORD is consumed by:
- paired 16×16 UBYTE surfaces `0x9C2E/0x9DAE` (caller `0x42B9C–0x42BC8`);
- dynamic-axis 16×16 UBYTE map `0x9B2E` (multiple callers around `0x473xx–0x476xx`);
- 8×8 UBYTE map `0xAB22` (caller around `0x4E2AE`);
- four inline 8×8 SWORD channels `0x0B422/0x0B4A2/0x0B522/0x0B5A2` in `sub_969C2`.

One producer trace can therefore resolve the runtime query provenance across several high-value table groups.

## First confirmed correction — sub_969C2 query is local, not incoming R12

At entry `sub_969C2` saves R12, but later assigns it locally:
- `0x969EC`: load base `FFFF859C` into R13.
- `0x96A12`: read UWORD `@(0x16,R13)` = `FFFF85B2`.
- `0x96A14`: `extu.w r0,r12`; this zero-extends the UWORD into R12.
- `0x96A16`: test R12.
- R12 is not redefined between `0x96A14` and the final-axis search at `0x96C12–0x96C28`; that search compares UWORD axis `0xFD9C` entries against this query at `0x96C1C`.
- The lookup's final column index is therefore derived from UWORD `FFFF85B2`, not an untraced incoming dispatcher R12 value. The scheduled/direct call at `0x70882` is not the source of this query value.

Confirm the bytes against the pinned ROM and preserve the exact branch/index/clamp semantics. Do not infer a physical sensor or engineering unit.
