## Bounded work

### A. Validate `0x84C4` candidate threshold (EL19A target)

1. ROM `0x84C4` is defined as `off_84C4:` at listing:14646–14647:
   ```
   000084C4  00 0A 0A 64              DATA      .data.l loc_A0A64
   ```
   It is a 4-byte pointer (`off_84C4 → loc_A0A64`), **not** a UBYTE scalar threshold. Embedded bytes: `0x84C4=0x00`, `0x84C5=0x0A`, `0x84C6=0x0A`, `0x84C7=0x64`.

2. `off_84C4` is referenced in code exactly once, at listing:74009:
   ```
   0003560A  C4 0F  mov.b   @((off_84C4+3 - h'84B8),gbr), r0
   ```
   This computes `gbr + (0x84C7 − 0x84B8) = gbr + 0x0F` and reads byte `0x84C7 = 0x64` — a pointer dereference, **not** a threshold comparison. No instruction loads or compares `0x84C4`, `0x84C5`, or `0x84C6` as a threshold operand.

3. No comparison in `sub_403D8` (or elsewhere) uses `0x84C4` as the threshold comparator. The threshold comparator in `sub_403D8` uses `0x8550` (WO65183 §1), not `0x84C4`.

**Finding A:** `0x84C4` is **rejected** as an EL19A candidate threshold. It is pointer data (`off_84C4 → loc_A0A64`), referenced only via a pointer dereference reading `0x84C7`. It is not consumed as a threshold anywhere in the listing.
