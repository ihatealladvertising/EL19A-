## Decision and principal result

A runtime diagnostic reporting path is established through `sub_31DAA`:

- The dispatcher calls it when the selected branch value in R14 is `1` (call at `0x31BCA`).
- It scans a 198-entry ROM pointer table at `0x13780` in lockstep with a 198-slot RAM status array at `FFFFA074`, using 4-byte pointer stride and 3-byte status stride.
- Each slot is filtered by a per-record status-byte bit and a bit in the first UWORD at the pointed-to ROM descriptor.
- Eligible slots increment an aggregate byte at `FFFF2F00+0x413`; a separate per-record bit contributes an aggregate `0x80` flag.
- The aggregate count/flag and other status bytes are appended to a diagnostic response buffer beginning at `FFFF2FBB`, with the write index at `FFFF3316`, through `sub_33E18`.

This proves one diagnostic response-building path, not the DTC code table's runtime consumption, DTC detection/writer logic, or the final physical serial transmission.

## 1. Distinguish the DTC code table from the runtime descriptor-pointer table

WO65090 identifies the DTC-like code record block:
- Start: `0x12E44`
- End-exclusive: `0x13780`
- Record size: 12 bytes
- Count: `0x93C / 12 = 197` records
- Code field: UWORD at record offset `+6`

Immediately following it is `dword_13780`:
- Start: `0x13780`
- End-exclusive: `0x13A98` (FID `8CMCKRN5` begins at `0x13A98`)
- Size: `0x318` bytes = 198 longword pointers
- Sample first entries: `0x116D4`, `0x116BE`, `0x115E8`, `0x1148E`, `0x115A2`, etc.

**Important count mismatch:** the ROM code table has 197 records, while the pointer table and the runtime loop have 198 entries. The code in this WO consumes `dword_13780`, not the 197-record block at `0x12E44`. Do not assume the two arrays are one-to-one or that a pointer entry is the description for the DTC code at the same ordinal. The relationship remains unresolved.

## 2. Runtime indexed reader and per-record gates

`sub_31DAA` establishes GBR as `0x12844`, reads the selector byte at `FFFF2F00+0xB4`, and calls `sub_33E18` to append the initial response byte. In its DTC/status-report branch:

- R4 starts at index 0; R7 starts at byte offset 0 into the RAM status array.
- R12 is initialized to `0xC6 = 198`; each loop increments R4 by 1 and R7 by 3. The loop therefore visits indices 0–197.
- The per-entry RAM base is `FFFFA074 + 3×index`.
- It reads status byte `record+2`; if bit `0x04` is set, that entry is skipped.
- Otherwise it loads `dword_13780[index]`, dereferences the 32-bit ROM pointer, reads the first UWORD at that target, and skips the entry if bit `0x80` is set.
- If both gates pass, it increments the aggregate counter `FFFF2F00+0x413`, subject to the bound described below.
- Independently, it reads status byte `record+1`; if bit `0x20` is set on any scanned record, it sets an aggregate `0x80` flag in R11.

This is a proven indexed pointer-table reader. The pointer-target first-word bit is a descriptor-level gate; the listing does not establish its semantic name. The status-array bits are per-entry gates/flags, not confirmed Nissan symbols.

## 3. Aggregate count and response-byte construction

- At the beginning of the scan, `FFFF2F00+0x413` is cleared to zero.
- An eligible record increments this byte unless its current value is already greater than `0x7F`.
- Because the compare is against the current value before increment, a current value of `0x7F` can increment once to `0x80`; subsequent increments are suppressed. Do not simplify this to a proven clean 0–127 saturation.
- After the loop, the function ORs the aggregate counter with R11 (which is either zero or `0x80` and passes the combined byte to `sub_33E18`.
- **Bit-7 ambiguity:** the count can reach `0x80`, while the independent status flag also uses `0x80`). The code proves the OR operation, but the protocol-level interpretation of this combined bit is unresolved. Do not call it a DTC count with a confirmed overflow or MIL meaning.
- Additional response flags are assembled from GBR-relative state bytes (including offsets `+6`, `+0x37`, `+0x31), and `+0x39)) and appended through the same writer. Their complete bit semantics are outside this bounded path.

## 4. Diagnostic response buffer endpoint

`sub_33E18` is the response-byte append primitive:
- Base pointer: `FFFF2F00`
- Output buffer base: `FFFF2F00+0xBB = FFFF2FBB`
- Current byte index: `FFFF2F00+0x416 = FFFF3316`
- Store: `FFFF2FBB + index` receives R4 as one byte.
- The index at `FFFF3316` is incremented by one and stored back.

Thus the DTC/status reporting path reaches a concrete RAM diagnostic-response buffer. The path followed here ends at that buffer. No proven consumer/transmitter from `FFFF2FBB` to the SCI output/message buffer or physical diagnostic connector was established in this WO.

**Dispatcher distinction:** the neighboring case-8 branch at `0x31C20` calls `sub_332E0`, which uses a separate `dword_DFBC` group mask and `FFFF2150+0x5A6`. It is not the `dword_13780` indexed reader traced here; do not merge the two service paths.
