## 1. Result

The hypothesis fails, and it fails in a way that also corrects WO65328.

1. **`FFFF1810` is not a commanded setpoint.** Its only writer, `sub_36A26` (`0x36A42` read / `0x36A76` write), computes a first-order low-pass of `FFFF1810` **toward `FFFF1840`** with the ROM coefficient `U8[0x87C6]`; `FFFF1840` is the command source, `FFFF1810` the filtered state that the error term then subtracts from.
2. **`FFFF1820` has no producer anywhere in the listing.** It is read once as a word (`0x36E58`) and appears once as a **call target** (`mov.l off_4D54,r6 ; jsr @r6` at `0x4BB0`, ROM literal at `0x4D54` verified `FF FF 18 20`). A 16-bit data cell cannot also be a valid code entry, so the "compared measured level" reading is unsupported.
3. **`FFFF1838` also has no producer** — a single read at `0x36E84`, nothing else in the whole listing.
4. **`FFFF1814`'s first consumer is `sub_37074`**, which folds it into a 32-bit accumulator `FFFF183C = U16[FFFF1830] + U32[FFFF1814] + U16[FFFF1CA8+0x2C]` (clamped at 0). That accumulator is then read at `0x374C8` and scaled by `U16[0x94EE]`/`U8[0x8B83]` — a computed output, not a stored actuator word.

So the loop's *own* arithmetic is real and verified, but two of its three inputs (`FFFF1820`, `FFFF1838`) are unproduced, and its "setpoint" is a filter state. Physical domain stays **UNRESOLVED**, and the earlier "regulated target" classification must be weakened to "internal filter + rate-limited update whose reference cells are not written in this listing".

## 2. `FFFF1810` is the output of a filter, not a setpoint (`sub_36A26`)

Prologue: `ldc` gbr = `FFFF180C` (`off_36C1C`), so every `gbr` displacement below is `FFFF180C + disp`.

| PC | Instruction | Meaning |
|---|---|---|
| `0x36A30`–`0x36A36` | `r6 = U16[FFFF861A]`; `r0 = U8[r6+2]`; `tst #1`; `bt loc_36A72` | gate on `U8[FFFF861A+2].bit0` |
| `0x36A72`–`0x36A76` | `r0 = U16[FFFF1840]`; `mov.w r0, @((word_FFFF1810 - h'FFFF180C),gbr)` | gate clear ⇒ **state := command**, no filtering |
| `0x36A38`–`0x36A40` | `r2 = off_36C20 = 0x87C6`; `r0 = U16[FFFF1840]`; `r5 = U8[0x87C6]`; `r4 = extu.w r0` | command into `r4`, coefficient `k = U8[0x87C6]` |
| `0x36A42`–`0x36A4C` | `r0 = U16[FFFF1810]`; `r2 = 1 << 8`; `r2 = 0x100 − k`; `r5 = extu.w r0` | old state and `256 − k` |
| `0x36A46`, `0x36A4E`, `0x36A50`–`0x36A56` | `mul.l r4,r5` → `macl = FFFF1840 × k`; `mul.l r5,r2` → `macl = FFFF1810 × (256−k)`; `r6 = r6 + r2`; `shlr8` | `(cmd·k + state·(256−k)) >> 8` |
| `0x36A58`–`0x36A6C` | compares against both inputs, `±1` when the rounded result equals or passes an input | no-overshoot guard |

That is exactly a one-pole slew/ramp: `state' = state + (cmd − state)·k/256`. `U8[0x87C6]` is a **ROM filter coefficient**, not a gain on an error.

**Correction to WO65328 §2:** `FFFF1810` is "the filtered value of `FFFF1840`", not "the setpoint". WO65328's arithmetic (subtraction, `U8[0x8307]` gain, `/8` rounding, clamps, two destinations) is unaffected; only the naming of the two cells changes. `FFFF1840` is the candidate command and itself has **no producer** (three reads: `0x36A3A`, `0x36A72`, `0x370B8`).

## 3. `FFFF1820` — no producer, one call target

Whole-listing references to `FFFF1820` (grep, both the code and the RAM declaration):

| PC | Instruction | Reading |
|---|---|---|
| `0x36E58` | `mov.w @((word_FFFF1820 - h'FFFF180C),gbr), r0` | the word read in `sub_36E02`'s error term |
| `0x4BAE` | `mov.l off_4D54, r6 ; h'FFFF1820` | pointer load |
| `0x4BB0` | `jsr @r6` | **call** into `0xFFFF1820` (args `r4 = 0xFA0`, `r5 = 0`) |
| `0x4D54` | `.data.l word_FFFF1820` | literal, ROM `FF FF 18 20` verified with `od` |

There is **no store** to `FFFF1820` through any literal base, `gbr` displacement, or `@(disp,rN)` in the listing. The two xref rows that claim writes are mis-attributed and resolve elsewhere (§5).

The `jsr` at `0x4BB0` sits in a reset/programming path, not a control path: `0x4B40` `add #-4,r15`, `r12 = 0xFFFF83AE`, `r13 = 0xFFFFE800`, `r14 = 0xFFFF1800`; it clears a bit in `U8[FFFF83AE]`, writes `U8[FFFF1800] = 0xFF` (`0x4B60`), reads that byte back and tests it (`0x4B96`–`0x4B9A`), masks `SR` to supervisor with `#0xF0` (`0x4B6C`–`0x4B74`), sets `VBR = 0` (`0x4B78`), then sets bits in `U8[FFFF826F]` (`0x4B9E`–`0x4BA8`) and calls `FFFF1820` with `r4 = 0x0FA0`, `r5 = 0`.

**Leading explanation (recorded as a hypothesis, not a fact): RAM overlay.** The `FFFF1800` block is executed as code in the programming/reset path and holds data in the running application; whichever routine uploads that kernel is not present among the modelled forms. WO65118's own header states that "computed pointers, pointer tables, block-copy and `movca.l` transport are not modelled", so absence of a writer here is *not* proof of absence — but it is also not evidence for the "measured level" reading, which the `jsr` actively contradicts.

**Consequence for the loop:** the error `FFFF1810 − FFFF1820` subtracts a cell with no writer from a filter state. Whether that cell is stale RAM, a downloaded-kernel entry, or written through an unmodelled transport cannot be decided from this listing; the physical-domain question therefore stays open, and no claim that `FFFF1810`/`FFFF1820` are the same physical quantity may be made.

## 4. `FFFF1814` / `FFFF1818` — first consumer found

`FFFF1814` (long, written only at `0x37060` inside `sub_36E02`) is consumed by **`sub_37074`**:

| PC | Instruction | Meaning |
|---|---|---|
| `0x37076`–`0x3707A` | gbr = `FFFF180C`; `r0 = U16[FFFF1830]`; `r6 = r0` | base term |
| `0x3707C`–`0x3708C` | `r5 = 0xFFFF1CA8`; `r0 = U32[FFFF1814]`; `r2 = r0 + r6`; `r6 = U16[r5+0x2C]`; `r2 += r5` | `FFFF1830 + FFFF1814 + U16[FFFF1CA8+0x2C]` |
| `0x3708E`–`0x37092` | `cmp/pz r2`; if negative `r2 = 0` | clamp at 0 |
| `0x37096` | `mov.l r0, @((dword_FFFF183C - h'FFFF180C),gbr)` | store accumulator `FFFF183C` |

`FFFF183C` is read at `0x374C8` (`mov.l @((dword_FFFF183C - h'FFFF180C),gbr), r0`) where it is `cmp/pl`-gated and then scaled: `U16[0x94EE]`, `U16[0x94EE]` high word, `U8[0x8B83]`, an interpolation through `sub_21BE4`, and a compare against `0x727`. That chain ends in a computed value rather than a stored command word, so the integrator's first consumer is a **position/offset accumulator feeding a scaled computation**, not an actuator store.

The second half of `sub_37074` (`0x370AA`+) builds the same sum from `FFFF1840` when `U8[0x8B60] == 0`, compares the result against `U16[FFFF1822]` (`0x370FC`, `0x3712A`) and writes a word at **`FFFF1812`** (`0x37154`, `mov.w r0, @(6,gbr)` with gbr = `FFFF180C`), then stores to `U16[FFFF84A4+4]`. `FFFF1812` has no symbol in the RAM map — the listing itself prints the raw `@(6,gbr)` form instead of a `word_FFFF1812` label, which is consistent with an un-demarcated cell inside the `FFFF1810` word pair.

`FFFF1818` (word) is written only inside `sub_36E02` (`0x36EEE`, `0x36F04`, `0x37066`) and read only inside it (`0x36F36`, `0x36FBC`); no external consumer exists for it in the listing, so it is a loop-internal rate state, consistent with WO65487's finding for its sibling `FFFF1640`.

## 5. Additive correction: the RAM xref's `address` column is not always the resolved cell

For `base_disp` rows in this block the WO65118 xref reports a cell that disagrees with literal + displacement arithmetic. Three verified cases:

| xref row | xref address | instruction | literal base | true cell |
|---|---|---|---|---|
| `0x292DC` `sub_28C36` | `ffff1820` | `mov.w r0, @(2,r14)` | `off_29494` = `FFFF181C` (ROM `0x29494` = `FF FF 18 1C`) | `FFFF181E` |
| `0x7B2D8` `sub_7B22E` | `ffff1820` | `mov.l @(h'14,r6), r5` | `FFFF17D0` | `FFFF17E4` |
| `0x37154` `sub_37074` | `ffff1818` | `mov.w r0, @(6,gbr)` | `FFFF180C` | `FFFF1812` |

`0x29494` was re-read from ROM to settle the first row; the LST's own literal annotation and the ROM agree. Consequence: **no xref row may be used to claim a writer of `FFFF18xx` without recomputing base + displacement**, and the "write" rows for `FFFF1820` in §3 are refuted rather than merely doubted. `FFFF181E`, `FFFF1812` and `FFFF17E4` are the real cells those three instructions touch.

## 6. What the loop actually is (as far as this listing proves)

```
FFFF1840 --(no producer)--> LPF(k = U8[0x87C6], gate U8[FFFF861A+2].bit0) --> FFFF1810
error   = FFFF1810 - FFFF1820          (FFFF1820: no producer, also a jsr target)
rate    = error * U8[0x8307] / 8        (sign-corrected, WO65328)
offset  = ±U16[FFFF1838]                (FFFF1838: no producer)
rate   -> FFFF1818 (word, loop-internal) and FFFF1814 (long)
FFFF1814 -> sub_37074: FFFF183C = FFFF1830 + FFFF1814 + U16[FFFF1CA8+0x2C]
FFFF183C -> 0x374C8: scaled by U16[0x94EE] / U8[0x8B83] -> computed output
```

Three of the chain's five source cells (`FFFF1820`, `FFFF1838`, `FFFF1840`) and the accumulator base `FFFF1830` have **no writer in the listing**. That is a coherent picture only if the `FFFF18xx` block is populated by a transport this listing does not model (block copy / computed pointer), which is now the single testable question and is queued as WO65505.
