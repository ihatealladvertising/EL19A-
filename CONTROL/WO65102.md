## Findings

### Track A/B — a serial-message indirect-read path can reach either stage address

A runtime pointer path is established in the listing:

1. `sub_2C74E` is called at `0x2C6CC` in the SCI setup/service path. It parses data from the RAM receive/work buffer beginning at `FFFF8005`; its GBR state is `FFFF82E0`.
2. At `0x2CA1C`, the parser calls `sub_2BD74`; the delay-slot instruction at `0x2CA22` supplies the record byte offset in R4. The helper reads four bytes from `FFFF8005 + offset` and assembles them in big-endian order:
   `byte0<<24 | byte1<<16 | byte2<<8 | byte3`.
   The assembly is visible at `0x2BD78–0x2BDA4` (including the RTS delay-slot addition).
3. The returned 32-bit value is retained in R6 at `0x2CA26`. R13 is scaled by four at `0x2CA28–0x2CA2A`; `0x2CA2C` stores the pointer into `FFFF8234 + 4*R13`. R14 advances by four per input record at `0x2CA3A`.
4. `message_build_and_finalize` is called by `message_timer_tick` at `0x2BC82`. It sets GBR to `FFFF820C`; therefore its pointer-table base at GBR+`0x28` is `FFFF8234`. In the 1-byte group, `0x2CB02` loads the selected pointer into R4, `0x2CB06` sets R6=1, and `0x2CB08` calls `message_buffer_copy`. The corresponding 2-byte and 4-byte groups repeat this at `0x2CB36/0x2CB3C` and `0x2CB6C/0x2CB72`.
5. `message_buffer_copy` at `0x2BDCA` treats R4 as its source pointer. Its loop at `0x2BDD8–0x2BDE4` reads each source byte via `mov.b @r4+,r2` and writes it to the message buffer based at `FFFF810A` using the supplied output offset and length.

**Implication:** the source address is supplied at runtime through four bytes in the receive/work buffer; it is not a ROM literal. The inspected parser-to-copy path does not apply a source-address range check before dereferencing the pointer. Since the serializer has a 2-byte copy group, a runtime pointer value equal to `FFFF1648` or `FFFF29C4` could cause the corresponding UWORD bytes to be copied into the `FFFF810A` message buffer.

**Qualification:** this establishes a generic conditional indirect-read mechanism, not proof that either target was actually requested in a runtime session. The exact external command format, producer/fill path for the receive buffer, accepted pointer values, and serial transmission of the resulting message were not established here. This is an interface/message-serialization path, not an established engine-control consumer.

### Copy-helper census

The inspected named copy helpers do not provide a separate static copy alias to either target:

- `memory_copy_bytes` (`0x53C–0x552`) has three callsites: `0x4170`, `0x42EA`, and `0x433E`. The observed calls copy 8-byte CAN-mailbox/stack data; their argument setup does not use either target structure.
- `copy_longwords_by_size` (`0x21F3C`) is called at `0x20EF0`: source `FFFF8534`, destination `FFFF84D4`, length `0x60`. This is a distinct snapshot copy and does not overlap either target.
- `sub_21FFC` is the variable-length longword-copy dispatcher. Its four callsites are `0x20AAA` (source `FFFF2CEC`, destination `FFFF2D0C`, length `0x20`), `0x20B98` (source `FFFF180C`, destination `FFFF181C`, length `0x10`), `0x20F08` (source `FFFF85C4`, destination `FFFF1000`, length `0x28`), and `0x20F70` (source `FFFFA34C`, destination `FFFFA324`, length `0x28`). None includes `FFFF1054` or `FFFF2150` as a source/destination base.
- The `message_buffer_copy` path above is the only identified copy path in this bounded pass that accepts a runtime-supplied source pointer.
