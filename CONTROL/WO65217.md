## CF48D sub_315D4 Structure (lines 104179–104447)

```
mov.l   off_318B0, r0   ; r0 = 0xB624
ldc     r0, gbr         ; GBR reloaded to 0xB624 (self-relocating)
add     #-0x3C, r15     ; stack frame
mov.l   off_318B4, r2   ; r2 = 0xFFFF23AE (selector word)
mov.l   off_318B8, r5   ; r5 = 0xFFFF23AC
mov.b   @r2, r0         ; r0 = byte [FFFF23AE]
mov.l   off_318BC, r14  ; r14 = 0x8FD1 (default map)
and     #1, r0          ; selector bit0
...
jsr     @r3             ; sub_701C(r4=map, r5=GBR+0x10, r6=GBR, r7=1st query)
...
```

Key: CF48D `sub_315D4` **reloads GBR internally** (`ldc r0, gbr` = 0xB624) — self-relocating. Map pointer in r14→r4. Queries: 1st in r7 (extu.w), 2nd on stack (extu.b). Axis bases passed to sub_701C as r5=GBR+0x10, r6=GBR. Helper chain: sub_7700 → sub_7680 → loc_7510.

Map selection: `FFFF23AE` bit0 → 0x8FD1 vs 0x8ED1; further runtime branches select 0x8ED1 vs 0x8DD1.

## EL19A sub_22CB8 Structure (listing lines 26165–26192)

## Findings

1. **ABI-level correspondence: YES.** CF48D `sub_315D4`→`sub_701C` and EL19A `sub_22CB8` share the same calling convention: map in r4, 1st axis base in r5 (GBR+0x10), 2nd axis base in r6 (GBR), 1st query in r7 (extu.w), 2nd query on stack (extu.b), row stride mask 0xF. Both are 16×16 UBYTE two-axis readers delegating interpolation to a tail routine.

2. **Instruction-level alignment: NO.** Helper bodies differ (sub_7700/sub_7680/loc_7510 vs sub_2344C/sub_233CC/loc_23254), register save/restore patterns differ, and CF48D uses absolute map addresses loaded into r14 then r4 while EL19A uses off_XXXX loaded directly into r4.

3. **Relocation model: fundamentally different.** CF48D `sub_315D4` is self-relocating — it reloads GBR to 0xB624 internally via `ldc r0, gbr`, making all GBR-relative accesses valid regardless of caller GBR. EL19A `sub_22CB8` is **not** self-relocating — it never touches GBR and requires the caller to pass GBR-relative axis bases. A CF48D reader plugged into EL19A would read from the wrong GBR base unless the caller explicitly sets up GBR=0xB624-equivalent before the call.

4. **No literal-pool match.** CF48D literal pool references 0xB624 (GBR base), 0xFFFF23AE/0xFFFF23AC (selector), 0xFFFF84A0/0xFFFF846C (axis tables), 0xFFFF85DC (query word), 0x701C (helper). EL19A references 0xFFFF8498/0xFFFF859C (query words), 0xFFFF1054/0xFFFF1000 (runtime tables), map addresses 0x9B2E/0x9C2E/0x9DAE. No shared literal values or address patterns exist between the two functions.

## Conclusion

**Relocation-aware function alignment: NEGATIVE at instruction level, POSITIVE at ABI/calling-convention level.**

CF48D `sub_315D4` and EL19A `sub_22CB8` are structurally analogous 16×16 UBYTE two-axis map readers with identical argument-passing conventions (map r4, axis bases r5/r6, query r7/stack, stride mask 0xF). However, they differ fundamentally in relocation model: CF48D self-relocates by reloading GBR internally; EL19A expects caller-supplied GBR-relative bases. Helper bodies and interpolation tails are unrelated. No literal-pool or table-pointer correspondence exists between the two.

The three required positive-control helper pairs (`sub_2344C`≡`sub_7700`, `sub_233CC`≡`sub_7680`, `sub_22C38`≡`sub_6F78`) are all VERIFIED per WO65179, confirming the Nissan SH705x lookup library is shared at the helper level even though the reader wrappers do not align.

This confirms WO65204's negative instruction-level alignment finding and extends it: even the "relocation-aware" variant (CF48D sub_315D4, which manages its own GBR) does not align with EL19A sub_22CB8 at any level below the ABI calling convention. WO65206 remains BLOCKED (requires positive alignment).
