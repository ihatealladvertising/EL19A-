## Objective

Resolve the consumer/traversal of ROM pointer 0x13B28 → 0x16CD0, decode the relevant entry around 0x16DA4, and identify whether the four-word patterns beginning 0x13B50 are consumed as ADC/peripheral descriptors feeding FFFF84B4 / FFFF84BA.

## Findings

### 1. 0x13B28 → 0x16CD0 is a bulk-copy source, not an ADC descriptor table

- ROM pointer block at 0x13B20–0x13B40 contains 0x13B28 = 0x00016CD0; surrounding entries include FFFFB61C at 0x13B20 and FFFFBA64 at 0x13B24.
- Consumer: sub_24EA8, 0x24EA8–0x24F40. It sets GBR=0x13B00, loads the three RAM bounds/pointers from 0x13B20/24/28, then at 0x24F08–0x24F22 copies BE32 entries from source 0x16CD0 to destination FFFFB61C, advancing both pointers by 4 until destination reaches FFFFBA64.
- Copy span is 0x448 bytes = 274 longwords; source range 0x16CD0–0x17117, destination range FFFFB61C–FFFFBA63.
- The first 0x24 bytes at 0x16CD0 are zero-filled, but the full copied span is not; it includes the pointer block at 0x16D94 onward.
- The entry at ROM 0x16DA4 is at source offset +0xD4 (longword index 53). Its value FFFF84BB is therefore copied to RAM FFFFB61C+0xD4 = FFFFB6F0.
- sub_24EA8 is called from 0x24D86, 0x24E58 and 0x25066. Its immediate follow-on calls include sub_238DA, sub_241D2 and sub_241EE. These calls do not, in the inspected bounded spans, establish a consumer of the copied FFFFB6F0 entry.

### 2. FFFFB61C runtime use does not yet identify the +0xD4 entry

- A separate routine beginning 0x20422 loads FFFFB61C into R11 and updates UWORD fields at offsets +0x0E and +0x10 (0x20444–0x20456). This confirms runtime use of the RAM object, but does not access offset +0xD4 or establish what FFFFB6F0 points to.
- A targeted LST search for literal FFFFB6F0 found only its RAM declaration; no direct code consumer was identified in this bounded pass.

### 3. The ADC-looking records at 0x13B50 are real register-address patterns, but their consumer is unproven

- The records begin at 0x13B50 inside the object labelled dword_13B44. Repeating values include FFFFF819, FFFFF818, channel-like words 07000000/08000000/0A000000/0B000000, and result-register addresses FFFFF80E/F80E/F810/F814/F816.
- LST register definitions identify FFFFF819 as ADCR0_B, FFFFF818 as ADCSR0_B, FFFFF80E as ADDR7H_B, and FFFFF810 as ADDR8H_B; FFFFF814/F816 are ADDR10H_B/ADDR11H_B. This makes an ADC/peripheral descriptor interpretation plausible, but record layout, channel-field encoding, and use remain unconfirmed.
- Direct references to dword_13B44 resolve to code that reads only its prefix fields: +0 (0x8204), +4 (0x000FFFFF), and +8 (0x00020004). The reviewed consumers are 0x21374, 0x21406, 0x21542 and the VBR comparison at 0xABA04–0xABA0C. None of these reviewed accesses reads the descriptor-like records beginning at +0x0C / 0x13B50.
- No direct LST code reference to 0x13B50 was found. This is a bounded negative, not proof that calculated or external indirect access is impossible.

### 4. Link to FFFF84BA

- FFFF84BB is confirmed as a copied pointer value in the runtime RAM block at FFFFB6F0.
- No evidence in this segment connects FFFFB6F0 or the 0x13B50 ADC-looking records to FFFF84B4 or FFFF84BA.
- No sensor identity, ADC channel assignment, conversion, or producer for FFFF84BA is established.

## Conclusion / confidence

- **High confidence:** sub_24EA8 bulk-copies the 0x16CD0 ROM block into FFFFB61C; ROM 0x16DA4 value FFFF84BB lands at FFFFB6F0.
- **High confidence:** 0x13B50 contains repeated ADC-register-address patterns, based on the target LST's register labels.
- **Unresolved:** the consumer and semantics of the +0xD4 runtime pointer; the consumer/layout of the 0x13B50 records; any path from either to FFFF84BA.
- **Do not promote:** coolant identity, ADC channel identity, or an assertion that 0x13B50 feeds the FFFF84B4 structure.
