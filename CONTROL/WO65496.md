## 1. The read is genuine — base load verified

WO65484 §1 attributed the Y query to `FFFF84FE` through the `WO65118` `address` column, which WO65493 proved unreliable for `base_disp` rows. Re-decoded from the listing, the read is real:

| PC | Encoding | Instruction | Note |
|---|---|---|---|
| `0x66E0E` | `9A 41` | `mov.w word_66E94, r10 ; h'FFFF84D4` | PC-relative word load; `mov.w` **sign-extends** 0x84D4 → `FFFF84D4` |
| `0x66E10` | `E0 2A` | `mov #h'2A, r0` | byte displacement 0x2A |
| `0x66E14` | `00 AD` | `mov.w @(r0,r10), r0` | word read of `FFFF84D4+0x2A` = **`FFFF84FE`** |
| `0x66E24` | `81 F1` | `mov.w r0, @(2,r15)` | Y query passed on the stack |
| `0x67DAE` | `99 99` | `mov.w word_67EE4, r9 ; h'FFFF84D4` | twin `sub_67D0C` |
| `0x67DB0` | `E0 2A` | `mov #h'2A, r0` | |
| `0x67DB4` | `00 9D` | `mov.w @(r0,r9), r0` | same cell |

The block base is reached by **sign-extending a 16-bit literal pool word**, not by a full 32-bit literal load. This explains the WO65118 gap: the index records resolved addresses, and a sign-extended literal registers as a `mov.w` load, not as an access to `FFFF84FE`. **WO65484 §3's stop boundary is confirmed, not corrected.**

**Reusable convention note:** this listing prints **byte** displacements for `mov.w @(disp,Rn)`/`@(disp,GBR)`. `C1 15` (disp field 0x15) is displayed as `mov.w r0, @(h'2A,gbr)`. Offsets in this report are therefore byte offsets and are directly comparable with the `.res.b` address map.

## 2. The cell has no symbol and no field-level writer

- `FFFF84FE` appears in the listing **only** as an address-map row: `FFFF84FE  FF  UNDEFINED .res.b 1`. There is no `word_FFFF84FE`, `byte_FFFF84FE` or `dword_FFFF84FE`. The whole region `FFFF84D4`–`FFFF8533` is unlabeled `.res.b`.
- **Whole-ROM store scan (any width, any base):** exactly **28** stores carry displacement `0x2A` or `0x2B`, and **all 28 are `@(h'2A,gbr)` / `@(h'2B,gbr)`** — GBR-relative, never register-base-relative. There is therefore **no `mov.w`/`mov.b` store instruction in the ROM that addresses block offset 0x2A or 0x2B through a general register.**
- **GBR provenance:** 2430 `ldc rN, gbr` sites were traced with register provenance; **none** loads `FFFF84D4` (or `FFFF84C8`). So no `@(h'2A,gbr)` store can land on `FFFF84FE`.
- **Long-store overlap:** a `mov.l` at displacement `0x28` would cover `FFFF84FC–FFFF84FF` including `FFFF84FE`. In all 429 routines that reference the block base, the only `@(h'28,·)` stores are `@(h'28,r15)` (stack) and `@(h'28,gbr)` — neither reaches the block.
- **No pre-offset base:** the distinct block-base annotations in the `84C0`–`8540` window are only `FFFF84C8`, `FFFF84C9`, `FFFF84CB`, `FFFF84CD`, `FFFF84CF`, `FFFF84D4`, `FFFF8500`, `FFFF8534`. No `FFFF84D0`/`FFFF84D8`/`FFFF8530` style shifted base exists, so no displacement is silently rebased onto `FFFF84FE`.
- **No literal address:** no instruction anywhere loads the 32-bit constant `FFFF84FE`.

**Writer count: 0 field-level writers.** (Bounded negative: whole instruction set, not a sampled set.)

## 3. The only population path is a 96-byte block copy

`copy_longwords_by_size` is referenced once and **called exactly once in the ROM**:

| PC | Instruction | Value |
|---|---|---|
| `0x20EEA` | `mov.w word_21024, r2 ; h'FFFF8534` | source |
| `0x20EEC` | `mov.w word_21026, r1 ; h'FFFF84D4` | destination |
| `0x20EF0` | `jsr @r9 ; copy_longwords_by_size` | call |
| `0x20EF2` | `mov #h'60, r0` | **delay slot** → length argument = 0x60 |

Routine semantics, decoded at `0x21F3C`:

- `0x21F3E–0x21F48`: `mov #h'40,r3; cmp/hs r0,r3; bf loc_21FDC` — sizes **≤ 0x40** dispatch through the unrolled jump table `glb_21F98` (e.g. `0x21F52 mov.l @(h'3C,r2),r0` / `0x21F54 mov.l r0,@(h'3C,r1)`), which uses **byte** displacements and leaves `r1` fixed.
- `loc_21FDC` (`0x21FDC–0x21FEC`): `mov r2,r3; add r0,r3` then the loop `loc_21FE2: mov.l @r2+,r0; cmp/hs r2,r3; bf loc_21FF6; mov.l r0,@r1` — a forward 4-byte copy with `r1` = destination base, `r2` = source, `r3` = source + **byte** length.

Because `r0 = 0x60 > 0x40`, the call at `0x20EF0` takes `loc_21FDC`. The transfer is therefore:

```
FFFF84D4 .. FFFF8533  <-  FFFF8534 .. FFFF8593      (96 bytes, non-overlapping, shift-down by 0x60)
```

Consequences:

- The block is exactly **96 bytes** (`FFFF84D4`–`FFFF8533`); `FFFF84FE` is offset `0x2A` in it and is refreshed by the copy from **`FFFF855E`**, at the same offset.
- The routine name is misleading: the length is a **byte** count added to a byte pointer, not a longword count.
- Neither side of the copy has a field writer at 0x2A, so the chain terminates in bulk-copied, unlabeled RAM on both ends.

## 4. Residual (explicitly unbounded) class

Data-dependent stores `mov.b rX, @(r0,rN)` exist into this block in a few routines (`0x41594`, `0x60E02`, `0x7DF34`, `0x818FA`, `0x89FDE`, `0x9528C`, `0xA1E8E`), where `r0` comes from `extu.b` or a stack slot. A runtime value of `0x2A`/`0x2B` cannot be excluded statically. However:

- none of these carries a **constant** index 0x2A;
- every resolvable constant index used against the block is **≥ 0x137** (observed pool values 0x137, 0x15D, 0x2A6, 0x2A8, 0x324, 0x32E, 0x330, 0x332, 0x336, 0x3B3, 0x3EE, 0x78C, 0x7F2, 0x8AC, 0x92E, 0x980, 0x9B6, 0xA10, 0xAAE, 0xF3C), all far above 0x2A;
- a byte store would only partially overwrite the word the reader consumes.

All these are `mov.b` stores; none is a word store that could produce the full 16-bit query value.
