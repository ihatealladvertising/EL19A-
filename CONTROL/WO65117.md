## Decision question

Once a GBR or base register is resolved, can the listing's `@(disp,GBR)`, `@(r0,GBR)`, `@(disp,Rn)` and `@(r0,Rn)` operands be converted arithmetically into effective addresses and grouped into a shared by-base dictionary — so future traces stop re-deriving "which fields of this base are touched, where" and stop repeating the `0x55xxx` GBR over-reach error?

## Why this is high-payoff and disjoint

- The playbook's recorded failure is a GBR value that is a ROM address (`sub_46E3E` using `0x821E`) being treated as if it were `FFFF8xxx`. WO65116 established GBR values but did not enumerate what they address.
- The supporting index ranks the base-register dictionary (`FFFF1054`, `FFFF2150`, `FFFF1990`, `FFFF1CA8`, `FFFF85C4`, `FFFF3628`, with observed offsets) as a high-value reusable artifact.
- **Not WO65115:** this WO has no target list, answers no "who reads/writes address X" question, emits no per-target reader/writer claim, does not classify constant-vs-dereference, and creates no `tools/` entry. It is an aggregate structural index keyed by base value.
- **Not WO65116:** this WO consumes GBR/base provenance as an input method; it does not republish the function/GBR map.

## Deliverables

1. `EVIDENCE/WO65117_effective_address_dictionary.tsv` — one row per fully resolved memory operand.
   Columns: `base_value | offset | effective_address | width | access | form | pc | function | instruction | note`
   - `form` ∈ `gbr_disp`, `gbr_r0`, `base_disp`, `base_r0`.
   - `effective_address` is 8 hex digits, computed as `base + disp × width-scale` for displaced forms and `base + r0` for index forms.
   - `access` ∈ `read`, `write`, `rmw`, derived from operand position/mnemonic only; no semantic naming.
2. `EVIDENCE/WO65117_effective_address_dictionary_unresolved.tsv` — mandatory second file.
   Columns: `base_value | pc | reason | instruction | note`. Reasons include `gbr_not_provable`, `base_not_provable`, `index_not_provable`, `displacement_not_provable`, `pc_concordance_mismatch`, `gbr_inherited`.
3. `EVIDENCE/WO65117_effective_address_dictionary_generator.py` — stdlib-only generator in `EVIDENCE/`, not `tools/`.
4. This record rewritten to closed form.

Both TSVs carry a header block with ROM MD5/SHA-256, listing member/SHA-256/size, generator version, run date, PC concordance `rows_checked / rows_matched`, target file hash `N/A`, and the explicit limits: "computed pointers, pointer tables, block-copy and `movca.l` transport are not modelled; inherited GBR and unprovable bases are reported as unresolved, never as address zero or as absence."

## Method (bounded)

1. Parse concordant listing CODE lines (address, raw bytes, mnemonic, operands) exactly as in WO65116; drop and report any byte mismatch.
2. Recompute function extents and per-function GBR values internally using WO65116 rules (local `ldc` only, short pool annotations resolved from ROM bytes, branch/label invalidation). No dependency on the WO65116 branch.
3. For every `@(disp,GBR)`, `@(r0,GBR)`, `@(disp,Rn)` and `@(r0,Rn)` operand, resolve the base, parse the displacement (decimal, `h'…`, `0x…`, or `label ± h'…` expressions using listing label addresses), apply SH-2 width scaling (b=1, w=2, l=4), and record the arithmetic result.
4. Track `r0` only from an immediately preceding provable `mov #imm,r0` / pool load in the same straight-line region; invalidate on any other write or control-flow boundary. An unprovable `r0` is an unresolved index, not a zero.
5. Deduplicate identical rows; sort by `base_value`, then `effective_address`, then `pc`. Every unresolved operand gets a row with a reason.
6. Verify the three WO65116 GBR anchors and the `0x46E3E` complex displacement expressions as spot checks. Confirm no `FFFF8xxx` attribution when the resolved base is `0000821E`.
