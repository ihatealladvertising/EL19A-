## Question

`FFFF34E7` is read at `0x0A19B8` (`tst #1`) and cleared inside `sub_A14F0`, and appears symbolically at `0x095094` under GBR = `FFFF34C1` (`@(h'26,gbr)`). Is it one byte seen through two bases, and does bit0 reach a named output or only gate the reset path?

## Answer 1 — it is one cell, not two

`FFFF34C1 + 0x26` = `FFFF34B3 + 0x34` = **`FFFF34E7`**. The two bases differ by `0x0E` and the displacements differ by exactly `0x0E`, so both notations name the same RAM byte. There is no second cell.

This matters because `FFFF34C1` is the base of the `0x08AD90` routine family and `FFFF34B3` is the base of `sub_A14F0` (`0x0A14F0`), so the same flag is shared across two unrelated subsystems through different GBR bases — a reader of either routine alone sees a private-looking offset.

## bit0 — a producer/consumer handshake, not a named output

```
producer side (sets bit0 after publishing to the FFFF2150 output band)
0x0A0888  mov #0x3C,r0 / or.b #h'40,@(r0,gbr)   -> FFFF2150+0x3C
0x0A088E  or.b #1,@(r0,gbr) with r0=0x26        -> bit0 SET
0x0A5402  after storing to FFFF2150+0x115/0x3DA/0x328/0x2A4/0x33A/0x33C
0x0A1A28  on the early-exit path loc_A1A26      -> bit0 SET

consumer side (sub_A14F0, 0x0A14F0)
0x0A19B8  mov.b @(h'34,gbr),r0 / tst #1 / bt loc_A19EC
0x0A19C4..0x0A19DA  U16[FFFF2150+0x16C] vs U16[FFFF84D4+0x20] -> sub_9D26C
0x0A19E6  store result to U16[FFFF2150+0x328]
0x0A19EA  and.b #h'FE -> bit0 CLEAR (consumed)
```

So bit0 is a "new result published" latch: set by whichever producer last wrote the `FFFF2150` output band, tested and cleared by the single consumer `sub_A14F0` after it folds the result into `FFFF2150+0x328`. It is an internal handshake between two firmware stages; it reaches no MMIO register, no command message and no dashpot/actuator store. The clear at `0x0A19EA` is a **dynamic-index** write (`r0 = 0x34`, then `and.b #h'FE,@(r0,gbr)`), which is why it does not appear in a fixed-displacement scan — the same blind spot recorded in WO65733/`FND-000010`.

## bits 5 and 6 — mirrors of two entry bytes in the `FFFF A074` table

`sub_804DA` (`0x0804DA`) derives both bits from the helper `sub_228F0`, which indexes the 3-byte-entry table at `FFFF A074` (the same 198-entry table WO65877 tested for bit3):

```
sub_228F0:  r0 = UBYTE[FFFFA074 + 3*index + 1]
            tst #h'80,r0 / movt r0 / xor #1   -> returns 1 when bit7 of that byte is SET
```

- `0x08053C..0x08054A`  `sub_228F0(0xAD)`: non-zero → bit6 set at `0x08054E`; zero → bit6 clear at `0x08054A`.
- `0x080550..0x080568`  `sub_228F0(0xAE)`: non-zero → bit5 set at `0x08056C`; if zero, `sub_228F0(0xAF)` is tried at `0x08055C` (its `mov #0xAF,r3` is the `bf` delay slot at `0x08055A`); only when both are zero is bit5 cleared at `0x080568`.

So **bit6 = entry 0xAD byte1 bit7, and bit5 = entry 0xAE byte1 bit7 OR entry 0xAF byte1 bit7.** These are read-only mirrors of configuration-table bytes recomputed by `sub_804DA`; nothing else writes them.

## bit4 — the condition bit two separate routines arm on

Set at `0x08B080` when `U16[FFFF2150+0x8AE] >= 0x258` (600), cleared at `0x08ADAE` on the reset path of `sub_8AD7C` gated by `UBYTE[FFFF3628+5].bit1` and `UBYTE[0x8C8E].bit0` — exactly the clear condition WO65877 recorded for `FFFF34F5.bit5`. Read as an arm guard at `0x08B38E` (immediately before the `FFFF860B.bit5` / `FFFF99F0.bit6` gates of WO65877's setter) and again at `0x095094` (followed by the chain `FFFF34F9.bit7`, `FFFF3530.bit1`, `FFFF3548.bit7`, `FFFF354D.bit5`).

## bit3 — a paired edge latch inside one routine

`0x077BD6` tests bit3 and `0x077BE4` sets it; `0x077C10` tests it and `0x077C1E` clears it, both around a comparison of `UBYTE[0x9860+0x1B]` against `UBYTE[0x8583]`. Set-on-entry / clear-on-exit within the same routine: an edge memo, not shared state.

## Verdict

`FFFF34E7` is a single **multi-bit diagnostic/status byte** shared between the `FFFF34C1` and `FFFF34B3` routine families. Bits 0, 3, 4, 5, 6 are used; bit1, bit2 and bit7 have no access site. Every use is a private branch gate, a mirror of a configuration-table bit, or a producer/consumer handshake. No named output is reached.

**Classification: INTERNAL STATE FLAG** (multi-bit status byte; no named output).

## Reconciliation (additive — WO65886 unedited)

- **WO65886 said:** `FFFF34E7` is read at `0x0A19B8` (`tst #1`) and cleared at `0x0A19E8`-`0x0A19EA`.
- **Upheld and refined:** the clear is at `0x0A19EA` and is a dynamic-index `and.b #h'FE,@(r0,gbr)` with `r0 = 0x34` from `0x0A19E8`; `0x0A19E8` itself is the `mov`, not a store. The byte is additionally written by three other PCs (`0x0A088E`, `0x0A1A28`, `0x0A5402`) and by four `FFFF34C1`-based sites, none of which WO65886 claimed as absent.
- **One cell, two bases:** `FFFF34C1+0x26` and `FFFF34B3+0x34` are the same byte; WO65892's premise that they might be unrelated cells is rejected.
- **Confidence:** high for the fixed/symbolic sites and for all ten dynamic sites (each had a provable constant index); medium for the claim that no *further* dynamic site targets the byte, because 695 dynamic sites and 13 bases could not be resolved.
