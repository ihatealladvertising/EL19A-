## Answer in one paragraph

The 4×4 premise is void: `0xEDA0` is a **16×1 UBYTE curve** read by exactly one instruction pair in `sub_488BA` (`mov.l off_48B6C,r4` at `0x048942`, `jsr @r14` at `0x048948`), and it is queried with **the same single index** as the immediately preceding `0xED64` lookup — `U8[FFFF84B4+0x04]` = `FFFF84B8`, the **rescaled AN27 NTC coolant-temperature image**. There is no second axis and no RPM input anywhere on the path. Both curve outputs are offset (`+0x18`), floor-clamped, and then used **only as single-sided thresholds** compared against one RAM byte (`FFFF85A9`); the results are never published as values. The routine's entire outward product is `UBYTE[FFFF34D2].bit6` plus a 0/1 return, and that return is consumed by the `0x0218F8`-dispatched routine at `0x047B54` as an input to the `FFFF11F3` 0–4 state machine (`sub_491BC` at `0x047C2C`) and as the gate for a `sub_48C1E` 16-bit publication into `UWORD[FFFFB644]` / `U16[FFFF11F0]`. No idle-speed, dashpot, throttle or actuator sink is reached.

**Warm-up hypothesis verdict: WEAKENED.** Input identity (coolant temperature) is *supported*; function and output identity are *not* — the tables feed a temperature-keyed plausibility/limit verdict, not an idle-control calculation.

## 1. ROM references and the actual call context

| Item | Anchor |
|---|---|
| Sole pointer pool entry | `off_48B6C` at `0x048B6C` = `00 00 ED A0` (symbol form `aJXxxxxpxtplh88+3`) |
| Pointer load PC | `0x048942` `mov.l off_48B6C,r4` → `r4 = 0xEDA0` |
| Helper call PC | `0x048948` `jsr @r14` (`r14 = sub_22E10`, loaded at `0x048936` from `off_48B64`) |
| Result staging | `0x04894A` `extu.b r0,r5` is the **delay slot** (runs before the call, on the query); `0x04894C` `extu.b r0,r6` after return; `0x048958` `mov.l r6,@(h'30+var_28,r15)` → stack local `var_28` |

Coverage: `0xEDA0` has **one** ROM reference in the entire listing — the pool word above. There is no `FF FF ED A0` absolute literal (the address is ROM, below `0x10000`, so only a `00 00 ED A0` pool word could reach it, and the only such word is `off_48B6C`). The two `; 0xEDA0` hits at listing lines 116 and 124258 are the generator's own annotation comments, not code.

`sub_488BA` (`0x0488BA`–`0x048C1C`) installs **its own** GBR = `0xFFFF859C` (`word_488EE` → `ldc r0,gbr` at `0x0488CE`, restored at `0x048C0A`). It loads `r8 = 0xFFFF34C1` (`off_48B68` at `0x048938`) for one register-relative access only. Every `@(h'NN,gbr)` in this routine therefore means `FFFF859C+NN`, not `FFFF34C1+NN`.

## 2. `sub_22E10` argument contract (reused, not re-audited)

Established from the helper body and confirmed against the WO65038/WO65291 contract:

- **`r4`** = table base pointer. **`r5`** = query byte, `extu.b` (0–255). Return value in **`r0`**.
- `0x022E10`–`0x022E16`: `r0 = word_22E22 = 0x00F0`; `extu.b r5,r5`; `cmp/hs r0,r5` — if `r5 >= 0xF0`, branch to `locret_22E1E` and `rts` with delay slot `mov.b @(h'F,r4),r0` → returns **`table[15]`**.
- Otherwise `jmp @r6` → `loc_2350C` with delay slot `r3 = IVECT1 = 0`. `loc_2350C`–`0x02351C` performs four `shlr r5 / rotcr r3` pairs → `idx = r5 >> 4` and the low nibble `frac` rotated into `r3`; `swap.w r3,r3` places `frac << 12`. `shlr8 r0` zeroes the limit's high byte and `tst r0,r0` selects the **byte** path at `loc_23532`: `r4 += idx`, `r1 = table[idx]`, `r0 = table[idx+1]`, `r2 = extu.b(hi)`, `r0 = extu.b(lo)`, then `jmp sub_231C8`.
- `sub_231C8` computes `lo + frac*(hi-lo)/16` via `mul.l` high-word, with a separate branch when `hi < lo` that restores `lo` and subtracts (`0x0231CC`–`0x0231E2`). **Verified formula: `value = table[idx] + (table[idx+1] - table[idx]) * (q & 15) / 16`.**

Effective grid: `q` 0–239 interpolates the 15 segments `0,16,32,…,224`; `q >= 240` returns `table[15]`. Entry 15 is therefore both the last interpolation endpoint (`q` 224–239) and the ≥240 clamp. This refines `FND-000017`'s "`0,16,…,240`" wording; it does not contradict it.

## 4. Both query operands are the *same* operand

- `0x04892C` `mov.w word_48A6E,r7` → `r7 = 0xFFFF84B4` (sign-extended, `FND-000012` discipline).
- **`0x048934`** `mov.b @(4,r7),r0` → `r0 = UBYTE[0xFFFF84B8]`; the delay slot **`0x04893C` `extu.b r0,r5`** passes it as the `0xED64` query.
- **`0x048946`** `mov.b @(4,r7),r0` — *the same load, again*; delay slot **`0x04894A` `extu.b r0,r5`** passes it as the `0xEDA0` query.

There is no transform between load and helper: no `add`, `shll`, `extu.w`, or intermediate RAM cell. `r6`/`r9` hold a *different*, ROM-sourced byte (`UBYTE[0x86AF]` = `UBYTE[0x86B0]` = `0x04`) used only as a later comparison floor; it is not a lookup query.

**Query identity (input layer, ADVANCED).** `0xFFFF84B8` = `U8[FFFF84B4+0x04]` is already established in the knowledge layer as the **rescaled AN27 NTC coolant-temperature image**: `CALIBRATIONS/discovered_tables_catalog.csv` rows `0x0F406` ("Linearized NTC temperature vector consumed across coolant/air temp scalers (`sub_35570` → `FFFF84B8/FFFF84BF`)"), `0x0DE5E` and `0x10FEA` (both "`r5=U8[FFFF84B4+0x04]` (`FFFF84B8`, rescaled AN27 NTC temp)"), and WO65739 §"The `+0x04` field is already established as the rescaled AN27 ECT image (WO65239)". Recorded by the linearising writer `sub_2245C` (`U8[FFFF84BB..84C1] → sub_2245C → U8[FFFF84B4..84BA]`, catalogue row `0x0F406`).

So the axis of both curves is **coolant temperature, referenced through the raw 0–255 rescaled-NTC image with the implicit `sub_22E10` grid**. It is not RPM and not a co-located ROM axis.

**Correction to WO65291 §C.** That report's "ED64/EDA0: 4×4 maps — require two axes. No co-located axis pointers found in `sub_488BA` loads" is wrong on both counts: geometry is 16×1 (one entry per point, one `sizey`), and the single query is shared, so no second axis exists to be missing. (The Release 1 scope matrix already carries the corrected 1×16 geometry; WO65291 was not edited.)

## 5. Selection and gating conditions

The two lookups themselves are **unconditional** once `sub_488BA` is entered. The only entry-level gate is cosmetic: `UBYTE[0x8CD3].bit7` set, or clear with `UBYTE[FFFF860B].bit7` clear, selects `UBYTE[0x86B0]` (`0x0488EA`); otherwise `UBYTE[0x86AF]` (`0x04892A`). Both ROM bytes are `0x04`, so the gate has no data effect.

Post-lookup pipeline (common to both results):

| Stage | PCs | Condition | Effect |
|---|---|---|---|
| Alarm offset | `0x048960`–`0x04899C` | `UBYTE[FFFF362E]` (`FFFF3628+6`) bit2 **set** | `r14 = UBYTE[0x8565] = 0x18`; `A ← min(0xFF, A+0x18)`, `B ← min(0xFF, B+0x18)` with `cmp/gt 0xFF` saturation |
| Floor | `0x04899E`–`0x0489BE` | `UBYTE[FFFF361D]` (`FFFF3616+7`) bit0 **clear** | `A, B ← max(·, UBYTE[0x86A7])`; that ROM byte is `0x00`, so the floor is degenerate (no-op) |
| Tree select | `0x0489C0`–`0x0489C4` | `UBYTE[0x8CD3]` bit7 | set → tree A (`0x0489C8`); clear → tree B (`loc_48A72`, selects on `UBYTE[0x87C8]` bit7) |
| Inner select | `0x0489C8` / `0x048A72` / `0x048AC4` / `0x048ADC` | `UBYTE[FFFF8600].bit1`, `UBYTE[0x87C8].bit7`, `UBYTE[FFFF84CA]==2`, `UBYTE[FFFF1D7C].bit6` | chooses which threshold and which arming path applies |
| Arming | every tree | `r13 = UBYTE[FFFF860B] & 0x08` | `r13 == 0` → unconditional exit with return 0; `r13 != 0` is required for any verdict |
| Inhibit | every tree | `UBYTE[FFFF860F]` (`FFFF859C+0x73`) bit3 | arms one alternative branch of each tree |
| Count floor | `0x048A94`, `0x048BDA` | `UBYTE[FFFF8531]` (`FFFF84D4+0x5D`) vs `r9 = 4` | `< 4` → exit with return 0 |

**Threshold comparisons.** The only comparison operand is `UBYTE[FFFF85A9]` (`@(h'D,gbr)` = `FFFF859C+0xD`, the cell WO65736 recorded as a 16-point 4.4 query with no established static writer). Every site tests `UBYTE[FFFF85A9] > threshold` with `cmp/gt`:

- **`0xED64` (A, in `r12`)** at `0x0489E4`, `0x048A3E`, `0x048AB8`, `0x048ACE`, `0x048B2E`, `0x048B44`, `0x048BCE` → **verdict V1** (`loc_48BD2`).
- **`0xEDA0` (B, stack `var_28`)** at `0x048A1C`–`0x048A22`, `0x048A5E`–`0x048A62`, `0x048A9E`–`0x048AA2`, `0x048BB6`–`0x048BC2`, `0x048BE8`–`0x048BEC` → **verdict V2** (`loc_48BF0`).
- `0x048ADC`–`0x048B02` additionally floors A at `UBYTE[0x8911] = 0x58` (88) before the V1 test.

So `0xED64` is the strict threshold (V1) and `0xEDA0` the soft threshold (V2). They are **not** simultaneously applied as a bracket: different branches select one or the other.

## 6. Outputs and first meaningful consumer

Terminal block `0x048BF4`–`0x048C04`:

```
0x048BF4 mov.b @(h'30+var_2C,r15),r0   ; verdict flag (0 at 0x0488D8, 1 on V1)
0x048BF6 tst   r0,r0
0x048BF8 mov   r10,r0                  ; r10 = old UBYTE[FFFF34C1+0x11] (0x04895A)
0x048BFA bt/s  loc_48C00               ; flag == 0 → clear bit6
0x048BFC and   #h'BF,r0                ; delay slot
0x048BFE or    #h'40,r0                ; flag != 0 → set bit6
0x048C00 mov   r0,r10
0x048C04 mov.b r10,@(r0,r8)            ; UBYTE[FFFF34D2] := r10   (r8 = FFFF34C1, r0 = 0x11)
0x048C06 mov.l @r15,r0                 ; return value
```

- **V1** (`loc_48BD2`) returns 1 **and** sets `FFFF34D2` bit6.
- **V2** (`loc_48BF0`) returns 1 with bit6 **cleared**.
- Default returns 0 with bit6 cleared.

`FFFF34D2` (`byte_FFFF34D2`, `UNDEFINED .res.b 1`) has exactly three absolute readers — `0x0A151E`, `0x0A31EE` (`FFFF34B3+0x1F`) and `0x0A3BAE` (`FFFF34C1+0x11`) — one of which (`WO65913`'s `0x0A1510`-`0x0A1524` early-exit group) already uses it as a gate. Its bit6 consumers were not traced further; this WO stops at the boundary.

Caller: **`bsr sub_488BA` at `0x047BDA`**, inside the alternate entry `loc_47B54` of the `0x047B54` routine, which is pointer-table entry `0x0218F8` (the same dispatcher band as WO65880's `0x0218F4`). The routine installs GBR = `0xFFFF34B0` (`off_47CB0` at `0x047B5E`).

|---|---|
| `0x047BDE`–`0x047BE2` | `tst r0,r0`; `bt/s loc_47C0A` — return 0 takes the skip path; `r12 ← r0` in the delay slot |

**First meaningful consumer:** the enum state machine at `0x047C2C` (`sub_491BC` → `FFFF11F3`, 0–4) together with the gated 16-bit publication at `0x047BF4`–`0x047C08` (`UWORD[FFFFB644]` / `U16[FFFF11F0]`). Neither curve value itself ever leaves `sub_488BA`; only the boolean does.

## 7. Warm-up comparison and hypothesis verdict

- **Compatible signal: coolant temperature only.** The only physical input on the whole path is `FFFF84B8`. **No RPM value is read anywhere** in `sub_488BA`, and no RPM-bearing cell is loaded into `r12`, `var_28` or the threshold comparison. The falling shape of both curves is therefore a *temperature* dependence.
- Consequently the falling-ramp resemblance that produced the provisional XML names `Fuel Cut Bosch [S] (ED64)` / `Fuel Cut JECS [S] (EDA0)` with `Rpm_x25` is not merely unsupported (as the Release 1 scope matrix already records) — it is **contradicted** by a proven non-RPM query.
- The 2026-11-25 warm-up log (APP=0, ECT 32–57 °C, falling RPM) shares exactly one signal with this path. Over that window both curves lie on their falling portion, so a temperature-varying threshold is *compatible* with the log's temperature band, but the log's RPM trend cannot corroborate a table that never reads RPM. Curve resemblance alone is not evidence.
- **Verdict: WEAKENED.** *Input identity: supported* (coolant temperature). *Function identity: not supported* — the curves are single-sided thresholds feeding a pass/fail plausibility verdict, not a warm-up/idle-speed calculation. *Output identity: not supported* — the path terminates in a status bit and an enum state, reaching no idle, dashpot, throttle or actuator sink.
