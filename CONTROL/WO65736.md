## Objective (as assigned)

WO65502 proved `0x108B4` is a 16-point interpolated characteristic indexed by `U8[FFFF85A9]` in 4.4 fixed point, carrying one step at index byte `0x60`. Find that byte's producer and state its numeric domain and whether it is a state flag, a computed ratio or a temperature/voltage-like input.

## Result: the producer is not in the image

The byte `FFFF859C+0x0D` has **zero writers** in the pinned listing, in every addressing form the WO required. Counts are reported for all of them:

### What the reference-anchored census does show

301 non-comment CODE lines load the literal `FFFF859C` into a register. Thirty-six of them are followed, before the next `rts`, by a store through that same register. The resulting fixed-displacement stores into the struct are `+0x00` (the base pointer itself), `+0x08`, `+0x0A`, `+0x0E`, `+0x12` and `+0x16` — never `+0x0D` and never a width that spans it. Representative sites:

- `0x4A018  mov.w r0, @(h'16,r5)` with `r5 = word_44CA8-styled` load of `FFFF859C` — the `FFFF85B2` word WO65724 already identified as an RPM mirror.
- `0x442A2` — a byte store at `+0x0A`.
- `0x78A92` — a word store at `+0x0E`.

The struct's other accesses are reads: `mov.b @(8,r3)` at `0x42D7C`/`0x42E88`/`0x42EF4` (a counter compared against a ROM byte), `mov.b @(h'D,r5), r0` at `0x44C04`, and `mov.b @(h'D,r6), r0` at `0x5B5C0` (WO65502 §1). Both known byte-`0xD` reads are therefore reads of a field that no code in this image writes.

## Verdict

- **Producer: NOT ESTABLISHED (bounded negative).** No producer exists in `f501.bin` under any addressing form whose base is statically anchored on the literal `FFFF859C`.
- **Hypothesis (state/mode variant selector): NOT CONFIRMED and NOT REFUTED.** The discriminator the WO specified — "if the writers only ever assign a small constant set, list those constants and the branch conditions" — cannot run without a writer. No constant set and no arithmetic lineage can be reported.
- **Domain: UNDETERMINED.** The byte's 4.4 interpretation at the `0x108B4` reader is WO65502's, not new evidence here.
- The one-step payload observation is untouched: the table still carries a single step at index byte `0x60` (6400 below, 7750 at and above).

**RR consequence for `0x108B4`:** it must keep its current description as a 16-point characteristic indexed by an **unnamed** byte at `FFFF85A9`. Do **not** upgrade it to a two-entry table, do **not** assert a mode selector, and do **not** assert a physical input. A "written only outside the calibrated image / dead or externally seeded field" reading is plausible but **unproven** and must not be stated as fact.

## Residual hole (the exact unresolved boundary)

Three routes remain open and are the only ways the byte can be written without tripping this census:

1. a base register established by a **pointer loaded from RAM** (`mov.l @(disp,rX), rM`) rather than by the literal;
2. a base passed in **as an argument** to the writing routine;
3. a **block/longword copy** whose destination base is derived by arithmetic from another address (post-increment stores do not exist in this ROM — WO65733 §2 — so any copy must use `@rN` + `add`).

None of these was followed; doing so is a new, differently scoped investigation, not a repeat of this one.

## Method note carried forward

A naive **linear register-value tracker** across the whole listing produces confident false hits: the symbol-named pool loads (`; HCAN1_TXACK1_W`, `; ATUII_TCNT7A_W`) are invisible to a regex that keys on `; h'XXXXXXXX`, so a register's value survives from an unrelated earlier routine. Under that tracker `0xAFDD2` and `0xBE910` appeared to write `FFFF859C+0x0A`; both are in fact HCAN1/ATUII peripheral writes (`0xAFD9A  mov.w word_AFE1C, r1 ; HCAN1_TXACK1_W`, `0xBE90C  mov.w word_BEA0C, r2 ; ATUII_TCNT7A_W` with pool words `F580`/`109C`). Every count in the table above was therefore computed **routine-locally**, stopping at the next `rts`, and only from literal-anchored bases. Do not trust a cross-routine register tracker on this listing.
