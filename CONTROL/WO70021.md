## Overview

Defined a conceptual data model and versioned JSON interchange envelope for the SH7055/SH7058 Nissan/Hitachi lookup-helper and calibration-table tool suite. The model covers all nine required areas (ROM artifact, processor/profile, address space, symbols, calibration objects, axes/conversions, readers/lookups/consumers, evidence/provenance, analysis run/result) and includes two worked conceptual examples demonstrating separation of target proof and donor hypotheses. No Python implementation, JSON Schema, or database code was produced.

## Nine Model Areas — Specification Complete

All nine model areas are specified with field tables, identity rules, optionality, unresolved-state behavior, and relationship representation that survives address relocation and cross-ROM comparison.

### 1. ROM Artifact / Image

Full specification with `artifact_id`, `container`, `source_path`, `decoded_size_bytes`, `decoded_sha256`, `loader`, `loader_args`, `byte_order`, and `import_notes`. File offset is never silently treated as ROM EA or RAM EA.

### 2. Processor / Profile

Full specification with `processor_family`, `model`, `endianness`, `capabilities`, `profile`, and `address_domain`. ECU-specific data is kept outside generic processor behavior.

### 3. Address Space / Memory Region

Full disambiguation of `ea` (ROM effective address), `file_offset`, `ram_address`, and `address_domain`. Resolution status enum (`resolved`, `unresolved`, `unknown`, `conflicting`) ensures no silent conflation. At least one of `ea` or `file_offset` must be present.

### 4. Symbols

Full specification with `symbol_id`, `name`, `namespace`, `kind`, `address`, `address_ea`, `address_ram`, `declaring_artifact`, `source_line`, `aliases`, and `duplicate_at`. Duplicate declarations sharing an address are retained as separate records.

### 5. Calibration Objects

Full specification with `obj_id`, `artifact_id`, `table_address`, `ea`, `file_offset`, `storage_type`, `element_type`, `dim1`, `dim2`, `axis1_type`, `axis2_type`, `byte_extent`, `payload_sha256`, `distinct_byte_values`, `axis1_values`, `axis2_values`, `axis1_count`, `axis2_count`, `conversion_provenance`, `reader_backed`, and `prior_report`. `byte_extent` = `dim1 * dim2 * element_width_bytes(element_type)` is explicitly defined.

### 6. Axes and Conversions

Full specification with `conv_id`, `obj_id`, `axis`, `convert_to`, `convert_from`, `formula_text`, `formula_direction`, `query_domain`, `axis_points`, `interp_method`, and `conversion_notes`. `formula_text` is preserved as-is; no evaluation is required.

### 7. Readers / Lookups / Consumers

Full specification with `call_id`, `call_pc`, `call_form`, `helper`, `arguments`, `lookup_behavior`, `consumer`, and `consumer_role`. At least `r4` must be present in `arguments`.

### 8. Evidence / Provenance

Full specification with `ev_id`, `source_path`, `source_hash`, `evidence_class`, `extraction_method`, `observation`, `confidence`, `status`, `links`, and `acquired`. Every evidence record has an immutable `source_hash`. `evidence_class` distinguishes `target` from `donor`.

### 9. Analysis Run / Result

Full specification with `run_id`, `tool_name`, `tool_version`, `timestamp`, `input_artifacts`, `output_schema_version`, `deterministic_id`, `arguments`, and `output_path`. `deterministic_id` = `sha256(run_id + json_dump(output, sort_keys=True))` ensures reproducible equality-checking.

## Versioning and Compatibility

- Minor version bumps may add optional fields; unknown fields are silently ignored.
- Major version bumps may rename or redefine fields; consumers must check `output_schema_version`.
- The `output_schema_version` field is mandatory in every envelope.
- TSV/CSV exports must include a header row indicating `spec:sh705x-datamodel-v1.0.0`.

## Worked Conceptual Examples

### Example A — Reader-Backed EL19A Calibration with Target Evidence

A complete JSON envelope demonstrates target-side calibration object, axis conversion, reader lookup, target evidence, and analysis run, all using the SH7058 / MR18DE_CVT profile.

### Example B — Donor A2L Characteristic with Axis/Conversion Links (No Target-Side Semantic Promotion)

A complete JSON envelope demonstrates donor-side data from CF48D A2L import, with axis/conversion links but explicit avoidance of any target-side semantic promotion. The `evidence_class` is `donor`; no `prior_report` link to FND/REC records is included.

Both examples are conceptual only — they illustrate the model's field structure and separation of target/donor evidence, not a working parser or database.
