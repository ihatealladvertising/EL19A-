## Objective

Define a practical, versioned shared data model and interchange contract for the modular ROM-tool suite. The result must let independently executable Python commands exchange reliable data without duplicating ROM/address/calibration logic or collapsing evidence provenance.

This is a specification task only. Do not implement Python classes, JSON Schema validators or database code.

## Required model coverage

Specify fields, identity rules, relationships, optionality and unresolved-state behavior for at least:

1. **ROM artifact/image:** original file vs reconstructed image, container, size, hashes, byte order, source identity and decoder provenance.
2. **Processor/profile:** processor family/model, capabilities, endianness and profile references; keep ECU-specific data outside generic processor behavior.
3. **Address space/memory region:** file offsets, ROM effective addresses, RAM addresses, address domains, mapping rules, region boundaries and address translation provenance.
4. **Symbols:** names, namespaces, kinds, multiple declarations at one address, duplicate names at different addresses, aliases and source references.
5. **Calibration objects:** address, storage type/width, signedness, byte order, dimensions, extents, axes, record-layout reference and conversion metadata.
6. **Axes and conversions:** fixed/axis-point/curve references, query domain, storage representation and raw-vs-physical conversion. Preserve source formula text and direction; do not require formula evaluation.
7. **Readers/lookups/consumers:** function and call-site identity, helper, arguments, query derivation, lookup/interpolation/search/clamp behavior, output and consumer relationships.
8. **Evidence/provenance:** immutable source hashes, path, source range, extraction method, observation, confidence/status, evidence class (target, donor, exact payload, screenshot, inferred) and links to Findings/Reconciliation records.
9. **Analysis run/result:** tool name/version, arguments, timestamp policy, input hashes, output schema version and deterministic result identity.

## Required design decisions

- Propose stable IDs and relationship representation that survive address relocation and cross-ROM comparison.
- Define address notation and ensure file offset is never silently treated as ROM EA or RAM EA.
- Define how duplicate address/name declarations and unresolved references are retained.
- Define a versioned JSON interchange envelope and compatibility/versioning rules; TSV/CSV should be derived review exports, not the canonical relational store.
- Separate shared core entities from processor-specific and ECU-profile extensions.
- Explain which fields are mandatory, nullable, unknown, unresolved or explicitly unsupported.
- Provide at least two worked conceptual examples: (a) a reader-backed EL19A calibration with target evidence; (b) a donor A2L characteristic with axis/conversion links but no target-side semantic promotion.

## Evidence and design rules

- A2L metadata and CF48D XML are donor inputs; they do not establish EL19A target facts.
- Exact payload equality, common geometry, structural function similarity and physical semantic identity are distinct relationships.
- Never require a semantic name for an object whose storage and reader behavior can be truthfully represented generically.
- Do not collapse source declarations sharing an address into one record.
- Preserve raw metadata and unsupported syntax so parser improvements do not discard evidence.
- The model should support SH7055/SH7058 now and other processor/ROM families later without pretending all address spaces or container formats are identical.

## Acceptance criteria

- All nine model areas are specified with identities, references and unresolved states.
- The versioned JSON envelope is sufficient for multiple standalone tools to exchange ROM, symbols, calibrations and evidence.
- Worked examples demonstrate separation of target proof and donor hypotheses.
- Migration from existing scanner/workbench outputs is addressed without altering those outputs.
- Findings disposition is stated; specification work alone should be NOT REQUIRED unless a material target calibration interpretation is corrected.
