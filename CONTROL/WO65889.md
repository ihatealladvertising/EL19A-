## Question

`FFFF355D` has two confirmed readers under GBR = `FFFF34B3` (`0x07EB14`, `0x0935C2`). Eight further `@(h'AA,gbr)` sites were listed in WO65886 as possible additional `FFFF355D` references. Which of those eight actually resolve to `FFFF355D`, and does any of them feed a torque/throttle/actuator path?

## Answer

**None of the eight resolves to `FFFF355D`.** The offset `0xAA` is a common GBR displacement, not an address. Under each site's own function-boundary base the eight split into exactly three distinct cells, and `FFFF355D` is not one of them.

Arithmetic: `FFFF1054 + 0xAA = FFFF10FE`; `FFFF3614 + 0xAA = FFFF36BE`; `FFFFB4A8 + 0xAA = FFFFB552`. `FFFF355D` is reached only from base `FFFF34B3 + 0xAA`, which is the base of `sub_A14F0` (`0x0A14F0`) — the writer routine of WO65886 — and of the two confirmed readers. No other routine uses that base.

### Disp scaling check

`0x032E8E` is `C5 55`. `mov.w @(disp,GBR),R0` scales `disp` by 2, so the encoded `0x55` is byte offset `0xAA`; the listing already prints the scaled offset. `C4 xx` / `C0 xx` (`mov.b`) are unscaled. Both encodings are confirmed by the listed opcode bytes at the cited lines.

### Function-boundary verification (no fixed line window)

- `0x25D5A` is `INT_ATU02_ICI0A`; its prologue is `stc.l gbr,@-r15` @ `0x25D7C` followed by `ldc r0,gbr` @ `0x25D80` from `off_25F00`. The nearest preceding `rts` is at `0x25D54`, whose delay slot `0x25D56` (`lds.l @r15+,macl`) and the data word `0x25D58` precede the entry.
- That body has three re-entries that each save and reload GBR: `0x26F66`/`0x26F6A` (`off_271B0`), `0x2772C`/`0x27730` (`off_2795C`), `0x27D82`/`0x27D86` (`off_27E8C`). **All three pool literals are `FF FF 10 54`, i.e. the same base `FFFF1054`**, so the reloads do not change the effective address for any of the seven sites. Two further entries in the same body use a different base entirely (`0x27992`/`0x27994` and `0x27AD6`/`0x27AD8`, both `word_27AF8` = `h'FFFF866C`) but lie after all seven sites and are not on their paths.
- `0x296BA` follows the alternate entry `loc_29500` (`sub_29500`-style interior label): full register save `0x29500`-`0x2950E`, `stc.l gbr,@-r15` @ `0x29510`, `ldc r0,gbr` @ `0x29514` from `off_29818`. That is the only `ldc rX,gbr` between the containing function's boundary and the site.
- `0x32E8E` is inside `sub_327FE` (symbol at LST line 66587; nearest preceding `rts` at `0x327FA`), whose `ldc r0,gbr` @ `0x32806` loads `word_328F0` = `h'B4A8`; `mov.w` sign-extends to `0xFFFFB4A8`. No `ldc rX,gbr` and no `lds.l @r15+,gbr` occurs between `0x32806` and `0x32E8E`.

## Classification of the three actual cells

### `FFFF10FE` — two-bit state flag written and read inside the ATU/ICI body

- **Writers** (the two stores): `0x02761C` writes `(r6 | 2) & ~1` — bit1 **set**, bit0 **clear**. `0x0276A4` writes `(FFFF10FE | 1) & ~2` — bit0 **set**, bit1 **clear**. The two writes are mutually exclusive single-bit states of the same byte, each built from the byte's own current value.
- **Readers**: `0x027274` `tst #2` → branch to `loc_2732A` when bit1 is clear; `0x0278F4` `tst #2` → branch to `loc_27908` when bit1 is clear. `0x0275F8` `tst #1` with `bf/s loc_27610` tests bit0 and seeds the bit1 write.
- The readers are pure bit tests gating private branches; the writers only flip the two bits. No value is scaled, offset-added, or handed to a command, and no path from these four PCs reaches an actuator store inside the traced window.
- **Classification: INTERNAL STATE FLAG** (two-state handshake bit pair, ATU/ICI-timer body). No named output.

### `FFFF36BE` — byte constant copied out of ROM

`0x0296B4` loads `off_29888` = `byte_83A8`, `0x0296B6` reads ROM byte `0x83A8` into `r0`, and `0x0296BA` stores it to `FFFF36BE`. This is a ROM constant seeded into a RAM cell, not a flag derived from computation.
**Classification: INTERNAL STATE CELL (ROM-constant image).** No named output established here.

### `FFFFB552` — `U16` word read at `0x032E8E`

`0x032E8E` reads `U16[FFFFB552]`, `0x032E90` `extu.w` zero-extends it into `r0`, `0x032E92` copies it to `r7`, `0x032E94` spills the low byte to the stack, and `0x032E9E` calls `sub_32790` before the `shlr8` at `0x032EA0` extracts the high byte. The value is therefore passed as a 16-bit **parameter** to `sub_32790` and split into two bytes for the stack frame.
**Classification: read-only input parameter of the `sub_327FE` dispatch path.** No named output; it is not a flag and it is not `FFFF355D`.

## Verdict on the issued question

Zero of the eight sites read or write `FFFF355D`. WO65886's added `FFFF355D` consumer set is unchanged: exactly the two base-`FFFF34B3` ladders at `0x07EB14` and `0x0935C2`. The remaining `FFFF355D` state also does not reach a torque, throttle, dashpot or actuator path from any of the eight sites. The inspection is a bounded negative over the eight named PCs only; no new `@(h'AA,gbr)` census was taken.

## Reconciliation (additive — no edit to WO65886)

- **Old claim (WO65886, "Consumers" section):** `FFFF355D` "also appears as plain `@(h'AA,gbr)`" at `0x027274`, `0x0275F8`, `0x02761C`, `0x02769A`, `0x0276A4`, `0x0278F4`, `0x0296BA` and `mov.w` at `0x032E8E`.
- **Corrected claim:** those eight sites are `@(h'AA,gbr)` under bases `FFFF1054` (×7), `FFFF3614` and `FFFFB4A8`, giving `FFFF10FE`, `FFFF36BE` and `FFFFB552`. None is `FFFF355D`; the shared value is the displacement byte `0xAA`, not the address.
- **Cause of the error:** matching the raw listing displacement (`h'AA`) across routines without resolving each routine's own `ldc rX,gbr` pool literal — the same failure mode as the `FFFF34E4` vs `FFFF34E7` error corrected inside WO65886, but applied in the opposite direction (assuming a shared base where none exists).
- **Confidence:** high. All bases are read directly from the pool literals at the cited addresses, and every site's function boundary was taken as the nearest preceding `rts`, not a line window.
- **Follow-on:** this is a second worked instance of the standing rule; it is folded into WO65895's reconciliation record rather than a separate record, because `FFFF10FE`/`FFFF36BE`/`FFFFB552` are RAM cells with no calibration-object identity.
