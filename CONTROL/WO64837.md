## Stage 3 — TEST results (2026-11-16; target ROM bytes verified)

### Exact target / donor fingerprint

Target ROM `VERSA f501.bin` (read-only; MD5 verified):
- F39E–F3A5: `14 6C 88 A4 C1 DD FF FF`
- E124–E12B: `07 1F 27 2E 36 3E 46 C8`

Juke reconstructed ROMs 9APCTDEM06/07/08 at A2L addresses 0x129F2 / 0x118A7 contain exactly the same two 8-byte vectors in all three variants:
- `mTTVBHOS`: `14 6C 88 A4 C1 DD FF FF`
- `mLVBHOS`: `07 1F 27 2E 36 3E 46 C8`

**Result: 8/8 data bytes and 8/8 axis bytes exact** in target versus all three Juke donor images. This is an exact paired fingerprint, not just an 8-point geometry match.

### Exact target query derivation

Correct function attribution: reader call is inside **`sub_36A80`** (entry PC 0x36A80), not the separate `sub_36A6` / `sub_36A08` helpers. GBR is set to FFFF2EC0. Data/axis call is at 0x36C7A–0x36C84.

Define:
- `d = U8(FFFF2ED5) + U8[ROM 0x8BA5]` (UWORD sum; target ROM[0x8BA5] = 0x11).
- `N = UDWORD[FFFF2ECC]`.

The UBYTE query passed to `sub_22EFC` is:
`q = 0xFF if d == 0; otherwise min( floor( floor(N / d) / 1000 ), 0xFF )`.
Both divisions are unsigned integer divisions through `sub_21BE4`; the helper has explicit zero-divisor and wide-divisor paths. The result is capped to UBYTE at 0x36C6E–0x36C78.

### Numerator / denominator state construction

- When FFFF35C8.bit6 is clear and bit4 is set, `FFFF2ED5 = low8(U8(FFFF2ED6) - U8[ROM 0x82EA])` (PC 0x36B64–0x36B78). The subtraction is not a saturating clamp; the low byte is stored.
- When FFFF35C8.bit6 is set, FFFF2ED6 increments by one with saturation at 0xFF (0x36B84–0x36B98); this path leaves ED5 unchanged. Otherwise ED5 may retain its previous value.
- When FFFF35C8.bit2 is set, the numerator is replaced by:
  `N = 5 × ROM[0x8BA5] × (ROM[0x8BA7] − ROM[0x8F49])²`.
  Target bytes: ROM[8BA5]=0x11, ROM[8BA7]=0xA1, ROM[8F49]=0x1E; this seed evaluates to **1,458,685**.
- On the alternate accumulation path (FFFF35C8 low two bits nonzero and upper C0 bits clear), N is updated by adding `5 × (U8[FFFF858A] − ROM[0x8F49])²`, saturating at `0xFFFFFFFF` (PC 0x36BCE–0x36C42). Otherwise the prior accumulator is retained. The upstream physical meaning of FFFF858A, FFFF2ED6 and the status bits remains unresolved.
- This establishes a squared-difference / accumulated-numerator and normalized integer-query mechanism. It does not establish that the underlying difference is voltage in mV or that the quotient represents mV².

### Output and downstream use

- Lookup result writes to `FFFF2EC8` and mirrors to `FFFF2EDB` at 0x36C86 / 0x36C8A.
- Under FFFF35C8.bit3 and additional branch gates, the first result is multiplied by `U8(FFFF2ED5) + 2×U8[ROM 0x8BA5]`, capped to UWORD, and stored at `FFFF2ED8`. A special gated branch may instead select 0x6400.
- A further `F2A6/E108` lookup uses the derived FFFF2ED8 word; its UBYTE result is stored at `FFFF2EDA`. Later state combination writes a longword at `FFFF2EDC`.
- `sub_36D80` consumes FFFF2EDC and ROM UWORDs at 0x9880/0x9886; it updates internal UWORD FFFF184C. Caller `loc_369D0` invokes `sub_36A80` then `sub_36D80`, scales FFFF184C and processes it through `sub_22E98/sub_3717E`, with an internal UWORD destination at FFFF84A6.
- No terminal physical sensor, actuator, or peripheral endpoint is established. FFFF2EC8/EDB are staged into the same routine’s later correction/lookup calculations; no separate direct consumer outside that routine is established in the inspected listing.

### Conversion / reference reconciliation

- Juke and V6 agree on data conversion `raw ×0.390625%`, but the target runtime arithmetic does not explicitly apply that display conversion.
- Juke axis A2L: `COMP_0457_S` = raw ×1,280,000 mV².
- V6 axis A2L: `COMP_0096_S` = raw ×1/255 dimensionless, although its same axis declaration retains a 0–326,400,000 mV² range and mV² display label. This is a reference-source inconsistency; neither axis formula is transferable.
- EL19A constructs q through a squared-difference accumulator, integer division and 1000 divisor, but no explicit conversion to mV² or normalized 0–1 is executed. This pattern is structurally compatible with a squared input metric but does not prove the units or signal identity.

## Correction note — V6 mTTVBHOS axis conversion (2026-11-16)

The V6 axis-conversion conflict stated in the initial Stage 1 / Stage 2 and Stage 4 sections above is **withdrawn**. It resulted from an incorrect reading of the accessible V6 A2L.

Reinspection of `64811000p2_m.a2l` confirms:
- V6 `mTTVBHOS` at `0xDC22` is an 8-point UBYTE curve using `COMP_0021` = raw × 0.390625%.
- V6 `mLVBHOS` axis at `0xCB17` uses `COMP_0096_S`.
- V6 `COMP_0096_S` is `COEFFS 0 1 0 0 0 1280000`, unit mV²: raw × 1,280,000 mV²/count.
- The V6 axis descriptor and `mLVBHOS` AXIS_PTS both declare 8 points and range 0–326,400,000 mV².
- Juke `COMP_0457_S` is also raw × 1,280,000 mV²/count.

Thus accessible Juke and V6 definitions have **numerically equivalent axis conversions**. Their method IDs differ, but coefficients and units agree. The earlier assertion that V6 `COMP_0096_S` is raw × 1/255 dimensionless was incorrect. Replace the earlier "SOURCE CONFLICT" disposition with **EQUIVALENT REFERENCE CONVERSIONS**.

This does not establish EL19A physical units: target q is generated by squared-difference accumulation and integer division, and EL19A does not explicitly apply the donor ×1,280,000 display conversion. The meanings of `FFFF858A`, `FFFF2ED6`, and `FFFF35C8` remain unresolved. Do not promote mV² units or a physical sensor identity into XML.

**Evidence:** Juke A2L `RFCC_2XHK19BDF1.a2l`, `mTTVBHOS/mLVBHOS/COMP_0457_S`; V6 A2L `64811000p2_m.a2l`, `mTTVBHOS/mLVBHOS/COMP_0096_S`. Both accessible V6 A2L copies were checked and contain the same COMPU_METHOD coefficients.
