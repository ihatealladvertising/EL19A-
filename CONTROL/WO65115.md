### Address normalisation (must be explicit in the output, not guessed silently)

The corpus mixes two notations and the ambiguity is real, not cosmetic: the playbook records that a 16-bit literal `h'8550` loads RAM `FFFF8550`, while a 32-bit pool value `0x8550` is **ROM** `0x8550`.

- 8 hex digits beginning `FFFF` → **RAM** (`FFFF85DF`, `FFFF1DB4`, `FFFF84BA`).
- Anything else (1–6 hex digits) → **ROM** (`0x8550`, `0x388AC`, `0xED64`, `0xF01C`).
- `--space rom|ram|auto` overrides; `auto` applies the two rules above. Every output row echoes the interpreted target and space so a mis-normalisation is visible rather than silent.

### Resolution ladder (all forms required)

For each target, resolve accesses in these forms and label which one hit:

1. **Absolute / literal-pool load** — `mov.l @(disp,PC),Rn` whose pool entry equals the target, and `mov.w`/`mov.b` literal operands where applicable.
2. **GBR-relative** — `@(disp,gbr)` and `@(r0,gbr)`, using the GBR value set by the most recent `ldc Rn,gbr` **in the same function** (GBR carried across a call or branch is an unresolved site, never a hit).
3. **Base register + displacement** — `@(disp,Rn)` where `Rn` was loaded from a literal/pool value and adjusted by `mov #imm` / `add #imm` / `add #imm,Rn` since.
4. **Base register + `r0`** — `@(r0,Rn)`, with `r0` tracked from `mov #imm,r0`, `mov.l …r0` and invalidated by any instruction that writes `r0` (`extu.b`, `exts.b`, `shlr`, arithmetic) unless re-established.

For ROM targets, additionally distinguish and report two different kinds of hit:

- `dereferenced` — the address is loaded and then used as a table/base (a reader of the data at that address).
- `constant` — the address value itself is used (e.g. `0xF100` compared, or a pointer stored), which is **not** a read of the table's contents.

`0x388AC` in the validation set is the `constant` kind; the four `0xEDxx`/`0xF01C` targets are expected to be `dereferenced`. Getting this distinction wrong is how "one user" and "one reader" diverge.

Widths: `b` / `w` / `l`, from the instruction form. Read vs write: destination memory operand = write, source = read; read-modify-write bit forms (`and.b`, `or.b`, `xor.b`, `tst #imm,@…`) report as `rmw` with the mask.

### Output contract

One TSV per run, sorted by target then PC, columns:

`target | space | pc | function | access | width | form | base | base_resolved | mask | note`

- `function` — enclosing `sub_XXXX`/`loc_XXXX` from the listing's own labels, or `unknown` with the nearest preceding label.
- `form` — `literal`, `pool`, `gbr_disp`, `gbr_r0`, `base_disp`, `base_r0`.
- `base` — the resolved base register value where provable, else `?`.
- `base_resolved` — `full` / `partial` / `none`. A `partial`/`none` row is **not** a reader claim; it is a lead.
- `note` — free text only for facts, never semantic names.

Plus a second file, `--unresolved`, listing every site where the ladder could not resolve the base or index, with the same columns plus `reason`. **Its existence is part of the contract**: a negative result must be able to say what was not checked. A run whose unresolved file is missing is invalid.

Both files carry a header block: ROM MD5, listing member name + SHA-256, resolver version, target file hash, run date, and the explicit method limits ("computed pointers, pointer tables, block-copy and `movca.l` transport are not modelled").

`--version` prints the resolver version. The version string is embedded in every output; **any behaviour change requires a version bump and a re-run of all five regression cases before the new output is cited.**

### PC concordance (cheap, required)

For every emitted row, verify that the opcode bytes at `pc` in the ROM match the bytes the listing shows for that line. Report `rows_checked / rows_matched` in the header of each output. A cited PC that does not byte-match the ROM is a phantom and must be dropped from that run and listed in `--unresolved`. This is the check that made the earlier traces trustworthy; it costs one pass over emitted rows only.
