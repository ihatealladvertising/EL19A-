## 2. `-64` hypothesis — resolved as a donor display conversion

| Symbol | Storage | Conversion | Limits |
|---|---|---|---|
| `vLADVTRM` | UBYTE | `COMP_0245` | `-64 … 191` |
| `vADVTRMAP` | UBYTE | `COMP_0245` | `-64 … 191` |
| `vADVTRM` | UBYTE | `COMP_0245` | `-64 … 191` |
| `vTADVMnm` | SBYTE | `COMP_0018` | `-128 … 127` |
| `bvBETA`, `vADVBL` | SBYTE | `COMP_0018` | `-128 … 127` |
| `vADVHOS` | SWORD | `COMP_0018` | `-32768 … 32767` |

`COMP_0245` is `/begin COMPU_METHOD COMP_0245 "X-64deg" RAT_FUNC "%8.2" "deg" COEFFS 0 1 64 0 0 1`, and `COMP_0018` is `"1deg" … COEFFS 0 1 0 0 0 1`.

So in the donor:

- the **trimming maps** (`vLADVTRM`, `vADVTRMAP`, `vADVTRM`) are stored UBYTE and displayed in degrees through a **64-count offset conversion** — this is exactly the forum's "conversion for them is X-64";
- **`vTADVMnm` does not use that conversion** — it is SBYTE through a plain `1deg` conversion with no offset.

**Verdict `-64`: SUPPORTED as a donor display conversion of the trimming maps; the forum's "finally -64 is applied to result in `vTADVMnm`" is INCORRECT against its own A2L family** — the offset belongs to the trimming-map parameters' display, not to an arithmetic step producing the base timing. Applying it to EL19A would be exactly the donor-semantics transfer the guardrails forbid.

**Target side:** EL19A's ignition-family objects (`0x9B2E`, `0x9C2E`, `0x9DAE`) are `storagetype="uint8"` with `scaling="Raw_UBYTE"`, and the v1 definition contains **zero** `deg` conversions. **No 64-count bias is established anywhere in the EL19A ignition path.** WO65287's negative stands and is not superseded.

## 3. `128` flag hypothesis — donor convention confirmed, target unresolved

- The trimming maps are **UBYTE** with a displayed range of `-64 … 191` (256 counts), while the downstream command variables are **SBYTE** (`-128 … 127`). The +128 the forum describes is therefore a **storage-format offset** in the trimming-map byte, consistent with its description of a knock window encoded in the same byte.
- The donor A2L contains no `COMPU_METHOD` that subtracts 128; the removal is firmware arithmetic in the donor, which this WO did not trace.
- **Target side:** the only EL19A bit-0x80 evidence in this lane is WO65704's finding that the two `bit_cleared=h'80` notes at `0x2902`/`0x2908` and `0x3626`/`0x362A` are **net SET** of bit 0x80 on *different* cells. That is **not** evidence of a knock flag on the ignition-family maps.

**Verdict `128`: donor-consistent storage convention; NOT supported on EL19A — UNRESOLVED.** No masks, tests or subtractions of 128 were found attached to `0x9B2E`/`0x9C2E`/`0x9DAE`.
