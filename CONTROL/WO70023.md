## Objective

Produce a source-grounded integration contract for converting the existing SH705x scanner's helper, call-site, table and span evidence into the tool's deterministic **per-address calibration-candidate catalogue**.

The goal is to prevent a lossy or misleading integration: every call must remain traceable; shared axes must not be mistaken for data tables; multiple calls to one address must be grouped without being discarded; conflicting geometry must remain explicit; and heuristic or unresolved observations must not be promoted to target-side facts.

This is a focused technical bridge between the existing scanner/workbench and the future shared model. It is deliberately complementary to WO70021: **do not define or supersede the canonical entity schema**. Use provisional conceptual mappings and list the exact alignment decisions that must be reconciled against WO70021 when its specification is available. Do not wait for WO70021 to complete this bounded source audit.

## Required work

### 1. Inventory the actual scanner export contract

Enumerate the fields and nested structures emitted by the current implementation for:

- helper records;
- every per-call record, including unresolved calls;
- per-table/grouped records;
- ROM/table/axis spans and hashes;
- top-level source, runtime, command and limitation metadata;
- JSON and TSV serialization.

For each field, record the producing function/source anchor, data type and nullability, what it directly observes, whether it is derived or heuristic, and any loss/transformation during TSV or workbench conversion.

### 2. Specify per-address grouping without losing observations

Recommend deterministic grouping and identity rules for calibration candidates, explicitly covering:

- one address referenced by multiple helper calls and/or functions;
- multiple calls that agree or disagree on width, dimensions, element type, axes or span;
- two distinct table candidates that overlap or share bytes;
- a data table and one or more shared axes at separate addresses;
- one call whose base is unresolved or whose geometry is incomplete;
- duplicate or repeated call rows and stable ordering across repeated runs;
- address-space identity (file offset vs ROM EA vs RAM EA), source ROM identity and profile context.

Do not silently merge conflicting observations into a single geometry. State when one address must retain multiple competing structural interpretations.

### 3. Define the non-lossy transformation into a per-address catalogue

Provide a field-mapping matrix from the current scanner export into provisional catalogue concepts, including:

- which source record is authoritative for each observation;
- which call-level evidence must remain nested or linked;
- how candidate byte extent is checked against the mapped ROM region and any independently observed span;
- how axis addresses and their extents are linked without treating them as table bases;
- how unresolved/null values and method limitations propagate;
- how source hashes, scanner version and run identity link each catalogue object to its input call rows.

Explicitly compare what the scanner JSON already preserves with what the aggregate workbench `cmd_scan()` / `cmd_audit()` currently lose or flatten. Identify the smallest adapter boundary that avoids duplicating `discover_helpers()`, `extract_calls()` or `build_scan_export()`.

### 4. Audit trust boundaries and failure cases

Identify which fields are direct observations, derived candidates or heuristics, including (where present) nearest-prologue caller candidates, bounded linear register-window values, delay-slot evidence, inferred memory bands, helper classification, dimensions and span bounds.

Specify failure/status behavior for truncated or out-of-region extents, missing span bytes, invalid element widths, inconsistent geometry, unknown processor/profile, absent optional indexes, malformed source metadata and partial scan failure. Do not invent semantic names, units, conversions, query sources, interpolation or consumer behavior.

### 5. Build an adversarial synthetic acceptance matrix

Specify small synthetic fixtures and expected outcomes for at least:

1. two independent calls to the same table address, with both call PCs retained;
2. one shared axis referenced by multiple data tables;
3. same base with conflicting geometries or element types;
4. overlapping but non-identical table spans;
5. unresolved table base / partial call arguments;
6. candidate extent crossing the mapped ROM boundary or truncated image end;
7. duplicate call evidence and deterministic sort/order;
8. donor-only symbol hit that must not become target semantic proof;
9. address-domain mismatch (file offset must not equal ROM EA by assumption);
10. missing/stale optional repository index.

This is a test specification only; do not write test code in this WO.

## Acceptance criteria

- All actual exporter record families and meaningful fields are accounted for from current source.
- The grouping strategy preserves every call and all conflicting interpretations while producing deterministic per-address catalogue records.
- Shared axes, overlapping spans, unresolved calls and address-space distinctions are represented without silent conflation.
- Every heuristic/derived field is separately labelled and its method limitation retained.
- The proposed adapter reuses existing scanner logic and avoids a second discovery implementation.
- At least ten adversarial fixtures have explicit expected outcomes.
- WO70021's canonical schema remains authoritative; unresolved alignment points are listed, not guessed.
- Findings disposition is explicitly stated. This specification should normally be NOT REQUIRED unless an actual calibration interpretation is materially changed.
