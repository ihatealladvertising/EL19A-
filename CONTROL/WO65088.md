## 1. Direct writers of UWORD `FFFF3366`

`sub_685A6` sets GBR=`FFFF9916`. The `FFFF2F00` base pointer is loaded from `off_6874C` (ROM `0x6874C` = `FF FF 2F 00`). The offset word is `0x0466` at both `0x6869A` and `0x6873A`. Exact effective address for each store is therefore `FFFF2F00 + 0x466 = FFFF3366`.

### Writer 1 — PC `0x68614`

- `0x68610–0x68614`: load base `FFFF2F00`, load offset `0x466`, then `mov.w R2,@(R0,R1)` stores a UWORD at `FFFF3366`.
- Candidate `R5` is selected from UWORD `FFFF992A` (`0x685C0`) or UWORD `FFFF9932` (`0x685C8`), according to whether byte `FFFF1E64` masked by `0xC0` equals `0xC0`. The `FFFF9932` branch is clamped to nonnegative; a negative input substitutes `IVECT1` (`0xFFFF` as a UWORD). Because writer 1 requires `R6=0` (equivalent here to `FFFF1E64.bit6` clear), its reachable `R5` source is specifically UWORD `FFFF9932`; the `FFFF992A` alternative requires bit 6 set and proceeds to writer 2's branch instead.
- Candidate `R7` is UWORD `FFFF9936` (`0x685EC`), likewise clamped nonnegative. The alternate `R7=R5` path requires bit 6 set in `FFFF1E64` and therefore does not reach writer 1.
- This writer is reached when `R6=0` at `0x685FA` (the `FFFF1E64.bit6`-clear path) and byte `FFFF1E6C.bit7` is **clear** (`0x68600–0x68604`). The code zero-extends `R5/R7`, then computes `R2=min(R5,R7)` at `0x68606–0x6860E` and stores it at `0x68614`.
- Its branch then sets `R2=IVECT1` and writes UWORD `0xFFFF` to the separate `FFFF2F00+0x46C = FFFF336C` field at `0x6861C`, before returning at `0x686D0`. It does not fall through to writer 2.

### Writer 2 — PC `0x686CA`

- The alternate path beginning at `0x6861E` obtains candidate `R5`: when bit 4 of `FFFF99EA` is clear and bit 7 of `FFFF8602` is clear, it takes the UWORD saved at `[SP]` (`0x6862C`); if either tested bit is set, it sets `R5=IVECT1` (`0x6863E`). It then processes the candidate using the following local state.
- `0x68640–0x686B6` gates/adjusts that candidate using `FFFF864A.bit7`, `FFFF3614+0x12 = FFFF3626.bit1`, `FFFF3629.bit4`, `FFFF362B.bit7`, `FFFF362B.bit6`, and ROM UWORD inputs `0x113BA/0x113BC` plus a byte at `0x11372`. Where that calculation path updates `FFFF336C`, its UWORD store is at `0x686B6`.
- Both paths converge at `0x686B8`. The routine reads UWORD `FFFF336C` at `0x686BE`, zero-extends it, and caps `R5` to the smaller unsigned word (`0x686C2–0x686C6`). It then stores UWORD `R5` to `FFFF3366` at `0x686CA`.
- Thus writer 2 is a final `min(candidate, UWORD[FFFF336C])` store. If `FFFF864A.bit7` takes the bypass branch at `0x68646`, the existing `FFFF336C` value still participates in this final cap.

### Exact-offset inventory

Across the annotated listing, the `0x466` offset object for `FFFF2F00` is loaded at `0x68612`, `0x686C8`, and `0x686F2`. The first two are the UWORD stores above; the third is the UWORD read at `0x686F6` by the adjacent `loc_686D4` ceiling path. No other exact literal-offset `0x466` code operation was found. This is an exact-offset result, not a census of computed/indexed aliases or generic block-copy destinations.

A bounded first-memory-operand triage of 85 literal roots into the `FFFF9800–FFFF98FF` region found no first operand that writes UWORD `FFFF9858`. This method stops at the first memory operation, explicit base-register rewrite, or control-flow boundary; it does not prove global absence of later uses or alternate aliases.

**Disposition:** no direct UWORD writer to `FFFF9858` is established by the exact literal-root/proven-first-use methods. This is not an immutability claim.

## 3. Relationship between the two ceiling inputs

- `FFFF3366` is written from the `FFFF992A/FFFF9932/FFFF9936` candidate path and, in the alternate writer, is capped by UWORD `FFFF336C`.
- `FFFF9858` is directly read by `sub_65174` and several other routines; the reviewed literal-root paths provide no proven writer or copy to/from `FFFF3366`.
- `sub_389AC` reads UWORD `FFFF9858` and fans it out into other `FFFF2F00` record fields (`+0x6A`, `+0x6C`, `+0x6E`, `+0x70`, `+0x72`, `+0x74`, `+0x76`, `+0x78`, `+0x7A`, `+0x7C`); it does **not** write `FFFF2F00+0x466`.
- Therefore no copy/common-source identity is supported between `FFFF3366` and `FFFF9858`. Keep the two ceiling inputs as separate values.
