## Question

What does `sub_32790` do with the 16-bit value it receives, and what is the role of `U16[FFFFB552]` in that path?

## Answer

`sub_32790` is a **five-append wrapper over the `FFFF2F00` byte ring** (the queue whose append helper `sub_33E18` was identified in WO65880). The 16-bit cell `FFFFB552` is read once, split into its two bytes, and both bytes are consumed as **message payload** for that queue: the low byte into a stack slot, the high byte into a 16-bit composite that is itself appended. No writer to `FFFFB552` was located; its producer is the stated boundary.

### 1. `sub_33E18` is a byte-ring append at `FFFF2F00 + 0xBB`

```
0x033E18  mov.l off_33E38,r1     ; FFFF 2F00
0x033E1C  mov   #0xBB,r6
0x033E20  mov.w word_33E36,r0    ; 0x416  -> head index word
0x033E24  add   r6,r2            ; r2 = FFFF2F00 + 0xBB
0x033E26  mov.b @(r0,r5),r6      ; r6 = UBYTE[FFFF2F00 + 0x416]  (index)
0x033E28  extu.b r6,r0
0x033E2A  mov.b r4,@(r0,r2)      ; UBYTE[FFFF2F00 + 0xBB + index] = r4
```

So each call appends **one byte** to a ring at `FFFF2F00+0xBB` whose head is a word at `FFFF2F00+0x416`.

### 2. `sub_32790` appends five bytes

```
0x032790  save r10-r14, pr; add #-8,r15
0x03279E  r10 = sub_33E18 (0x033E18)
0x0327A0  r12 = r4 ; r14 = r5 ; r13 = r6
0x0327A6  r0 = r7 ; 0x0327A8  mov.b r0,@var_1D     ; low byte of r7 on the stack frame
0x0327AA  jsr @r10 (r4 = r12)                      ; append #1 = argument r4
0x0327AC  r11 = @(0x20+arg_0,r15)                  ; stack-passed byte
0x0327AE  r4 = r14 ; jsr @r10                       ; append #2 = argument r5
0x0327B2  extu.b r11,r11
0x0327B4  jsr @r10  (delay: r4 = r13)              ; append #3 = argument r6
0x0327B8  r6 = (UBYTE var_1D << 8) + r11           ; 16-bit composite
0x0327C2  var_1C = r6
0x0327C8  tst #h'80,r0  (r0 = r12)                 ; r4 bit7 set?
0x0327CA  bf  loc_327E2                            ; set -> keep composite
0x0327CC  r2 = extu.w r6 ; r6 = r2-1 ; cmp/pz
0x0327D2  bt  loc_327DA -> r2 -= 1 ; r6 = r2       ; else r6 = 0
0x0327DC  r6 = r2  /  r6 = 0
0x0327E0  var_1C = r6
0x0327E2  extu.w r6,r4 ; jsr @r10 (delay: shlr8 r4) ; append #4 = composite >> 8
0x0327E8  r0 = word var_1C ; jsr @r10 (delay: r4 = r0) ; append #5 = composite low byte
```

Five bytes reach the ring per call: `r4`, `r5`, `r6`, `composite>>8`, `composite&0xFF`.

### 3. The caller hands the cell's two bytes to that path — at `0x032E8E`

`word_328F0 = h'FFFFB4A8`, and in this function `gbr = FFFF B4A8`, so `@(h'AA,gbr)` is exactly `FFFF B552`:

```
0x032E8E  mov.w @(h'AA,gbr),r0    ; r0 = U16[FFFF B552]
0x032E90  extu.w r0,r0
0x032E92  mov  r0,r7
0x032E94  mov.b r0,@(h'5C+var_59,r15)   ; LOW byte  -> stack slot h'5C
0x032E96  r0 = 0x1C ; r6 = UBYTE[r0+r15]
0x032E9A  r0 = 0x24 ; r5 = UBYTE[r0+r15]
0x032E9E  bsr  sub_32790            ; r12 holds the caller's flags word
0x032EA0  shlr8 r7                  ; DELAY SLOT: executes before the callee body
0x032EA2  bra  loc_331D0
```

The delay slot matters and is not an aside: `shlr8 r7` runs **before** `sub_32790`'s first instruction, so the callee receives the **high byte** in `r7`, not the whole word. The composite at `var_1C` is therefore `(high_byte_of_B552 << 8) | stack_arg`, and the cell's low byte is separately parked at stack slot `h'5C`.

### 4. Only one access exists, and it is a read

- `h'FFFFB552` appears **zero times** as a pool literal in the entire listing — there is no direct pointer to the cell.
- All ten `@(h'AA,gbr)` sites were checked: the five that are readable belong to other functions with other `gbr` bases (`FFFF866E` at `0x027600`, `r8`-relative at `0x0296A8`, `FFFF2150` at `0x0A948C`), so displacement `0xAA` is a generic offset and not a marker for this cell. `0x0296BA` is the `FFFF36BE` store already closed under WO65901.
- The single access to `FFFF B552` is the 16-bit read at `0x032E8E`. **No store to the cell was located.**

## Role

**Message payload field for the `FFFF2F00` byte ring.** The cell is a 16-bit quantity read by a command/response builder that appends a five-byte message; both of its bytes are consumed by that message path and neither is used as a flag or latch. The surrounding code at `0x032E74` compares a byte against `#h'41` (`'A'`), so this sits inside a command dispatch, not an independent sensor consumer.

## Classification

`QUEUE-PAYLOAD`, with the **producer `UNRESOLVED`** — no writer to `FFFF B552` exists in the located access set.
