### Track A — UWORD stage `FFFF1648`

- Reused WO65100: `sub_6CC8C` sets R13=`FFFF1054` at `0x6CC98`; both conditional paths store a UWORD at R13+`0x5F4`: `0x6CCEC` (RTS/branch delay slot) and `0x6CCF0`. Effective address is `FFFF1648`. The branch at `0x6CCBE` selects the direct-baseline/saturated-calculation path; both paths converge at `0x6CCF2`.
- Exact full-listing literal search for `FFFF1648` returns only its RAM allocation byte label, not a code pointer or direct absolute access.
- Exact immediate displacement search for `h'5F4` returns five occurrences total. The two relevant code occurrences are the UWORD stores at `0x6CCEC/0x6CCF0`; the other code occurrence at `0x96A4A` is followed by a store through R11 at `0x96A4C`. In that routine R11 was loaded from literal `FFFF2150` at `0x969EA`, so its effective address is `FFFF2150+0x5F4 = FFFF2744`, **not** `FFFF1648`. The remaining occurrence is the displacement data word itself.
- No direct UWORD load from `FFFF1054+0x5F4` was found in this exact-displacement census. No other literal pointer to `FFFF1648` was found. Thus the bounded direct/fixed-offset search found the writer but no direct reader.
- No consumer in the parent `sub_6CCFE` is established: it calls `sub_6CC8C` as the final operation in the gated sequence and then returns. This does not rule out a later task, dynamic pointer, computed offset or bulk-copy reader elsewhere.

### Track B — UWORD stage `FFFF29C4`

- Reused WO65100: `sub_969C2` conditionally updates or retains UWORD `FFFF9C5C` at `0x972A8–0x972B2`, then sets R13=`FFFF2150` at `0x972B4`, loads displacement `0x874` at `0x972B8`, and stores R14 to R13+R0 at `0x972BC`. Effective address is UWORD `FFFF29C4`.
- Exact full-listing literal search for `FFFF29C4` returns only its RAM allocation byte label, not a code pointer or direct absolute access.
- Exact immediate displacement search for `h'874` returns eight occurrences total. The only occurrence that pairs with a proven `FFFF2150` base is the writer at `0x972B8/0x972BC`; other occurrences are unrelated values/pointers (`0x8744`, `0x874D`), not the target displacement. No direct load from `FFFF2150+0x874` was found in this census.
- No second literal pointer to `FFFF29C4` was found. The bounded exact-literal/fixed-displacement search therefore establishes the writer and same-invocation copy from `FFFF9C5C`, but no later direct reader.
- This is not an exhaustive audit of dynamically computed offsets, inherited GBR aliases, pointer tables whose target is calculated at runtime, or block copies.
