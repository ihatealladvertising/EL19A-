## 3. Why the run must use LF copies of the inputs

`WO65803_ram_byte_bit_xref_generator.py` hashes its `--verify-wo65118` input and writes the digest into output header line 11 (`wo65118_tsv_sha256`). Executing it **in place** in this checkout reads the CRLF-smudged worktree copy of `WO65118_ram_byte_bit_xref.tsv` (2,214,495 B) and produces the same 5,262,288-byte file with **MD5 `224d44de92f153f0b27f5090f467620d`**, differing from the recorded artifact in exactly one line:

```

> # wo65118_tsv_sha256: b49375d3b7ab3ad5325107b5f7f024d59f938f86d7b75ea2be6e00f833fdf502
```

This is a checkout artefact, not a data difference (all 22,308 data rows are identical). The recovery therefore materialised the pinned inputs from their **git blobs** (LF bytes, hashes per §2) into a scratch directory outside the worktree and ran the committed generator there.

## 4. Recovery procedure (exactly reproducible)

Inputs are staged from the repository blobs, so the procedure is machine- and checkout-independent:

```
GD=$(git rev-parse --absolute-git-dir); S="$GD/w3-work/rec65803"; rm -rf "$S"; mkdir -p "$S"
git cat-file blob HEAD:"EVIDENCE/WO65803_ram_byte_bit_xref_generator.py"      > "$S/gen.py"
git cat-file blob HEAD:"EVIDENCE/WO65118_ram_byte_bit_xref.tsv"               > "$S/WO65118_ram_byte_bit_xref.tsv"
cp "EVIDENCE/VERSA f501.bin" "$S/VERSA f501.bin"
cp "EVIDENCE/EL19A_Complete_Disassembly_ANNOTATED_V3_NEXT6_14_GBR_BASE_RESOLVED.zip" "$S/"
cd "$S" && python gen.py --out run1.tsv && python gen.py --out run2.tsv
cmp run1.tsv run2.tsv
```

The generator resolves its defaults relative to its own directory, so `--rom`, `--listing-zip`, `--listing-member` and `--verify-wo65118` all point at the staged copies and no path string reaches the output (`listing_source` is `basename(zip)::member`). Interpreter: Python 3.12.10, standard library only. Wall time: a few seconds per run.

## 7. Checkout caveat for consumers

`.gitattributes` marks text files `eol=lf` while this host runs `core.autocrlf=true`, so a fresh checkout on Windows can leave the TSV's working copy CRLF while the committed blob stays LF. **Consumers must verify the committed blob** (`git cat-file -s`/`git cat-file blob … | md5sum`) or read via `git show`, not assume worktree bytes. Re-running the generator in a CRLF worktree reproduces every data row but rewrites the `wo65118_tsv_sha256` header line (§3), so in-place runs will not match the recorded MD5.
