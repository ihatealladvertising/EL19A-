## 1. Scope

WO65090/WO65065 identified a scalar cluster at ROM `0x829A–0x829F` and left its producer lineage
and arithmetic domain open. This WO resolves the consumers and the arithmetic role of each byte.
The cluster is ROM-resident, so "producer" here means the ROM image itself; no RAM writer exists.

## 3. Result — consumers and arithmetic domain

The cluster is a ROM-resident gain/limit table consumed by at least three routines. Each byte is
read via a pool pointer (`mov.l off_xxx, rY ; h'829A` etc.) and used with `shll2` (×4) or
`shll2`×2 (×16) scaling as a gain or comparison limit.

| ROM byte | Consumer (PC) | Function | Arithmetic role |
|---|---|---|---|
| `0x8298` | `0x8C710` | sub_8C6xx | gain (mov.b @r6, r2) |
| `0x829A` | `0x4CC0C`–`0x4CC32` | sub_4CB18 | gain: byte+2 shll2×2 (×16), byte+3 shll2×2 (×16) used as gain and limit vs a computed value; result stored to `FFFF2150+0xA86` |
| `0x829E` | `0x4CEEA`, `0x4CF0E` | sub_4CEC0-ish | gain: byte (0x829F) shll2×2 (×16) compared against an accumulated value; 0x829E used as a gain byte |
| `0x829F` | `0x4CEEA` | sub_4CEC0-ish | gain (shll2×2, ×16) |

The bytes at `0x829B`, `0x829C`, `0x829D` have no direct reader in the listing (no `h'829B/C/D`
occurrence); they are either padding or consumed by an indirect path not resolvable here.

### 3.1 sub_4CB18 path (the main consumer)

```
0004CC0C  D5 8E        mov.l   off_4CE48, r5 ; h'829A
0004CC14  84 52        mov.b   @(2,r5), r0      ; byte[0x829C]  (gain, ×16 after two shll2)
0004CC1A  40 08        shll2   r0
0004CC1E  40 08        shll2   r0
0004CC20  36 03        cmp/ge  r0, r6            ; computed value vs gain
...
0004CC28  D3 87        mov.l   off_4CE48, r3 ; h'829A
0004CC2A  84 33        mov.b   @(3,r3), r0      ; byte[0x829D] (limit, ×16)
0004CC2C  40 08        shll2   r0
0004CC2E  40 08        shll2   r0
0004CC30  35 07        cmp/gt  r0, r5            ; limit vs gain
0004CC38  90 20        mov.w   word_4CC7C, r0 ; h'A86
0004CC3A  0E 65        mov.w   r6, @(r0,r14)    ; result → FFFF2150+0xA86
```

So the cluster feeds a gain/limit clamp whose output is stored into the `FFFF2150` record block at
offset `0xA86` — the same block that holds `FFFF29C4` (offset `0x874`, WO65168).

## 4. Domain conclusion

The `0x829A–0x829F` cluster is a **ROM-resident gain/limit table** (bytes used as ×16-scaled gains
and comparison limits) consumed by at least three ignition/airflow routines, with outputs landing in
the `FFFF2150` record block. The bytes are not computed; they are calibration constants in the ROM
image. Their physical identity (which sensor/axis they scale) is not assigned here.

## 5. Residual unknowns

1. `0x829B`, `0x829C`, `0x829D` have no direct reader found; may be consumed via an indirect/indexed
   path or be padding.
2. The physical meaning of each gain/limit and the axis they apply to remain unassigned.

## Coordinator erratum — direct byte reads (2026-11-22)

The original §3/table text incorrectly lists 0x829C and 0x829D among bytes with no direct reader. The cited sub_4CB18 instructions show the opposite: with base r5 = 0x829A, mov.b @(2,r5),r0 at 0x4CC14 reads byte 0x829C, and with base r3 = 0x829A, mov.b @(3,r3),r0 at 0x4CC2A reads byte 0x829D. Both are shifted twice by shll2 (×16) and used in the gain/limit comparison path. Therefore 0x829C is a directly read gain operand and 0x829D is a directly read limit operand.

Corrected byte disposition: 0x829A is established here as the base address literal/pool pointer, not proven as a consumed table element by the cited excerpt; 0x829C and 0x829D are direct data reads; 0x829E/0x829F remain as described in the bounded sub_4CEC0-ish path; 0x829B has no direct read established by this evidence. Do not label 0x829C or 0x829D as unread. The broader gain/limit role is retained; physical sensor/axis identity remains unassigned.

No ROM/LST/XML/workbook/catalogue/tool changes were made. This note corrects the per-byte evidence ledger only.
