## Decision question

Ranked by downstream consequence, which of the 179 reader-verified varying tables absent from XML v3 should be promoted first, and what evidence would each promotion require?

## Answer in one paragraph

The ranking is dominated by how much the catalogue itself already records, not by the tables. Only **25 of 179** rows carry any destination or consumer text, and **154 rows** were catalogued as "varying table + accessor" with no downstream trace. Ranking therefore produces a defensible top nine (band A) and a much weaker band B, but **154 rows cannot be ordered on merit at all** with the evidence in the catalogue; they are not low-value, they are unmeasured. One row of the 179 is not a gap: **`0x0E904` is already declared in XML v3** (`Barometric Pressure Correction [S] mTHOSNTP (E904)`, 16×1 at `0xE904`, extent `0xE904–0xE913`), so the gap list is 178 promotion candidates plus one verification task — and of those 178, eighteen are byte-identical twins of another row, leaving **at most 160 distinct mechanisms**.

## Scoring method

Applied mechanically to every row; the score is a triage ordering, not a measurement.

```
score = 0.5 * min(distinct_callsite_PCs, 6)
      + 1.0  if distinct_callsite_PCs >= 2
      + 1.0  if distinct_callsite_PCs >= 4
      + 2.0  if destination_ram or consumer_or_notes is non-empty
      + min(sum(consumption keywords), 6)          # actuator 6, injector 5, ignition 5,
                                                   # throttle 5, duty 4, FFFF1340 4,
                                                   # FFFF1D12 3, advance 3, sets 2, GBR 2,
                                                   # feed/limit/clamp/gain/LPF 2, "->" 1
      + 1.5  if axis1 or axis2 names a ROM axis table (starts `0x…`)
      + 0.5  if neither axis does but axis text is present
      + 0.5  if the table is 2D (8x8 or 16x16)
      + 1.0  Reader-Verified / +2.0 Query-Traced / +1.0 Semantic-Strong
      - 8.0  if the extent overlaps a declared XML v3 data table
```

Columns used: number of distinct callsite PCs parsed from `helper_or_reader` (the ` @ 0x…` list — not the accessor name, so a routine used at six sites scores as six), presence of `destination_ram`/`consumer_or_notes`, consumption keywords, axis form, dimension class, `evidence_tier`, and XML occupancy. Bands: **A ≥ 8**, **B 5–7.5**, **C 3–4.5**, **D < 3**.

## Findings

### 1. The gap list is off by one, and the error is directional

`0x0E904` is declared in XML v3 as `Barometric Pressure Correction [S] mTHOSNTP (E904)`, 2D, 16 rows, `storagetype uint8`, occupying `0x0E904–0x0E913` — byte-identical to the catalogue row's `16x1` extent. It is not absent; it is declared `[S]` (source-only, unverified). Its correct treatment is **verification to lift `[S]`**, not promotion as a new table. Because it is both a gap-list member and an XML member, this is the only row where "absent from XML v3" is wrong.

### 2. `Reader-Verified` is weaker than its name implies, and it covers 88% of the list

158 of 179 rows are `Reader-Verified`, which in these records means *a varying table with a resolved accessor and callsite* — nothing about what reads the value downstream. Band D is 84 rows, of which the overwhelming majority are `Reader-Verified` single-callsite curves (`8x1` 47, `16x1` 32). **Queue position must not be read as confidence for these rows:** the tier attests existence and access, not consequence.

### 3. Consequence evidence exists for 25 rows and is concentrated

Only 25 rows reach any destination/consumer register, and nine of them name a block whose behaviour is already traced elsewhere: `FFFF1340`/`FFFF1054+0x2EC` (the WO65057/WO65058 LPF path), `FFFF1D12+0x3C`, `GBR+0x72`, `FFFF1054+0x244→+0x394`. That is why band A is small and why B drops sharply: beyond those blocks the catalogue stops describing destinations.

### 4. Multi-reader tables are almost absent

Only three rows have more than one distinct callsite, and one has four (`0x0F406`, the NTC voltage→temperature linearization, read from four sites). Reader multiplicity is therefore a weak discriminator here: the corpus is dominated by `sub_22DF8`/`sub_22F54`/`sub_22F80` one-site lookups. Consequence must be argued from consumer chains, not from read counts.

### 5. A partially covered region is visible by adjacency

39 rows sit within `0x20` of a declared XML table. The clearest cluster is the barometric/correction chain: XML declares `0xE800` (Warm-Up Decay Curve `[S]`), `0x0E904` (Barometric Pressure Correction `[S]`) and `0x0E974` (Correction Chain Enable Gate `[S]`), and the catalogue's `0x0E914` (16×1, sets `GBR+0x72` bit 4) and `0x0E934` (16×1, callers `sub_39FC8`) fall in the unclaimed gaps between them. Adjacency is circumstantial — it establishes a region, not a role — but it is the only structural hint available for rows with no consumption text, and it supports promoting these two together with the `0xE904` verification.

### 6. Eighteen rows are duplicates of other rows, so the list is ≤160 distinct mechanisms

Eighteen rows record themselves as a `Trustful twin` of another catalogue address (`byte-identical`), and one more (`0x10CE2`) records itself as a duplicate of `0x10226`. Every twin's stated primary is itself in the catalogue, so no twin introduces a new mechanism: **179 rows describe at most 160 distinct tables.** Bands C and D absorb almost all of them (14 in C, 4 in D), and none of the 18 carries any consumption text — the duplication is exactly in the unmeasured tail, where it does the most damage to a queue built on row count. Six twin claims were checked against the ROM and all six are byte-identical over their full extent: `0x119C4`≡`0x0C756` (512 B), `0x11BC4`≡`0x0C956` (512 B), `0x12A6E`≡`0x10226` (32 B), `0x128FE`≡`0x0F712` (16 B), `0x12D98`≡`0x1109A` (16 B), `0x12B9E`≡`0x10F2A` (64 B).

One cluster is worth naming because it chains: `0x10226` ↔ twin `0x12A6E`; `0x10CE2` is a duplicate of `0x10226` and itself has twin `0x12D38`. That is **one curve at four ROM addresses** (`0x10226`, `0x10CE2`, `0x12A6E`, `0x12D38`), which a row-count-based queue would have promoted four times.

### 7. Axis status does not discriminate, and one axis form is a convention, not a finding

81 rows carry an axis described as a fixed arithmetic progression (`fixed_0_32_224` = 0,32,…,224 for eight points), 53 name a ROM axis table, and 45 give storage form only (`explicit U8`). The `fixed_…` form is a reconstruction convention that matches a natural progression; it is not an independently measured axis and should not be cited as one. All 11 `8x8` and all 13 `16x16` rows do record both axes, so the 2D rows are the best-specified part of the corpus.

## Rows that cannot be scored from the catalogue alone

**154 rows.** Every one is `Reader-Verified` with at most one callsite and no `destination_ram`/`consumer_or_notes`. Three of them record no discrete callsite PC at all — `0x1100A` (`sub_22FAC @ 0x68A86+`) and `0x0CD56` (`sub_22D68 @ 0x66150+`) give only a `+`-suffixed address, and `0x10206` gives the accessor name with no address — so even the access count for those three is nominal. These rows are not rankable on merit; promoting any of them requires first extending its consumer trace — a per-row cost that WO65110 explicitly puts out of scope. Band C (75 rows) is the same class with a second callsite or a sparse note; band D (84 rows) is this class in its purest form.

Recommended handling for the 154: do **not** queue them individually. A single future WO should pick the densest sub-region (the `0x10xxx` and `0x12xxx` accessor families `sub_22E44`/`sub_22E60`/`sub_22F54`/`sub_22F80`/`sub_22FAC`/`sub_23128`/`sub_23170` account for most of them) and resolve consumer chains block-wise rather than curve-by-curve.

## Coverage limit — stated so it is not over-read

- **Duplicate detection against XML v3 is reliable only for 2D/3D XML tables.** Internal (catalogue-to-catalogue) duplication was taken from the rows' own `Trustful twin`/`Duplicate of` notes, not re-derived by comparing every pair of extents; six of the eighteen twin claims were verified byte-identical and the rest are taken as recorded. XML `1D` entries declare no extent (no `sizex`/`sizey`), so they were treated as single-point occupied addresses. A catalogue `1D` row that duplicates a declared `1D` table *and* does not start at its address would not be caught. Only `0x0E904` was found by the containment test, and it was confirmed by hand.
- **Axis identity is not resolved anywhere in this record.** Where the catalogue says `fixed_0_32_224`, this record repeats that as a reconstruction convention and claims nothing about the physical quantity.
- **Consumption keywords are a heuristic.** The keyword table is a screening device; two rows with the same score are not necessarily of equal consequence, and a row with no keywords is not necessarily inconsequential.
- **No new disassembly was performed.** Ranking only, per non-scope. Nine ROM comparisons were made to confirm catalogue claims (three ranges, six twin pairs) rather than to extend it.
- **ROM spot checks** (MD5 `46991697c502052752a2cabcb84c9e27` confirmed first): `0x0E914` 16×u8 = `143…119` (catalogue "143..119" ✓); `0x10FEA` 8×u16be = `26624,25006,23654,22323,20890,19640,18514,17531` (catalogue "26624..17531" ✓); `0x0A8A2` 64×u8 min 23 max 190 (catalogue "23..190" ✓).
