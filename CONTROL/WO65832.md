## Question

Do the big-endian U16 sequences at ROM offsets `0x0F8F2` and `0x0F942` have genuine target-code references as lookup axes, and, if so, which registered or previously uncatalogued data objects consume them?

The lead comes from `EVIDENCE/outside scan.txt` at repository commit `590a7f81ebd0c230f571fc760266bb016ca0a3b3` (blob `f9348b294c4ad15116ed641757cb6c4120cb563e`). That scan reports:
- `0x0F8F2`: a 16-word ascending sequence beginning `[25, 50, 100, 150, ...]`, with a purported longword occurrence `0x0000F8F2` at ROM PC `0x0704A4`.
- `0x0F942`: an 8-word ascending sequence `[0, 200, 400, 600, 800, 1000, 1200, 2550]`, with a purported longword occurrence `0x0000F942` at ROM PC `0x06BF00`.

These are scan-reported observations, not yet validated code references or axis identities.

## Falsifiable hypotheses

1. At least one of the two longword occurrences is a genuine SH7058 PC-relative literal loaded by executable code and passed, directly or after bounded register movement, as an axis argument to a lookup helper.
2. The occurrences may instead be mixed code/data bytes, unused constants, non-axis pointers, or incidental values; numeric monotonicity alone does not establish an axis.
3. Any true axis reference may belong to an already-catalogued data object; a new table is not presumed.

**Prediction:** a valid axis relationship requires a decoded instruction that loads the exact ROM address, a trace of the receiving register to the lookup call, and helper argument evidence identifying the address as the query axis. A matching 32-bit value in a byte scan without this chain is not a pointer finding.

1. Verify the ROM bytes at `0x0704A4` and disassemble the surrounding `0x070480–0x0704DF` context from the pinned EL19A listing/ROM.
