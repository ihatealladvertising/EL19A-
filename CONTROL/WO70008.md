## Question

Does the reported dual-donor `mQTBL` correspondence provide reproducible, correctly sourced evidence that improves the interpretation of EL19A `0x0FEE0`, or is it only a geometry-compatible A2L candidate?

## Lead to test — not a conclusion

The user-reported matcher result says the target's 64×1 UWORD lookup at `0x0FEE0` uniquely matched V6 `mQTBL` at A2L address `0x0E36C` and Juke `mQTBL` at `0x13984`. The reported matcher aggregates (103/217 functions; 45 dual-donor consensus) and the exact pair-level output have not been independently reproduced. The matcher source, documentation and raw outputs are not currently present in the repository.

Target geometry is already established by FND-000021/REC-000024. WO65133's older `mTATVO` candidate was 32×1 and its “dimensions exact” rationale is superseded. The new `mQTBL` lead is dimension-compatible, but that alone does not establish physical identity, axis units, function or scaling.

## Mandatory provenance boundaries

1. **V6 A2L ↔ candidate HEX remains NOT VERIFIED.** WO65212 explicitly found no adequate identity proof between `64811000p2_m.a2l` and `64810223F121200000.hex`. Treat the V6 A2L as metadata only. Do not use V6 HEX payload or code to claim a validated V6 function correspondence unless a separate, explicit pairing proof is established within this scope.
2. **Juke A2L ↔ S19 address mapping has bounded support only.** WO65213 validated three independent address mappings. Independently validate the `mQTBL` address against `9APCTDEM06.s19` before making a payload claim about this particular symbol.
3. Neither donor is EL19A. Donor function names, dimensions, axes, conversions and values are hypotheses for comparison, not target-side proof.
4. Do not fabricate missing matcher source, documentation, score details, matched function IDs or raw result rows. If those artifacts are unavailable, say so and continue only with independently available A2L metadata checks.
