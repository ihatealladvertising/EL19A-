## 3. Independent Juke address/payload verification

`9APCTDEM06.s19` was parsed record-by-record: 4,096 S1 records and 61,440 S2 records, yielding 1,048,576 distinct byte addresses over `0x00000–0xFFFFF` with zero conflicting byte assignments.

- Address `0x13984–0x14003` is fully populated (0 missing bytes): 128 bytes = 64 big-endian UWORDs.
- Values: `[0, 111, 111, 111, 111, 111, 111, 133, 162, 200, 244, 297, …, 58889, 61939]`; monotonic non-decreasing; 59 distinct values; first `0`, last `61939`.
- The following 16 bytes at `0x14004–0x14013` are all `0x00` (zero padding).
- The three WO65213 anchors were reproduced from the same parse: `mECUHWNO` `0x8204` = ASCII `10030400000`; `mMKLMRTH` `0x11937` begins `00 00 00 07 0A 07 07 0A 07`; `mTADVTRSN` axis `0x11B6C` begins `08 0C 10 14 18 20 28 30 38 40 48`.

This confirms that the Juke A2L address convention maps directly to the S19 payload for this symbol and that the declared 64-UWORD extent is physically present. It does **not** establish correspondence to the EL19A object.

This is not a contradiction, but the doc does not state which V6 table address the function match used and provides no auditable pair rows.
- Per the stop boundary, the matcher was **not** run, recreated or modified.

Therefore the reported `mQTBL` function correspondence remains an external, unreproduced claim. The A2L declaration facts in §2 and the Juke payload facts in §3 are independently reproducible; the function-level consensus is not.
