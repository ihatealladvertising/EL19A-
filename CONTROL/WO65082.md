## Checkpoint 2 — object classification supersedes table-geometry hypothesis (2026-11-21)

### Finding

The premise that `0x12844` is a single calibration table is **not supported**. The LST explicitly labels the address `byte_12844`, and direct readers use it as a byte-addressed base / global data base, not as a conventional table pointer passed to a calibration interpolation helper.

### Direct evidence

1. **ROM object bytes:** LST lines 19088–19142 show:
   - `0x12844–0x1284D`: individual byte fields `10 01 02 00 00 0F C0 00 01 20` (with alignment at `0x1284E`).
   - `0x12850–0x1286E`: mixed longword/byte data.
   - `0x1286F–0x12893`: further individually labelled byte/longword fields.
   - `0x12894–0x1289B`: longwords `8, 0`.
   - `0x1289C` begins a separate large data region containing byte/word sequences that resemble axis/curve data; this is not evidence that the entire base `0x12844` is one uniform map.
2. **Direct fixed-offset byte-field readers:**
   - `0x2131E` loads `byte_12844` into R6, then tests byte offsets `+0x25` and `+0x26` using bit `0x80`.
   - `0x2E532`, `0x2E57E`, `0x2E5D4`, `0x2E628` load the same base and inspect byte offsets `+0x06`, `+0x2B`, `+0x02`, `+0x39` respectively; these are flag/field tests, not map indexing/interpolation.
   - Similar fixed-offset flag/field reads occur at `0x338B8`, `0x338FA`, `0x33944`, `0x33998`, `0x35FD0`, `0x3A45A`, `0x4823E`, `0x65BEA`, `0x6DF50`, `0x708B2`, and throughout the `0x7xxxx–0x87xxx` code regions.
3. **Used as a GBR/global data base:** `sub_31DAA` at `0x31DB8` loads `0x12844` into R0 and executes `ldc R0,GBR` at `0x31DBA`. Its subsequent routine uses GBR-relative state/fields while calling `sub_33E18`; this is incompatible with treating the base itself as a simple calibration array pointer.
4. **Used as a byte lookup/indexed mask base:** at `0x33218`, R9 is loaded with `0x12844`. The loop at `0x33242` uses a dynamically derived byte index in R0 and reads `mov.b @(R0,R9),R2`; the index originates from a byte in a separate `0x12E38` record. This is a byte-indexed lookup/flag path, not a demonstrated numeric interpolation map.
5. **Another reader context:** around `0x2E8CE`, the code loads `0x12844` into R5, reads byte `+2`, and gates a path that separately obtains UWORD inputs from GBR offsets `+0x24/+0x26`, `+0x20/+0x22` and calls `sub_33A30`. The helper's query values are supplied by those GBR fields; the observed `0x12844` access is a flag gate, not a demonstrated table argument.

### Corrected interpretation and limits

- Treat `0x12844` as the base of a **heterogeneous ROM data/configuration block** containing byte fields, longword fields, and subsequent embedded data regions. This is a structural description only; no Nissan semantic name is assigned.
- The 35-load count and the claim that these are all calibration-helper arguments were inherited from WO65080; this WO did not independently reproduce the 35-call census. The sampled code-use evidence contradicts interpreting all 35 as a uniform calibration table. Any specific helper-argument use must be demonstrated at its own callsite before it is classified as a calibration table.
- The block's exact end boundary, full field schema, and identities of embedded arrays beginning at/after `0x1289C` remain unresolved. Do not infer a single 1D/2D geometry from the block's byte patterns.
- No numeric table width/signedness, dimensions, axes, interpolation, or clamping contract can be assigned to base `0x12844` as a whole.
