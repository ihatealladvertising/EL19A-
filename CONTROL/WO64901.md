## Objective

Resolve the caller-local R9 cap in the ECCE/ECDE lookup path, prove the exact effective query, and distinguish caller saturation from the fixed-grid helper's upper-bound behavior.

## Exact R9 initialization and use

- Within `sub_77608), PC `0x77F5E` loads `0xFFFFFFFF` into R9 and PC `0x77F62` zero-extends the low byte. Therefore **R9 = 0xFF**.
- No intervening R9 write was found before the comparison at `0x7836E`; the inspected intervening lookup/helper and local arithmetic code does not assign R9.
- At `0x78358), the caller reads UBYTE `FFFF859C+0x08`.
- PCs `0x7835E–0x7836A` subtract 8, floor negative values to zero, and move the nonnegative result into the query register. PC `0x7836C` doubles it.
- At `0x7836E), the doubled query is compared with R9; when it is above R9, `0x78374` moves R9 into the query register.
- Exact query equation:
  `q = min(2 × max(U8[FFFF859C+0x08] − 8, 0), 255)`.

## Helper upper-bound behavior

`sub_22E10` is a fixed-grid 16-point UBYTE lookup:
- It compares the UBYTE query against `0xF0) at `0x22E14`.
- For `q >= 0xF0), it takes the return path whose delay slot reads the last table byte `[R4+0x0F]` at `0x22E20`.
- For `q < 0xF0), it enters the normal fixed-grid interpolation path.

Consequences for the ECCE/ECDE caller:
- UBYTE input values below 8 produce query 0.
- For input values 8–127, query is `2×(input−8)`.
- At input 128, query reaches `0xF0`; inputs 128–255 therefore select the final 16th point under the helper's upper-bound path.
- Although caller R9 caps the query at `0xFF`, the helper's final-point return threshold is `0xF0`; the last-point region begins at input 128, not only when the cap is reached.

## Distinction from ECEE–ED1E path

The four-curve ECEE–ED1E query path has its own R9 initialization/cap sequence and is not to be conflated with the ECCE/ECDE path. This WO resolves the cap used at the ECCE/ECDE calls only.
