## Decision question — ANSWERED

The two `0x10FEA` callers are **parallel applications of the same 8×1 UWORD curve in distinct state machines**. They use different AN27-derived source bytes (`FFFF84BF` vs mirrored `FFFF84B8`), different caller routines, and different multiplier sources, but they converge on the same staged fields `UWORD[FFFF1848]`, `ULONG[FFFF1844]`, and `UWORD[FFFF84AC]`.

`FFFF84AC = FFFF8494+0x18` is directly written by both paths, including C2 at `0x375CC`. It is a **separate field** from the E904/E914 query multiplier at `FFFF8494+0/+2`; WO64842's warning remains correct. No physical unit, sensor/actuator endpoint, or shared physical calibration meaning is proven.

This record consolidates the parallel branch pass (`2a46b40`) with an independent reconstruction. The parallel pass correctly established the payload, fixed grid, reader mechanics, both callsites, the shared `FFFF1848` cell, and the catalogue discrepancy. Its stop boundary is superseded here by the traced `FFFF84AC` read and flag consequence, and three of its delay-slot/width statements are corrected in section 5.

## 4. Caller 2 — `FFFF84B8` path

## 5. `FFFF8494+0x18` and cross-record reconciliation

| Claim | Resolution |
|---|---|
| `FFFF84AC = FFFF8494+0x18` | **Correct.** Listing displacement and resolver run B confirm it. |
| C2 writes it at `0x375CC` | **Correct**, with `r8 = FFFF8494` loaded at `0x375C4`. |
| C1 writes it at `0x292BC` | **Correct**, via `r6 = FFFF84A4` and already-scaled offset `8`. |
| It is the E904/E914 query multiplier | **Wrong.** E904/E914 use `UWORD[FFFF8494+0]`; the `+2` field `FFFF8496` is also distinct. |
| `0x20E30 mov.w @(2,r14)` reads `FFFF8496` | **Wrong.** With already-scaled offsets it reads `FFFF8498`; `0x20E34` then writes `FFFF8494`. The broad A552-derived direction is retained, but that specific `+2→+0` citation is invalid. |
| C1/C2 share the same field | **Yes for `FFFF84AC`**, but not for `+0/+2`. C1 also writes `FFFF8496` at `0x29302`; C2 writes `FFFF84AA` and `FFFF8496` nearby. |
| `0x20A54` writes `FFFF1848` | **Wrong.** `r3 = FFFF1798`, `@(h'2C,r3)` gives `FFFF17C4`; resolver run B has no `FFFF1848` hit there. |

Distinctions preserved: same routine vs shared input vs arithmetic dependency vs same field. C1 and C2 are different routines with different multiplier sources; they share the curve and the AN27 producer family and converge on `FFFF1848`, `FFFF1844`, and `FFFF84AC`.

Corrections to the parallel branch record (`2a46b40`) that do not discard its valid findings:

1. `0x2917C` and `0x3759E` `extu.w r5,r5` are `jsr` **delay-slot argument setup**, not post-return result normalization.
2. `0x375A8` is `mov.l`, so the `FFFF1844` store is a **ULONG**, not a UWORD.
3. `0x375CC` stores the clamped scaled product through `r5 → r0`, not a raw unscaled curve result; the multiplier `U8[FFFF18DC]` and `>>7` clamp are part of the field's value.
