## Falsifiable hypothesis record

- **Identity layer advanced:** internal coefficient identity, input side.
- **Hypothesis:** the two levels are a genuine two-set coefficient pair selected by a condition inside `sub_22E7C`, because a padded block would normally repeat one value throughout.
- **Evidence:** WO65490 §4.6 (distinct-count 2: `0x1900` ×6, `0x1E46` ×10, split at entry 6); WO65323 §3.4.
- **Prediction:** the reader will either index the block in a way that distinguishes entries <6 from entries ≥6 (or load one level per branch), **or** read it uniformly, which would mean the step position is an artefact of a shared table.
- **Cheap discriminator:** decode the indexing at `0x5B5CE` and its caller only.
- **Result:** **REJECTED.** Neither a flag branch nor a uniform block read exists. The reader performs a **continuous 16-entry interpolated lookup** whose index is a 4.4 fixed-point byte; the payload is a step, so both levels are reachable as *consecutive points of one curve*, chosen purely by the numeric index. There is no selection condition other than the index value itself.
- **Information gain:** settles that `0x108B4` is not two coefficients and not padding, and identifies the exact input (one RAM byte) and the exact consumer address — converting an unclassified demoted row into a reader-verified 16-point table with a degenerate payload.

## 2. Reader `sub_22E7C` — a range guard, then the shared word-table path

`0x22E7C`–`0x22E8C`:

```
0x22E7C  mov.l off_22E94, r0 ; h'F000
0x22E7E  extu.w r5, r5
0x22E80  cmp/hs r0, r5          ; r5 >= 0xF000 ?
0x22E82  bt      locret_22E8A
0x22E84  mov.l off_22E90, r6 ; h'234EC
0x22E86  jmp @r6
0x22E88  mov #IVECT1, r3        ; delay slot
locret_22E8A:
0x22E8A  rts
0x22E8C  mov.w @(h'1E,r4), r0   ; delay slot: returns U16[r4+0x1E]
```

- `locret_22E8A` returns **`U16[0x108B4+0x1E]` = `FFFF…`→ ROM `0x108D2` = entry 15** (`0x1E46`). Because the caller always passes `byte<<8 ≤ 0xFF00`, this branch is taken only for **`byte ≥ 0xF0`** — i.e. it is a **table-end clamp**, not a mode/flag test: index 15 would otherwise interpolate toward a non-existent entry 16.
- Otherwise control enters `loc_234EC`, the shared word-table entry point (`sub_22E98` enters at `loc_234FC` for byte tables).

## 3. Index geometry — 4.4 fixed point, 12 shifts

`loc_234EC` is a shift chain, counted exactly in `0x234EC`–`0x2351C`:

- **12 × `shlr r5`** with **12 × `rotcr r3`** — so `r5` loses its low 12 bits and those bits land in `r3`.
- `0x2351C swap.w r3, r3` forms the fraction; `0x2351E shlr8 r0` turns the carried `r0 = 0xF000` into `0xF0`; `tst r0,r0` is therefore **always non-zero**, so `bt loc_23532` (the byte-table variant) is **not taken** and the word path runs.
- `0x23524 shll r5` (×2 → byte offset), `0x23526 add r5, r4`, then `mov.w @r4, r1` / `mov.w @(2,r4), r0` → `(entry i, entry i+1)`, `extu.w` both, and `jmp @r6 ; sub_231C8` with `r0 = lo`, `r2 = hi`, `r3 = fraction`.

With `r5 = byte << 8` and 12 shifts:

```
index    i = byte >> 4      (0 … 15)          -> r4 + 2*i
fraction f = byte & 0x0F    (0 … 15)          -> r3, passed to sub_231C8
```

So the table is indexed by a **4.4 fixed-point quantity**: `0x00` → entry 0 exactly, `0x0F` → entry 0 + 15/16 of the step to entry 1, `0x10` → entry 1, and so on to `0xFF` (clamped by the guard at `0xF0`).

## 4. Why the payload is a step

| Index byte | Entry `i` | Payload | Result |
|---|---|---|---|
| `0x00`–`0x5F` | 0–5 | `0x1900` (6400) | 6400, except the last sixteenth |
| `0x5F` | 5, f=15 | `0x1900`→`0x1E46` | blended (≈7666 under linear interpolation) |
| `0x60`–`0xEF` | 6–14 | `0x1E46` (7750) | 7750 |
| `0xF0`–`0xFF` | guard | entry 15 | 7750 (no interpolation) |

Both levels are reachable at runtime, but they are not alternatives to be *selected*: the table encodes a **single step located at index byte `0x60` (= 6.0)**, and the 16-point vector exists only so the step can be interpolated over one sixteenth of the input range. The 6/10 split is therefore the **step position**, not a tap count, not a loop bound, and not a flag split — no loop or counter in `sub_22E7C` or the caller references 6 or 10.

## 5. Consumer

`0x5B5D2`–`0x5B5D6`: the interpolated result is stored to `U16[FFFF1054+0x2CA]` = **`FFFF131E`** (`mov.w r2, @(r0,r12)`, `r12 = FFFF1054`, `r0 = 0x2CA`). Immediately after, `0x5B5D8`–`0x5B5F6` reads `U16[FFFF1D12+0x3C]` and `U16[FFFF1D12+0x42]`, adds both to `U16[FFFF1054+0x5EC]` (= `FFFF1640`), clamps at `0x7FFF`, and enters a `mul.l`/`shll16` ramp computation. So the coefficient feeds a **scaling/ramp term alongside `FFFF1640`**, not an axis or a fuel/air map.

## 7. Reconciliation (additive) — correction to WO65490 §4.6

- WO65490 §4.6 recorded: *"`0x108B4` is not a 16-point coefficient vector: it holds exactly two values"*, and demoted it on that basis.
- **The measurement stands; the interpretation is corrected.** The *reader* unambiguously consumes it as a 16-entry interpolated vector (`@r4`/`@(2,r4)`, 12-shift index). Only the *payload* is degenerate. The correct statement is: **a 16-point interpolated characteristic carrying one step at index 6**, not a padded scalar and not a two-set pair.
- Consequence for the demotion: demoting it because "only two values" rests on an assumption the reader contradicts. The object should be described as a **step-shaped 16-point table**, and either emitted as such (16 points, two levels) or — better — described as a single threshold with its position, once the index's meaning is known.
