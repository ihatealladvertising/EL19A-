## Method actually used

Join only — no new ROM tracing, no reader census, no map rebuild. Per catalogued table the query cells were taken from `traced_query_inputs`, unioned with any `FFFFxxxx` cells named in the catalog `query_expression` (this union is what recovers second-axis queries such as the absolute-load axis of `0x0A0F2`). Each cell was then resolved against the diagnostic/query evidence already in the repository: the `query_pid_semantics` column, the WO65239 leads, and the Consult/OBD maps.

**Structural limitation worth recording:** `INDEX/consult_mode22_pid_map.tsv` carries ROM pointer/source addresses (`ptr1_addr`, `ptr2_addr` such as `0x0E36F`), not RAM query cells, and `INDEX/obd_mode01_pid_map.tsv` carries K-line/CAN *frame* and mask addresses (`0x0DFC0`, `0x0DFD0`). Neither index can be joined to a RAM query cell by address. The RAM-cell → diagnostic-variable identity therefore exists only where a prior WO already established it, which is why four variables account for all 24 named rows.

## Interpretation rules preserved

- The name describes the **query variable**, never the table's output or downstream purpose. No row claims a physical function, unit or conversion.
- `derived` is kept separate from `direct`: the ECT/IAT cells are rescaled NTC images, so no row asserts OBD/Consult equivalence for them.
- Where no supported label exists, the row keeps an address-based generic name (`Unnamed table 0xADDR (query cell FFFFxxxx …)`) rather than a guess.
- The 63 `definition-only` rows retain the provisional v1 XML names **unchanged** and are explicitly marked as not query-derived.

## Consequences for the next definition revision

- 24 rows may carry a query-variable-based name; every other row must keep a generic name.
- Do **not** emit ECT/IAT names as measured physical inputs of the table's output; the wording `… rescaled` is load-bearing and must survive into any new XML.
- `0x10FEA` is the only table here carrying two differently-named coordinates (ECT and IAT) — it must be emitted as a two-axis map, which agrees with the WO65490 axis findings.
