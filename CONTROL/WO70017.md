## Outcome summary

A machine-readable donor metadata library was extracted from the two pinned Nissan A2Ls and the CF48D RomRaider XML. The TSV contains **12,555 rows**: 4,614 V6 objects, 7,676 Juke objects and 265 CF48D table entries. Every A2L `CHARACTERISTIC` and `AXIS_PTS` declaration was parsed (`OK`); the CF48D rows are `PARTIAL` because that XML declares no scaling, storage width or extent. The library includes exact source hashes, record layouts, dimensions, byte extents, both axis descriptors, referenced conversion objects with raw formula text, units, limits, function-group membership and explicit unresolved fields. A concise candidate crosswalk to known EL19A addresses is recorded below, with every relationship labelled as a lead rather than a target-side proof. No donor name, unit, conversion or physical meaning is promoted into EL19A.

## 2. Parser and output integrity

The extractor was a purpose-written standard-library Python 3 script held outside the repository (not a scanner/workbench edit). Its SHA-256 at the extraction run was `88456f6c540138aec802933f994c614bdc30bac363d55fdf036f38de72db5aad`. The generated TSV `CONTROL/WO70017_DONOR_METADATA.tsv` has SHA-256 `6cf3552a51a8dd19c74de65e51dab5928a9786461a14badde9b800f71289220b`, exactly 26 header columns and 12,555 data rows, with no width-mismatched rows.

A2L files were decoded as Shift-JIS with replacement only for non-decodable bytes; every retained identifier and conversion token is ASCII. Each row carries `donor_rom`, `donor_a2l_or_xml` and `source_hash`, so a second pass can resolve it back to the exact source declaration by object name and address. Extra A2L attributes that are not part of the required schema (`BIT_MASK`, `DISPLAY_IDENTIFIER`) are preserved with a `META:` prefix in `unresolved_fields` and do **not** downgrade `parse_status`.

Every A2L `COMPU_METHOD` in both files uses `RAT_FUNC` with `COEFFS`; no `COMPU_TAB`, `FORMULA` or unsupported conversion type was encountered, so all raw conversion formulas are preserved verbatim in `raw_formula`. Dimensions and byte extents were derived from the object type, the resolved `FNC_VALUES`/`AXIS_PTS_X` element width, and each `AXIS_DESCR` point count (using the referenced `AXIS_PTS` count for `COM_AXIS`). No formula was numerically evaluated or transferred.

CF48D has 197 named top-level tables and 68 child axis tables (`X Axis`/`Y Axis`). For child rows the fixed schema is documented as follows: `object_name` is the child `type`, `function_group` carries the parent table name, and `axis_1_ref`/`axis_2_ref` carry child axis addresses. All CF48D rows are `PARTIAL` with `scaling_undeclared`, `storage_width_undeclared` and `extent_undeclared`: the XML contains zero `<scaling>` elements and no per-table byte length or data type.

## 4. V6/Juke conflicts preserved

There are **2,628 object names present in both A2Ls**. No shared name has the same donor address. **18** have different object kinds and **22** have different geometries; these are retained as separate rows, not normalized away.

- Type/geometry examples: `mHOSQMAX`, `mHOSQMIN`, `mRHSOSQL`, `mRO2DTHS1/2/3` are `CURVE 2x1` in V6 but `VALUE 1` in Juke.
- Geometry-only examples: `mGSTPID1` and `mGSTPID2` are `12x1` in V6 and `16x1` in Juke.
- Conversion-id conflict example: `mMPAMBFAC` is `8x8` in both, but uses `COMP_0485_S` in V6 and `COMP_0334_S` in Juke (identical normalized coefficient string `COEFFS 0 1 0 0 0 0.0244141`).
- Axis-unit conflict example: `mTMSATH/A/B` use `COMP_0482_S` in V6 and `COMP_0318_S` in Juke.
