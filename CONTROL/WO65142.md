## Objective

Preserve a bounded three-way audit of the CF48D definition, donor ROM and SH3B listing. Establish inventory/provenance consistency, classify XML storage-address coverage in the LST, record shared and non-directly-referenced entries, and document the two checksum-exclusion loops. This is a donor-reference audit only; it does not authorize importing CF48D addresses or semantics into EL19A.

Each of the 197 table nodes contains a name and storage address; the reported XML has no inline axis/scaling sub-elements.

All 197 storage-address entries fall within `0x7AD0–0xE022`; there are 194 unique start addresses. The ROM/LST/XML hash consistency above is accepted as reported input evidence, not independently re-hashed in this closeout.

## Methods recorded

1. Parse the XML with ElementTree and enumerate all 197 `<table>` entries.
2. Read raw ROM bytes and sample UBYTE, big-endian UWORD, F32 and 16-byte windows at each declared storage address.
3. Index LST line-start addresses using the `ROM:XXXXXXXX` prefix.
4. Search LST text for explicit `h'<hex>` literals matching XML storage addresses; separately inspect label names and nearest preceding packed data directives.
5. Inspect the SH3B listing around the standard and alternate checksum routines and their checksum-field exclusion tests.
6. Group the XML entries by the supplied name-based categories.

The first exact-line test was intentionally refined: IDA `.data.b/.data.w/.data.l` directives can pack sequential data under an earlier line-start address. Therefore, absence of an exact `ROM:0000ADDR` line is not evidence that the address is absent from the listing. Explicit literal matching is also only a textual-reference heuristic; it is not a complete relocation, pointer, data-flow or table-consumer analysis.

### Shared storage addresses

Three start addresses are each declared twice, giving six XML entries:

| Address | XML entries |
|---|---|
| `0x8DD1` | Cold Ignition Timing Map (16x16); Cold Ignition Timing Map Knock Window |
| `0x8ED1` | High Octane Ignition Timing Map (16x16); High Octane Ignition Timing Map Knock Window |
| `0x8FD1` | High Detonation Ignition Timing Map (16x16); High Detonation Ignition Timing Map Knock Window |

The supplied ROM samples report initial byte `0x43` at each address. The LST has an explicit label at `0x8FD1`; `0x8DD1` and `0x8ED1` lie inside a packed `.data.l` block beginning at `0x8DC4`. The duplicate definitions are consistent with two XML views over the same starting storage, but this audit does **not** establish their respective extents, bit layout, stride, or whether the knock-window view is a bitfield/overlay. The separate reader trace previously described for the ignition/knock data is relevant corroboration, but must be consulted before treating the layout as fully resolved.

### Entries without direct literal hits

There are 21 XML entries without a direct `h'<storageaddress>` match:

- **DTC 2–18:** 17 entries at `0xDDCE–0xDE0E`, each spaced by four bytes. DTC 1 at `0xDDCA` has a direct label/reference (`word_DDCA`). The following DTC addresses sit within the packed data block shown from `0xDDCC`; the absence of individual literal mentions is expected for sequential records and is not evidence of missing storage.
- **Four non-DTC entries:**
  - `0x8A4C` Speed Limiter — explicit label `word_8A4C`, with a write xref from `sub_48FE4+0x142`.
  - `0x854E` Speed Limiter (Fuel Restore) — lies inside a packed data block beginning at `0x853C`.
  - `0x7DA0` Dwell TIM Coefficient — lies inside a packed data block beginning at `0x7D90`.
  - `0x7AD5` Retard Side Limiter — lies inside a packed data block beginning at `0x7AD4`.

Thus, “no direct literal” means only that the simple textual search did not find a matching literal. It does not mean the object is unused, absent, or incorrectly addressed.

### Checksum definitions and code evidence

**Standard checksum** — XML-reported range `0x000000–0x0FFFFF`; sum location `0x8C38`; XOR location `0x8C30`.

- The listing labels `dword_8C30` at `0x8C30`; reported ROM values are XOR `0xA9FC26D7` at `0x8C30` and sum `0xADD2A987` at `0x8C38`.
- In the routine around `0x30AC–0x30C2`, the loop reads 32-bit words through `r6), accumulates XOR in `r7` and addition in `r4`, and advances by four bytes.
- It explicitly skips the word at `r5` (resolved in the supplied trace to `0x8C30`) and the word at `r5+8` (`0x8C38`).
- The caller-derived end/boundary is capped against `0xFFFFF` / `0x100000` in the shown path.

**Alternate checksum** — XML-reported range `0x2414–0x4162`; sum location `0x240C); XOR location `0x2410).

- The ROM block at `0x2408) is reported as `0x46343844` (ASCII `F48D`), followed by sum `0xBCA51E03` at `0x240C` and XOR `0xDFE3A261` at `0x2410). `INT_ATU31_IMI3A` begins at `0x2414`.
- In the routine around `0x32D2–0x32EA`, the loop reads 32-bit words through `r5), accumulates XOR in `r14` and addition in `r7), and advances by four bytes.
- It explicitly excludes `r5 == 0x240C` and `r5 == 0x2410` from the accumulation.

**Verification boundary:** the supplied evidence establishes that the code contains the described 32-bit add/XOR loops and exclusion guards. It does not include an independently executed recomputation of either checksum over the exact XML range, nor a proof that every runtime path uses the same range endpoints. Therefore, the stored checksum values are recorded, but checksum arithmetic is not marked independently reproduced or accepted as a successful recomputation.
