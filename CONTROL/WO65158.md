## 1. Target A — `0x98B1` (high-detonation intake-cam timing)

### Geometry

| Property | Value |
|---|---|
| Start / end (excl.) | `0x98B1` / `0x98C1` |
| Element | UBYTE, unsigned |
| Shape | 4 rows × 4 columns, row-major, no padding |
| Payload SHA-256 | `4e972baaee2ad54f78153134ef6484cd1a8e383d21582a21a481d4d214161916` |
| Payload | `80` ×16 (all bytes equal) |

Pointer: `off_96E24: .data.l dword_98B0+1` → `0x98B1`, loaded at `0x96D1C`. The 16-byte extent is fixed by the helper, not by the next XML entry: `sub_6E94` is the front-end already resolved in WO65156 — two `sub_7680` axis searches entered with `r4 = 3` (4 points) and a tail jump to `loc_74B8` with `mov #4, r5` (4 columns, byte neighbours `@r4`, `@(1,r4)`, `@r5`, `@(1,r5)`).

### Trace

| PC | Effect | Note |
|---|---|---|
| `0x96CB2` | `gbr = off_96E10` = `0xC2A0` | **ROM base**, not a RAM base; `@(disp,gbr)` therefore addresses ROM |
| `0x96CBA` | `tst #1, byte[FFFF23AC+2]` | section gate; cleared → the high-detonation correction is skipped entirely |
| `0x96CC2` | `tst.b #1, @(r0,gbr)` with `r0 = h'FFFFBBDE` | second gate; wraps to ROM byte `0x7E7E` bit 0 |
| `0x96CEA` | `r4 = off_96E20` = `0x9B11` | 16×16 **base** intake-cam map |
| `0x96CF6`/`0x96CFA` | `r5 = gbr+0x6C` (`0xC30C`), `r6 = gbr+0x4C` (`0xC2EC`) | base-map axes (out of scope) |
| `0x96CFE` | `jsr sub_6FB0` | base-map read; result → `r13` (`extu.b` at `0x96D02`) |
| `0x96D06` | `tst #h'40, byte[r12]` (`r12 = FFFF23AC`) | gate: bit 6 selects the correction branch |
| `0x96D1A` | `r5 = gbr + 0xC0` = `0xC360` | **first axis** (4 UBYTE) |
| `0x96D22` | `r6 = gbr + 0xB8` = `0xC358` | **second axis** (4 UBYTE) |
| `0x96D18` | `r0 = byte[FFFF85DC+5]` | first-axis query |
| `0x96D14` | staged low byte of `r14` at `sp+3` | second-axis query (read by the helper as the low byte of the word at call-site `sp+0`) |
| `0x96D24` | `jsr sub_6E94` (`r4=0x98B1`, `r5=0xC360`, `r6=0xC358`) | **the only read of `0x98B1`** |
| `0x96D28–0x96D2E` | `r13 = extu.b(base) − extu.b(correction) + 0x80` | base map result minus this map's result, re-biased by `0x80` |
| `0x96D30–0x96D40` | clamp to `0..0xFF` (`cmp/pz`, then `cmp/gt 0xFF`) | unsigned byte clamp |
| `0x96D44` | `byte[FFFF10B4+0xABB] = r6` | **result latched at `FFFF1B6F`** |

Two facts worth carrying forward:

1. **`gbr` is a ROM calibration base here.** `off_96E10` holds the literal `0x0000C2A0`, and the axes fall at `0xC360`/`0xC358` — inside the calibration area, not RAM. Assuming a RAM `gbr` for this function would put the axes in the wrong space.
2. **Both axes are currently all-zero** (`0xC360–0xC363` = `00 00 00 00`, `0xC358–0xC35B` = `00 00 00 00`) and the payload is uniformly `0x80`. In the arithmetic at `0x96D2A` an `0x80` correction means "subtract zero", so this map is neutral in this image. Whether that is a deliberate "no correction" calibration or an uncalibrated stub is **not resolvable statically**.

## 2. Target B — `0x8D01` (VVT drive abnormality diagnosis judgement delay)

### Geometry (the XML address is an interior cell)

| Property | Value |
|---|---|
| Reader base | `0x8CF8` = `0x8D01 − 9` (`0x7172E` loads `0x8D01`; `0x71736` `add #unk_FFFFFFF7` → `−9`) |
| Address formula | `0x8CF8 + i*8 + j`, both indexes from 8-point axis searches, **`i,j ∈ 1..8`** (both loops initialise to 1 and cap at 8) |
| Consumed window | `0x8D01 – 0x8D40` (exclusive of `0x8D40`; last reachable cell `0x8D40` holds `0x00`) |
| Element | UBYTE |
| Shape | 8 rows × 8 columns, row stride 8, the `j = 0` byte of each row unused |
| Window SHA-256 (`0x8D01–0x8D40`) | `558316e9f1e0e5918009a43d4d069e7723a7dc6f8a04ddbedc50d824284212f2` |

Consumed payload (rows `i = 1..8`, columns `j = 1..8`):

| i | bytes |
|---|---|
| 1 | `64 00 00 00 00 00 00 00` |
| 2 | `64 64 64 00 00 00 00 00` |
| 3 | `64 64 64 64 64 00 00 00` |
| 4 | `64 64 64 64 64 64 00 00` |
| 5 | `64 64 64 64 64 64 00 00` |
| 6 | `64 64 64 64 64 64 64 00` |
| 7 | `64 64 64 64 64 64 64 00` |
| 8 | `64 64 64 64 64 64 64 00` |

The nine bytes at `0x8CF8–0x8D00` (`00 03 07 AA 20 05 00 00 00`) are reachable by the address formula but **never selected** because index 0 is unreachable from either loop; they belong to the preceding object. That is why the XML's `0x8D01` is the first *consumed* cell and not a wrong address — but it is also not the reader's base, and a future handler that treats `0x8D01` as the table start with stride 8 would misalign every row by one byte.

## 3. Pairing / shared-state test

| Aspect | `0x98B1` path | `0x8D01` window path |
|---|---|---|
| Function | `sub_96CA4` (caller `0x96A06`) | `sub_712EC` |
| Axes | ROM `0xC360` + `0xC358` | ROM `0xB262` + `0xB26A` |
| Result cell | `FFFF1B6F` | `FFFF126C` |
| Downstream | subtractive correction on the `0x9B11` base cam map | deviation-vs-threshold decision |
| Shared | — | — |

- **No shared selector, gate or state cell.** Every flag each path tests belongs to its own function (`FFFF23AC+2`, ROM `0x7E7E` vs `FFFF84A0`, `0x85C1`, `FFFF105A`).
- **One shared input:** both take their first-axis query from `byte[FFFF85DC+5]` (`0x96D18` and `0x716F0`). That is the same *observed quantity*, not a selector linking the two paths; the axes it is searched against differ.
- **A is not standalone:** `0x98B1` is a correction subtracted from the `0x9B11` 16×16 intake-cam map result (`0x96D2A`). Any later claim about "the high-detonation cam map" must include that it is only ever consumed as a delta on another map.

Disposition: **A — established (structure, reader, arithmetic role). B — established (structure, reader, base bias, first decision). Relationship — contradicted as shared selector/state; limited to a shared query byte.**

## 4. Unresolved edges (explicit stop boundary)

1. **Physical identity, units and scaling** of both objects. `0x64` (100) as the delay plateau and `0x80` as the neutral correction are raw bytes; no unit, timer base or delay resolution is established.
2. **The all-zero axes at `0xC358`/`0xC360`** — intentional neutral calibration or uncalibrated stub; not determinable from static code.
3. **Query producers** — `FFFF85DC+5`, `FFFF84A9`, and the `r14` byte staged for the second `0x98B1` axis are RAM reads of untraced origin.
4. **The `0x9B11` base-map axes** (pool entries `0xC30C`/`0xC2EC` seen in the same block) and that map's own calibration status — out of scope here.
5. **The ROM-`gbr` convention** — `gbr = 0xC2A0` is verified from the pool literal, and the `@(r0,gbr)` gate wraps to ROM `0x7E7E`; the platform's exact intent for a non-RAM `gbr` base is not documented in the donor material.
6. **Computed-address/indirect readers** — the census is literal/pool-reference based; an indirect reader is not excluded.
