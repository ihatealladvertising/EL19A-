**Scope:** Normalize existing detailed Nissan SH705x table-layout exports into a versioned, family-aware structural baseline; quantify layout consistency; document scalar/axis/semantic coverage boundaries.

## Objective and boundary

Build a reviewable base set from pinned scan outputs, then answer whether the scanned ROMs share a consistent table layout and whether the corpus identifies the expected ignition/fuel/knock tables, scalars and axes. This is an offline synthesis of existing evidence. It does not run a new ROM census, promote donor semantics, modify calibration definitions, or claim vehicle validation.

## Method

1. Read each existing per-address table record and preserve the source image identity, decoded ROM hash, primary FID, processor, start/end/extent, table kind, element type/width, dimensions, axis storage/reference information where exported, call PCs, helper addresses, nontrivial flag and payload hash where available.
2. Keep source tiers explicit: full direct-DAT scans, EL19A target scan, first-class V6 strict scan, C12W work-order table map, and partial WO70026 donor aggregates. Do not merge these evidence classes.
3. Build shape and FID profiles using strict structural signatures. Compare the existing 431-DAT pairwise and direct EL19A comparison results; do not use donor name/scaling labels as target truth.
4. Keep Juke S19 as a code-twin inherited layout and a separate payload overlay; do not count it as an independent layout scan.
5. Validate row counts, extent/dimension arithmetic, output hashes and C12W/Juke payload-comparison totals.

The normalized data was built with `build_nissan_base_table_set.py` using Python 3.12.10 and standard-library modules. No fresh scan, `audit`, reference-index build, or XML export was run as part of this work order.

## Results

- **434 independent detailed layouts:** 431 direct DAT images plus the EL19A, V6 and C12W images. The normalized set contains **129,481 table observations** and **75,110 axis-link observations**. Juke is recorded separately as an inherited code twin.
- **48 structural signatures** appear in the combined profile. In the 431 DAT batch alone, 128,307 table observations were detected across revisions, 73,401 marked nontrivial, with 157,369 call/table associations. These are repeated per-image detections, not unique calibration objects.
- Common shapes are widespread: UBYTE 8×1 and 16×1 vectors, UWORD 8×1/16×1/32×1 vectors, and 8×8 / 16×16 2D maps recur through the corpus. There are 18,157 3D observations with both dimensions at least 8 in the combined set. Shape recurrence supports a structural search vocabulary, not ignition/fuel/knock naming.
- Within the 431-DAT set, all **4,939 pairs sharing the same primary FID** have exact agreement in the compared strict layout signature (address, extent, kind, type, dimensions and axis storage types).
- Across all **92,665** DAT-to-DAT pairs, median strict-layout Jaccard is **0%** and median address-ignored geometry-multiset Jaccard is **86.90%**. Across the 431 DATs compared to EL19A, none has a same-geometry match at a shared table start; the closest 1 MiB DATs share 14 of 291 start addresses, with 0 matching geometries. This is not a universal Nissan address template.
- C12W/Juke is a controlled layout/value example: 581 table addresses, 463 identical payloads and 118 differing payloads, across 7,170 differing calibration-region bytes; the executable code region is byte-identical.
- EL19A has 291 target table candidates. WO70031 records 287 RAW/PROVISIONAL rows, two established-presentation exceptions and two overlap holds. The target payload hash is present for all 291 rows in this base set. V6 has 302 current strict candidates and C12W has 581 rows, each with per-table payload hashes retained.

## Coverage limits and conclusion

The verified detailed-layout denominator is 434 independent ROM layouts, not 550+ complete per-ROM catalogs. The input batch had 11,668 unique direct DAT payloads; 9,186 loaded as ROM candidates, 2,482 were loader-rejected, and only 431 emitted detailed helper/table records. Another 8,755 loaded without detailed table records in that run. No-detail output is not evidence that no calibration tables exist. The 151-ROM reference index reuses earlier metadata and is not 151 complete rescans. The 24 WO70026 family aggregates and 183-row conservation ledger are kept separate to avoid overstating per-ROM coverage.

The evidence establishes a common **shape vocabulary** and very strong exact structure within same-primary-FID groups. It does not establish one cross-family address map or a complete catalog of expected Nissan calibration systems. The 431-DAT table pass was not a scalar census. EL19A has 2,739 scalar candidates and a bounded set of 72 off-window RAW/PROVISIONAL scalar candidates; these results do not establish scalar completeness across the donor corpus. Axis addresses/storage are captured where exports support them, but physical axis domains and units are not universally known.

The large 8×8/16×16 maps and 1D curves cannot be labeled ignition, fueling or knock from size/type alone. EL19A Findings keep the 9B2E ignition/knock overlay provisional. Boost, transmission, region and cylinder-count effects remain dimensions for future stratified analysis; this work does not assign observed layout differences to those causes.

**Conclusion:** treat this as a family-aware structural base, with per-ROM payload overlays and a separate semantic crosswalk. We do not yet know every table/scalar/axis a Nissan ROM should contain, especially the complete ignition/fuel/knock inventory.
