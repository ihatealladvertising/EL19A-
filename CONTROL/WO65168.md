## 4. The indirect consumer

`FFFF29C4` is not read as a named cell; it is consumed through the `FFFF2150` record block:

1. It is **stored into** the block at offset `0x874` (`0x972BC`), so any later routine that
   indexes the `FFFF2150` block at offset `0x874` reads this value.
2. The very next instruction (`0x972C2`) reads `UWORD[FFFF2150 + 0x19C]` (`FFFF22EC`) into `r0`
   and writes it to `UWORD[FFFF9C56]` — i.e. the routine uses the `FFFF2150` block as a lookup
   table keyed by the value it just stored, closing the loop `FFFF9C5C → FFFF29C4 (as index) →
   FFFF22EC → FFFF9C56`.

So the consumer of `FFFF29C4` is **the `FFFF2150`-block indexer at `0x972C2` and the surrounding
`sub_969C2` logic**, which treats `FFFF29C4` as a stored index/pointer rather than a scalar.
The "indirect" framing in WO65100 is confirmed: the value never appears as a `mov.w @rX, rY` with
`rX → FFFF29C4`; it is reached via `base + 0x874`.

## 5. Domain conclusion

`FFFF29C4` is a **stored index word** in the `FFFF2150` record block: it captures `UWORD[FFFF9C5C]`
(possibly updated from `r6` when `U8[FFFF9C12] == 0`) and is then used to index the same block at
offset `0x19C` (`FFFF22EC`). It is a pointer/index, not a measured scalar, and its "consumer" is
the block-indexing logic in `sub_969C2`.
