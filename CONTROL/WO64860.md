## Investigation closeout — 2026-11-16

**Technical status: COMPLETE — bounded internal-state consumer; objective address corrected.**

### Critical address correction
- The original objective incorrectly identified the output as `FFFF12EA`. At `0x403FA`, `sub_403D8` loads `R14 = FFFF2150`; the bypass path reloads the same base at `0x40418`. No later R14 reassignment occurs before the store/read pair.
- At `0x4052E–0x40530`, offset `0x296` therefore resolves to **`FFFF2150+0x296 = FFFF2446`**, not FFFF12EA.
- The selected byte from `0x848A/0x848B` is written to FFFF2446. At `0x4055A–0x4055E`, the same routine reads that byte back.

### Confirmed downstream calculation
- GBR is set to FFFF1028 at `0x403E8–0x403EA`; `mov.w @(0x1A,GBR)` at `0x40556` therefore reads UWORD **FFFF1042**.
- At `0x40560–0x40570`, the routine compares FFFF2446 (zero-extended UBYTE) with FFFF1042 (UWORD). If FFFF1042 is at least the byte, it calculates the difference; otherwise it selects UWORD sentinel `0xFFFF`.
- The resulting UWORD is stored to **FFFF1018** at `0x4057C`.
- WO64852 already established no direct reader/alias or bounded bulk-copy/DMA/DTC consumer for FFFF1018. Do not repeat that audit.

### Separate FFFF12EA collision
- The only audited `h'296` access using base FFFF1054 is in `sub_5C220`: it writes a UWORD to FFFF12EA at `0x5C262–0x5C268`. Its caller is `0x5C6AE`. This is a separate producer/path and does not establish that sub_403D8 writes or consumes FFFF12EA.
- Other `h'296` occurrences use different structure bases (including FFFF2F00) and are not aliases to FFFF12EA.

### Disposition
- Furthest proven QDSPT dataflow: ROM byte 0x848A/0x848B → UBYTE FFFF2446 → compare/subtract against UWORD FFFF1042 (or 0xFFFF sentinel) → UWORD FFFF1018.
- This is an internal numeric calculation. No throttle target, airflow request, actuator command, MMIO write or physical output is demonstrated.
- No evidence connects this pair to the separate screenshot 52.34% scalar.
- No XML, workbook, ROM or LST edits. Read-only closeout.
