## Principal result

A bounded HCAN1 subset is now mapped:

- **MB12** remains inactive (`MBC=111`).
- **MB27, MB29, MB30** are serviced as receive mailboxes by `INT_HCAN1_RM1`, using `RXPR1` bits `0x0800`, `0x2000`, and `0x4000` respectively.
- **MB28** is used as a transmit mailbox: code writes its eight-byte payload and requests transmission with `TXPR1` bit `0x1000`.
- A configuration block writes standard-ID candidate words for MB27–MB30 and DLC 8. MB28's ID/DLC are independently written by the transmit helper; the ID/DLC block's caller is not fully resolved for MB27/29/30.
- MB30's receive payload is copied from `FFFFDCC8` to a stack buffer, then parsed into `FFFF3DB2` and `FFFF3DBC–FFFF3DC1`. It does **not** flow to `FFFF8234`.

## 1. Mailbox initialization and configuration table

`sub_AFA9E` initializes the 32 HCAN1 mailboxes from the mailbox base at `FFFFD900`, stride `0x20`. Its generic pass clears the ID/extended-ID/timestamp fields and writes `0x0700` to each mailbox's MBC/DLC word (`MBC=111`, inactive).

It then calls `sub_AF6A6`, which applies a 30-entry ROM configuration table beginning at `0x9A66` to MB1–MB30. The table entries for MB27–MB30 (indices 26–29; `0x9ACE`, `0x9AD2`, `0x9AD6`, `0x9ADA`) begin with `0x02`; the routine writes MBC value `2` into each corresponding MBC/DLC word. MB12's inactive state is independently established in WO64836 and is consistent with the `MBC=111` configuration.

`sub_AFA9E` has callsites at `0x297EC` and `0xB01C8`. Thus the generic reset-to-inactive pass and subsequent table configuration are part of reachable initialization/reinitialization paths.

A separate ID/DLC writer block beginning at `0xAF9C8` writes the following values and checks them back. It sets R5 to `8` and stores that byte at mailbox offset `+5` (DLC field):

| Mailbox | ID/control word written | Standard ID if IDE=0 | DLC | ID/DLC writer confidence |
|---|---:|---:|---:|---|
| MB27 | `0x7DF0` | `0x7DF` | 8 | Medium — writer observed; caller not resolved |
| MB28 | `0x7E80` | `0x7E8` | 8 | High — also written by transmit helper `sub_B5580` |
| MB29 | `0x7E00` | `0x7E0` | 8 | Medium — writer observed; caller not resolved |
| MB30 | `0x7D00` | `0x7D0` | 8 | Medium — writer observed; caller not resolved |

The ID word field layout is from the Renesas *SH7058 Hardware Manual*, Rev. 6.00, §16.3.2–16.3.3 (pp. 529–533): STDID occupies bits 14:4, RTR is bit 3, IDE is bit 2, and the high two extended-ID bits occupy bits 1:0. All four observed words have IDE=0, RTR=0, and extended-ID bits zero; the decoded IDs above are therefore standard 11-bit data-frame IDs. The MBC field is bits 10:8 and DLC is bits 3:0 of the MBC/DLC word. The manual identifies `MBC=111` as inactive and `110` / `011` as prohibited; the MB27–MB30 table value `MBC=010` is not the inactive setting. Direction below is assigned from the observed RXPR1/TXPR1 paths, not guessed from MBC alone.

**Activation qualification:** the ID/DLC writer block at `0xAF9C8` is present, but its caller/cadence was not recovered in this bounded pass. Treat MB27/MB29/MB30 ID values as configuration candidates until that call path is tied to the initializer. MB28's ID/DLC are independently re-established in its transmit helper.

The HCAN1 pending registers are `TXPR1_W` at `FFFFD820` and `RXPR1_W` at `FFFFD840`. The receive interrupt vector entry at `0x2039C` points to `INT_HCAN1_RM1` at `0xB56F0`. That handler checks the HCAN1 receive interrupt status, then examines MB30, MB29 and MB27 pending bits. It clears the selected RXPR1 bit, copies eight bytes from the corresponding mailbox data start into a stack buffer, and dispatches the parser.

MB28 is not handled as an RXPR1 mailbox in this handler. Its transmit path explicitly sets TXPR1 bit `0x1000`.

## 3. MB30 receive payload and parser

For MB30, `INT_HCAN1_RM1` performs this sequence:

1. Test `RXPR1 & 0x4000` and clear the pending bit by writing the mask back to RXPR1.
2. Use source `FFFFDCC8` (MB30 data bytes 0–7), destination R15 stack buffer, and length 8 in `sub_B57D8`.
3. Read the DLC nibble from `FFFFDCC5`,  mask to four bits, and call `sub_B5392`. The delay-slot store places the DLC at stack offset `+8` for the parser.

`sub_B5392` accepts only this bounded layout:

- DLC at stack offset `+8` must equal 8.
- Data byte 0 must have a zero upper nibble, be nonzero, and be no greater than 7.
- Data byte 0 is stored as a UWORD at `FFFF3DB2`.
- Data bytes 1–6 are copied to the RAM destination pointed to by `off_163A4+4`, whose value is `FFFF3DBC`; destination span is `FFFF3DBC–FFFF3DC1`.
- Data byte 7 is copied to the stack but is not consumed by this parser path.
- The parser checks `FFFF3DAC.bit5` as a busy gate and updates status fields including `FFFF3DB5`, `FFFF3DCE`,  and `FFFF3DAC`.

MB27 uses the same `sub_B5392` parser path, with its own RXPR1 bit and data buffer. MB29's receive branch calls `sub_B437E`; that parser's payload layout was not expanded here.

## 4. MB28 transmit payload

`sub_B5580` is called from `sub_B560E` at `0xB5664`. It:

- Writes MB28 ID/control word `0x7E80`.
- Writes DLC 8 at MB28 offset `+5`.
- Copies 8 bytes from RAM source `FFFF3DD0–FFFF3DD7` to MB28 data `FFFFDC88–FFFFDC8F` via `sub_B57D8`.
- Sets TXPR1 bit `0x1000` when the associated state gates permit transmission.

A separate interrupt path at `0x4AF4–0x4B20` also writes MB28 data bytes and requests transmission with TXPR1 bit `0x1000`. After matching an input pattern `03 31 81 01`, it writes the eight-byte response-shaped payload:

```text
03 71 81 01 00 00 00 00
```

This proves an eight-byte MB28 transmit example. No protocol-service name is assigned from the payload alone.

## 5. Corrections and cross-checks

- **False lead corrected:** MB30's data source is `FFFFDCC8`; the parser destination is `FFFF3DB2) and `FFFF3DBC–FFFF3DC1`. It is not `FFFF8234). WO65102 establishes `FFFF8234` as a runtime pointer-table base populated from four-byte values in `FFFF8005`, not a CAN mailbox payload buffer.
- The serial receive parser window documented in WO65062 (`FFFF8500–FFFFBD00`) is a separate parser path. The CAN parser destination `FFFF3DB2/FFFF3DBC` is outside that window; do not merge their layouts.
- MB27 and MB30 share `sub_B5392`'s 8-byte receive layout. MB29 uses `sub_B437E`; its payload layout remains open. MB28 is a transmit mailbox.
- MB12 remains inactive; no new MB12 receive/transmit path was found.
