## Objective

Implement a durable, reproducible master ROM index that links every catalogue ROM code to its vehicle application and master-code group, then cross-references scanned ROM images by decoded identity, Nissan FID/ECUID, CPU, source filename and structural profile. Compare images to generate explainable candidate firmware/layout relationships and a chronological model/year/engine/transmission view.

This is not a workbook-only deliverable. The authoritative output is a versioned JSON index plus one-row-per-entity TSV views generated by the workbench. Workbook views may be generated from these outputs later.

## Data model and identity boundaries

The index keeps the following identities separate:

1. UpRev catalogue ROM code: one row per ROM ID, preserving IsMasterROM, MasterROM_ID, model, make, year, engine, transmission, source line and source URL.
2. Nissan FID/ECUID: exact matches to the separate ECU/FID inventory are linked; prefix-only matches remain explicitly provisional. Where a primary FID exactly matches an inventory row whose ECUID also exactly matches the UpRev crosswalk, a separate EXACT_CATALOGUE_CODE_VIA_ECUID catalogue link is emitted.
3. Decoded binary image: decoded ROM SHA-256 is the canonical image key. Duplicate containers and duplicate decoded images retain all source paths/scan records without multiplying image records.
4. Candidate structural family: pairwise relationships and connected components derived from independent code-region and strict layout evidence. These are not official Nissan ECU family identities.

No FID, catalogue master-code or filename match is treated as proof of structural family. No structural correspondence transfers calibration names, units, axes or physical semantics.

## Family-comparison policy

Relationship types are kept separate:

- CATALOGUE_MASTER_ROM_GROUP: common UpRev catalogue master group only; not structural proof.
- SAME_PRIMARY_FID_GROUP: shared binary FID only; not structural proof.
- EXACT_CODE_REGION_HASH: exact shared executable code-region hash.
- HIGH_STRICT_LAYOUT_OVERLAP: address + extent + structure + element type/width + byte order + dimensions + axis-storage signature Jaccard >= 0.80 and at least 12 shared observations.
- MODERATE_STRICT_LAYOUT_OVERLAP: weaker exact-address layout lead.
- SHAPE_PROFILE_SIMILARITY_LEAD: rare-weighted, address-ignored geometry similarity; generic common shapes are downweighted.
- REPEATED_EXACT_PAYLOADS_AT_SAME_ADDRESS: exact-payload supporting evidence.

Only an exact code-region hash or HIGH_STRICT_LAYOUT_OVERLAP can join a candidate component. Catalogue master groups, same FID, common payloads alone and shape-only similarity cannot merge components. All candidate groups remain explicitly unverified.

Per-image geometry prefers the fresh workbench catalogue when present and falls back to the pinned 434-layout table set for images without a fresh detailed catalogue. Images lacking either source are marked SUMMARY_ONLY, not treated as empty ROMs.
