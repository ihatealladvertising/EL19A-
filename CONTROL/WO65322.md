## Falsifiable hypothesis record

- **Identity layer advanced:** input identity (selector and query numeric domain).
- **Hypothesis:** `r14` is a bounded row index (0..15, 32-byte stride) selected by one software state, and the `+0x8000` term means the query is a signed, zero-centred quantity stored as offset-binary.
- **Evidence:** WO65293's read window `0x69150–0x69186`; target LST `EL19A_Complete_Disassembly_ANNOTATED_V3_NEXT6_16_ALL_PENDING_ANNOTATIONS.lst` (`sub_690C6` = `0x690C6–0x69260`+, caller `sub_68C28` @ `0x68DAA`, producer region `0x6B240–0x6B278`); `EVIDENCE/WO65120_call_graph.tsv`; `EVIDENCE/WO65118_ram_byte_bit_xref.tsv`; bounded ROM reads of `0x0E2C9`, `0x0FEC0`, `0x87C8` and the `0x0CD56` payload.
- **Prediction:** a bounded caller/guard trace would show `r14` assigned from a small enumerated state or a bounded multiply-by-32, and would show whether `FFFF1D72` is reused unchanged or re-derived before the centred lookup.
- **Cheap discriminator:** decode only `sub_690C6`'s entry/index construction and the `FFFF1D72` writer, using the existing call graph and RAM index before touching the listing.
- **Result:** **HYPOTHESIS PARTLY REJECTED, DOMAIN CONFIRMED.** `r14` is **not** a mode/state selector: it is loaded as the **axis-table pointer `0xE2C9`** at function entry and only later overwritten with the interpolation index. The row index is `r5`, produced by a bounded search of that same map's own X axis. The `+0x8000` centring is real and is the *same* offset-binary convention used to store the map payload and the staged value `FFFF1D72`.
- **Information gain:** converts the "unproven computed offset" worry into a verified bounded axis interpolation (row index is a normal map index, not a pointer), and fixes the query numeric domain as signed offset-binary — which is the precondition for ever giving this table defensible axis units. It also shows that only **one** of the two WO65293-recorded lookups is reachable with the current ROM configuration byte.

Conclusions:

1. **`r14` is an axis pointer that is re-used as the row index register.** There is no state/gear/mode selection and no unbounded computation: the only `r14`-derived offset is `index × 32` with `index ∈ {0..15}`, so every access stays inside `0x0CD56–0x0CF55` (512 B, 16×16 UWORD, matching the catalogue extent).
2. **Stride is exactly 32 bytes** — 16 UWORD cells per row — confirmed independently by the three shifts at `0x69148/0x6914C/0x6914E`.
3. **The index is a normal interpolation index into the map's own X axis `0x0E2C9`.** Axis bytes read directly (`0x0E2C9`, 16 B): `00 10 18 20 28 30 38 40 48 50 58 60 68 70 78 80` = 0, 16, 24, 32, 40, 48, 56, 64, 72, 80, 88, 96, 104, 112, 120, 128. The code compares against `axis[i] × 16`, i.e. a comparison domain of 0, 256, 384, 512, …, 2048.
4. **A second, non-lookup path exists.** When the query falls strictly inside the axis range, `r4` is left at its entry value (the listing's `IVECT1` = 0), `tst r4,r4` leaves `T = 1`, and `bt/s 0x6919C` skips the row lookups entirely in favour of the interpolating path at `0x691A0–0x6925C` (two `sub_21AC0` divides at `0x691F6`/`0x6920E` and two further `sub_22F80` calls at `0x6923C`/`0x69250`). The exact-breakpoint/below-first/above-last branches (`r4 = 1`) are the ones that reach the WO65293 window.

## 3. Query numeric domain — offset-binary confirmed

| Evidence | Anchor | Reading |
|---|---|---|
| staged value is produced as `lookup − 0x8000` | `0x6B264–0x6B26C` | signed offset-binary representation |
| consumer re-adds `0x8000` before the lookup | `0x6915A`–`0x6915E` (`mov.w @(0x60,FFFF1D12),r6`; `add r5,r6` with `r5 = 0x8000`) | the axis domain is the *unsigned* image of a signed quantity |
| second lookup always adds `0x8000` | `0x6913C`–`0x6913E` (`r2 = U16[FFFF1640]`; `add r6,r2`) | same convention for `FFFF1640` |
| payload is centred on `0x8000` | bounded read of `0x0CD56` (512 B): min `0x7EDE` (−290), max `0x8682` (+1666), 23/256 cells below `0x8000`, 233 at or above; first row `80F8 811B 8153 81B9 8211 825A 82ED 8326 835A 8374 838B 8394 83AB 83B9 83BE 83FC` | the *cells* are offset-binary too |
| `0x0FEC0` axis is a mixed ladder terminating in a sentinel | bounded read (32 B): 0, 8, 16, 32, 48, 64, 96, 128, 160, 192, 216, 224, 232, 240, 248, `0xFFFF` | last entry is a sentinel, not a physical breakpoint |

**Consequence:** the `+0x8000` is not "a signed physical quantity" in the sense of a measured pressure or torque; it is the software's offset-binary storage convention, applied consistently to payload, to `FFFF1640`, and to the `FFFF1D72` stage. The centred query is therefore an **internal staged value**, not a sensor reading. Physical meaning remains unresolved.

**ROM configuration fact:** `U8[0x87C8] = 0x00`, so `bit7` is **clear**. At `0x6914A`–`0x69152` that forces `bt loc_69172`, i.e. with the shipped bytes the `FFFF1D72`-based lookup that stores `FFFF1614` (`0x5C0`) is **skipped**, and only the `FFFF1640`-based lookup storing `FFFF161A` (`0x5C6`) executes on that path. WO65293's "two stores" description is a code-path capability, not the shipped runtime behaviour.
