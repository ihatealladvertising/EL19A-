## Question

Where does the table at `FFFF A074` come from — ROM copy, runtime-built structure or mixed buffer — and what are its three fields?

## Answer

**Runtime-built, not a ROM copy.** The band is cleared by a longword zero-fill at initialisation, is absent from the ROM image entirely, has no ROM→RAM copy path, and is read through 92 base-pointer loads. The code that *populates* entries was not located; that is the stated unresolved boundary.

### 1. The RAM map marks the band as having no ROM image

Every address in `FFFFA074`-`FFFFA322` appears in the listing's RAM section as `UNDEFINED .res.b 1` — 656 such rows across the band. The band therefore has **no ROM image at those addresses**: no byte of it can be a copy of the same ROM offset, and the `REC-000010` firmware-initialised-RAM rule applies directly.

### 2. A descriptor block defines the buffer bounds

`0x00013B10` (`off_13B10`, referenced from the descriptor pairs at `0x000242E8`, `0x0002A8B4` and `0x0002AA4C`) holds the buffer geometry:

```
0x13B10  FF FF A0 74   start = FFFF A074
0x13B14  FF FF A3 23   end   = FFFF A323
0x13B18  FF FF A3 24   next structure start = FFFF A324
0x13B20  FF FF B6 1C
```

`sub_24122` (`0x024122`) and `sub_24166` (`0x024166`) both load it with `mov.l off_242E8,r6 ; h'13B10` and read `@r6` as the start pointer and `@(4,r6)` as the end pointer.

### 3. Its only located writer is a zero-fill — `sub_24166`

```
0x024166  mov.l off_242E8,r1     ; r1 = 0x13B10
0x024168  mov.l @r1,r0           ; start = FFFF A074
0x02416A  mov r0,r2
0x02416C  mov.l @(4,r1),r0       ; end = FFFF A323
0x02416E  cmp/hs r0,r2
0x024170  bt locret_2417E        ; empty range -> return
0x024172  mov #0,r6
0x024174  mov.l r6,@r2           ; *r2 = 0 (longword)
0x024176  add #4,r2
0x024178  mov.l @(4,r1),r0
0x02417A  cmp/hs r0,r2
0x02417C  bf loc_24174           ; loop until r2 >= end
```

Callers: `0x0238B4` (`bsr`, inside an initialisation path — `jsr sub_2598E`, then `mov.w @(8,PLIOR_W),r0`, then this call, then stores to `FFFFB616`) and `0x024158` (`bsr`, tail of the `sub_24122` routine). So the buffer is **zeroed during init**, not filled.

### 4. No ROM copy and no GBR writer targets the band

- A fixed-displacement census resolving every GBR base over `[FFFFA074, FFFFA2C6)` returns **0 sites**.
- The only copy helper with a located call site in this ROM is `copy_longwords_by_size` (`0x21F3C`), called once at `0x20EF0` with destination `FFFF84D4` (WO65739, `REC-000012`) — not this band.
- The band's `FF FF A0 74` literal at `0x13B10` is a descriptor, not a source address; there is no `mov.l off_X,rN` load of a ROM address whose content is copied here.

### 5. Readers

92 code sites load the base pointer with `mov.w word_…,rN ; h'FFFFA074` and index into it three bytes per entry. Two are already characterised:

- `sub_228F0` (`0x0228F0`): `r0 = UBYTE[FFFFA074 + 3*index + 1]`, returns 1 when **bit7** of that byte is set (used for entries `0xAD`/`0xAE`/`0xAF`, mirrored into `FFFF34E7` bits 6/5 — WO65892).
- `sub_8AD7C` (`0x08AD7C`): walks the entries testing **bit3** of the same byte (WO65877's setter gate).

`byte0` and `byte2` of each entry have **no located consumer** in any closed report; recording them as `UNRESOLVED` is deliberate.

### 6. Size discrepancy carried forward (not resolved here)

The descriptor bounds give `FFFFA323 - FFFFA074 = 0x2AF = 687` bytes, which is exactly **229 three-byte entries**, whereas WO65877's loop is recorded as covering **198 entries**. Both can be true (a loop may deliberately cover a subset), but the 198 figure was used to argue "all entries must have bit3 set", so the true bound matters. This is handed to WO65916 rather than resolved here.

**Conditional consequence (flagged, not claimed):** because `sub_24166` zeroes the whole buffer, every entry's byte1 is `0x00` immediately after init, so `bit3` and `bit7` are both clear for the entire buffer until some routine writes entries. Whatever populates it was not located by this WO; WO65877's "all 198 entries bit3 set" latch condition therefore cannot be satisfied on a freshly initialised unit unless a population path exists.

## Classification

**`RUNTIME-BUILT`** — a firmware initialised, non-ROM-backed buffer with a located zero-fill initialiser and 92 reader sites; population writer `UNRESOLVED`.

## Findings disposition

**NOT REQUIRED as a calibration finding, with one deferral recorded.** The buffer is not a calibration object and no inventory row or XML decision depends on it, so no FND record is raised: it is `.res.b UNDEFINED` RAM, zeroed at init, with no ROM image. The material element is the **bound/entry-count discrepancy** (687 bytes = 229 entries vs WO65877's 198), which qualifies WO65877's "all entries" reasoning. That is deferred to **WO65916** rather than deferred to a REC, because WO65877's actual loop bound must be re-read before any correction is stated — asserting 229 over 198 without reading the loop would repeat the very error `FND-000012` warns about.

## Confidence

**HIGH** that the band has no ROM image and is zeroed by `sub_24166` (both read directly: 656 `.res.b` rows, and the fill loop is fully visible with its two descriptor loads).
**HIGH** for the 92 reader sites and the two characterised bit consumers.
**MEDIUM** for "no other writer exists": the negative covers fixed-displacement GBR stores and ROM-copy helpers, but a writer reached through a pointer chain (as `sub_24166` itself is) would not be caught by either, and was not searched exhaustively.

## Reconciliation

`FND-000010`'s rule — firmware-initialised RAM must not receive a calibration definition — applies and is upheld for this band. WO65877's 198-entry figure is **qualified, not corrected**, pending WO65916. No report was edited.

## Stop boundary
