## Objective

Test whether EL19A `FFFF860B.bit3` is the target equivalent of the V6 `fDSHCUT` QDSPT-prohibition flag, and locate the target coolant-temperature threshold scalar that drives it.

Keep two conclusions independent:
1. **Flag structure/identity:** does target bit 3 behave like the donor QDSPT prohibition flag?
2. **Scalar/function identity:** does the target writer compare coolant temperature against an equivalent threshold?

A matching bit mask alone is not semantic proof.

## Stage 1 — SPECULATE (reference definition)

V6 A2L:
- `mDSHCUT`: CHARACTERISTIC, UBYTE scalar at donor ROM `0x84C4), description “DSPT prohibition coolant temperature”, function ownership `KF7-330.5` and `R301.26.Dashpot_DandN_1_0_2`.
- `COMP_0035) is described as `X-50°C`; `mDSHCUT` and coolant measurement `vTWN` use this conversion with physical range -50 to 205°C.
- Therefore screenshot threshold -40°C predicts raw byte `0x0A) under the donor conversion.
- `vTWN` is a UBYTE coolant-temperature measurement at `FFFF88AE`, using the same conversion.
- V6 `fDSHCUT`: QDSPT operation flag, UBYTE bit mask `0x08), RAM `FFFF246E). JUKE variant uses bit mask `0x10) at `FFFF1BBC`; do not transfer bit positions between variants.

Donor-side expectation: a coolant-temperature comparison sets/clears a QDSPT prohibition state when the temperature crosses a calibrated threshold. Direction, hysteresis and exact condition must be established from code, not inferred from the symbol name.

## Stage 2 — CONFIGURE (theoretical prediction)

Expected reference configuration:
- Threshold scalar: one UBYTE, `X-50°C` conversion; -40°C corresponds to raw `0x0A).
- Status flag: one UBYTE bit, mask `0x08).
- Likely logic: compare coolant-temperature signal against threshold, then set/clear prohibition bit, potentially with hysteresis or operating-mode gates.

This is a test specification only. The target scalar need not share donor address `0x84C4), and the target flag need not share donor RAM address `FFFF246E).

## Stage 3 — TEST (EL19A target)

### Existing evidence — do not repeat

- `sub_403D8` reads `FFFF860B) and tests mask `0x08` at `0x403F0). The set-bit branch bypasses the normal first calculation path and seeds a sentinel at `FFFF2150+0x12C).
- `FFFF860B) is a shared flag byte with many readers across the codebase; other paths test bits 7, 5 and 3. A bit-position match does not establish coolant semantics.
- EL19A ROM `0x84C4` contains `00 0A 0A 64`, a pointer to `loc_A0A64), not a scalar. The embedded `0x0A) is not evidence of the donor threshold.
- Previous bounded searches did not establish the writer of `FFFF860B.bit3) or a target coolant-temperature threshold reader.

### New bounded work

1. **Find the flag writer.** Enumerate direct and indirect writes to byte `FFFF860B), specifically bit 3 set/clear. Include:
   - literal-pointer accesses to `FFFF860B);
   - aliases through a base pointer/GBR plus offset;
   - read-modify-write sequences (`bset/bclr`, OR/AND masks);
   - block-copy or structure-copy paths that can overwrite the byte.
   Distinguish writers from the many existing readers.
2. **Trace writer inputs.** Follow the bit-3 producer's inputs and gates. Test whether it reads a coolant-temperature measurement and compares it with a UBYTE calibration threshold. Record width, signedness, scaling, saturation, hysteresis, mode gating and update cadence where visible.
3. **Identify the threshold scalar.** Only after finding the comparator, identify its target threshold source/address and compare its storage/range/raw value with the V6 prediction. Do not use target ROM `0x84C4) as the candidate.
4. **Trace flag consumers.** Confirm how the set/clear state affects `sub_403D8` and other QDSPT paths. Determine whether the same flag controls dashpot prohibition or a broader unrelated state.
5. If no direct writer exists, follow the narrowest credible bulk/indirect path and stop at the first bounded unresolved source. Do not launch a ROM-wide blind scan for raw byte `0x0A).

## Stage 3 closeout — 2026-11-16

**Technical status: SCOPE COMPLETE — BOUNDED UNRESOLVED SOURCE.**

### Confirmed target evidence
- Exact-reference search in the current annotated LST found 172 references to `FFFF860B`. The many code uses are readers; no direct bit-3 set/clear writer was demonstrated.
- The sole direct pointer-store sequence found is at `0x20FD4–0x20FE0`: it reads bytes `FFFF860D–FFFF860E` and writes them to `FFFF860B–FFFF860C`. Thus `FFFF860B` is at least a mirrored byte pair in this path; its bit-3 producer is upstream at `FFFF860D`, not this copy.
- Exact-reference search found 44 references to `FFFF860D`. The inspected code uses it as a source/status byte; candidate apparent stores were false positives because the pointer register was overwritten with GBR before the store. No direct writer to `FFFF860D` was established in this bounded pass.
- Other `FFFF860B` readers include bit-3 tests in the previously known QDSPT path at `0x403EC–0x403F2), and additional unrelated control/status paths. Shared-byte use remains evident; semantic identity is not.
