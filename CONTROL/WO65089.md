## Objective

Trace selected high-priority 3D maps and 32-point UWORD curves from their actual caller-side query construction through lookup return, immediate arithmetic/storage, and the first direct downstream consumer. Establish the software role of each path from code behavior, not from donor labels, raw value morphology, or informal candidate names.

### Selected 3D map families

1. **Mode-selected 8×8 UBYTE pair:** `0x0A342` / `0x0A382`, same explicit UBYTE axes `0x0DFF2` / `0x0DFFA`, `sub_22C38` call at `0x37BF8`; map pointer selected by `FFFF85FB.bit7`. Determine both query sources and branch outcomes, return width, caller-side conversion and first consumer. The existing `candidate_register` filename/label is only a search lead, not a confirmed semantic name.
2. **Centered 16×16 UWORD map:** `0x0D8D6`, `sub_22AFC` call at `0x5C28E`. Reconstruct the two caller queries, axis/search contract as used at this site, signed-centering operation (existing catalogue reports a `0x8000` offset), result destination and first consumer. Do not infer signed storage unless the code demonstrates it.
3. **Inline 8×8 SWORD bank:** `0x0B422`, `0x0B4A2`, `0x0B522`, `0x0B5A2`, direct indexed reads in `0x96C36–0x96C7E`. Establish index sources/ranges, each map's actual indexed result, shared/different destination fields, branch alternatives, and the immediate consumer(s). Do not call the four maps one semantic surface unless dataflow proves a common role.

### Selected 32-point UWORD curve families

1. **Bidirectional pair:** `0x0F712` / `0x10F8A`; relevant direct calls include `0x37398` and `0x648D8`. Reconstruct each direction and determine whether one is an inverse/forward conversion, how the axis/table argument roles switch, where each result is stored, and the first direct consumer.
2. **Paired curve group:** `0x10EEA` / `0x1100A`; inspect normal-bank call context(s), including the `0x6904A` path, and establish whether the pair is used as an axis/data pair or in a different arrangement.
3. **Paired curve group:** `0x10F2A` / `0x1104A`; inspect normal-bank call context(s), including `0x69058` and `0x68ACA`, and trace the selected result to its first direct consumer.

Trustful mirror placements listed in WO65060 may be used only where the selected caller itself passes them or an exact shared result path requires comparison. Do not repeat WO65060/WO65080's byte-identical mirror census.

## Scope and method

1. Reconfirm ROM/LST hashes and verify the specific caller, pointer-pool and target instruction bytes against ROM.
2. For every selected lookup call, record the enclosing function, exact call PC and delay slot, incoming arguments, effective ROM pointer/axis roles, query-source addresses and widths, and all relevant branch/gate predicates.
3. For each helper return, establish returned register, width/signedness/extension, scaling or centering arithmetic, clamps/saturation, and exact RAM destination(s).
4. Trace each direct RAM result through the shortest supported local consumer path: direct read(s), arithmetic/weighting, branch/decision, additional lookup, output/staging field, or the first explicit unresolved boundary.
5. Distinguish related objects: paired axes vs curves, two inverse lookup directions vs independent mappings, mode-selected maps vs simultaneous alternatives, and four inline map values vs a shared bank operation. Keep every physical ROM placement distinct.
6. Identify the caller's observable software role where the chain supports it. Functional confidence and physical-domain confidence must be separate. Do not use the labels “fuel”, “MAF”, “flow”, “torque”, “ignition”, “knock”, “dwell”, or “candidate_register” as conclusions without code-path support.
7. Keep helper-internal logic to the minimum needed to interpret the caller contract. Stop at the first unsupported pointer/index, call-preservation, indirect/global consumer, peripheral/DMA, or runtime boundary.

## Acceptance criteria

- Every selected map/curve group has a documented callsite and verified effective ROM arguments.
- Query sources are distinguished from axes and from returned values; units/scales remain unknown unless proven by arithmetic or another direct calibration reference.
- Each output destination and its first direct consumer are identified, or the exact unresolved stop boundary is stated.
- Branch/gate conditions and SH-2 delay-slot effects are retained; no path is inferred from fall-through across a return/call boundary.
- The semantic/software-role assessment is based on direct caller behavior and independent evidence, with separate confidence for structure, software role, and physical calibration identity.
- Corrections to WO65060 catalogue descriptions or inherited candidate terminology are recorded explicitly without modifying the catalogue.
- The result identifies which of these candidates now have a supportable software-role label, which remain generic, and the next highest-payoff investigation (maximum three items).
