# WO65239 — Calibration Query-Variable to Diagnostic Symbol Join

**Status:** ASSIGNED — WORKER 1 — READY

## Objective

Determine which catalogue tables are queried by RAM variables that already have a named diagnostic identity in the Consult-II Mode $22 CID map, OBD Mode $01 PID map, or bounded DTC crosswalk.

The test is falsifiable:

> If a table's actual reader query is the same runtime RAM value exposed by a diagnostic PID/CID or used by a named DTC monitor, the reader/caller query lineage and diagnostic source record must resolve to the same effective RAM cell or to a fully explained identical derivation, including width, byte lane, signedness and scaling. If they do not, reject the proposed alias.

Produce a row-level join with explicit confidence and unresolved cases. This is not a repeat of WO65173.

## Critical prior-work boundary

WO65173 is **CLOSED — BOUNDED COMPLETE**. It joined all 259 Consult-II CIDs to the RAM byte/bit xref, catalogue consumer summary and OBD Mode $01 map:
- 75 direct joins, 166 partial joins, 2 ambiguous/not-RAM-comparable, 16 unresolved-no-xref;
- OBD joins there were limited to explicit RAM-source address tokens;
- catalogue joins were address-token overlaps in query/destination/downstream summary fields;
- no new ROM/LST trace was performed.

This WO must instead join each catalogue row's **actual reader query argument and caller-supplied query value** to the diagnostic map's **source RAM cell**. Do not reproduce the 259-row CID join, RAM xref join, or generic catalogue address-overlap logic.

## Required method

1. Build the candidate set from the 179 catalogue rows. For each row, identify its specific reader, caller(s), and actual query argument(s). Use existing report anchors and catalogue metadata; do not re-run helper or table censuses.
2. Resolve each query to its effective RAM address/value only where existing reader/caller evidence supports it. Record direct memory operands, pointer indirection, register/stack provenance, field offset, width, signedness, and any shift/mask/arithmetic that changes the query.
3. Join that query cell against the OBD Mode $01 source fields and Consult CID ptr1/ptr2 fields. Keep DTC monitor names separate: a DTC slot is a diagnostic test identity, not automatically a sensor/PID name.
4. For each match, record whether it is an exact same-cell input, an identical derived value, a different-width/byte-lane view, an output/consumer-only overlap, or merely adjacent/partial.
5. State how many of the 179 rows have a proven query address, a direct diagnostic source match, a derived match, no match, or insufficient provenance. Include representative positives and the strongest negative/disconfirming examples.
6. Reconcile any overlap with WO65173 without changing that report. If a prior row was joined only because a destination or downstream address matched, retain that as consumer evidence, not query identity.

## Output schema

The report must include a compact row-level table with at least:
- EL19A table address, geometry/storage, reader and caller;
- query expression and effective RAM cell (or unresolved provenance);
- query width/byte lane/signedness and applied scaling/operations;
- matching Mode $01 PID, Consult CID, or DTC monitor source and its documented source cell;
- match class, evidence anchors and confidence;
- explicit disconfirmers or missing link.

Keep diagnostic display labels distinct from confirmed physical calibration meaning. A direct same-cell match supports a diagnostic-variable alias; it does not by itself prove the table's physical control function.
