## 1. Objective and result

For the single-byte (`size=1`) rows in `EVIDENCE/EL19A_scalar_alignment.tsv`, do the inferred EL19A bytes match the pinned Juke reconstructed-ROM bytes at the named Juke A2L address, and are the TSV `el19a_value`/`donor_value` columns faithful to those bytes?

**Result: HYPOTHESIS SUPPORTED — `mixed`.** Of 2,025 single-byte rows, 745 are `byte-exact` (target byte equals Juke byte at the named address and both value columns equal that byte), 156 are `coordinate-mixed` (bytes agree but `donor_value` disagrees), 560 are `byte-mismatch` (target and Juke bytes differ) and 564 are `unresolved` (no Juke symbol/address, so no donor byte claimed). The TSV `el19a_value` column is faithful to the pinned EL19A target byte in 2,025/2,025 rows; the `donor_value` column is faithful to the Juke byte in only 880/1,461 Juke-resolvable rows. As in WO65827, a real byte-exact subset exists but is outnumbered by mismatch/unresolved rows, so the width class is `mixed` rather than uniformly useful. Structural/address confidence only advanced; no semantic promotion.

- **Identity layer advanced:** structural/address confidence only; no input, function, output or physical identity is promoted.
- **Hypothesis:** single-byte rows are predominantly byte-exact and value-faithful at both coordinates, with a smaller artifact subset caused by the same coordinate/provenance mixing demonstrated at multi-byte width in WO65827.
- **Evidence:** WO65815's reproduced 2,696-row TSV and non-uniform `donor_value` warning; WO65827's 671-row multi-byte result; WO65213's A2L-to-reconstructed-ROM mapping.
- **Prediction:** classify `byte-exact` only when target byte equals donor byte and both value columns equal that byte; `coordinate-mixed` when bytes match but a value column disagrees; `byte-mismatch` when bytes differ; `unresolved` when no Juke symbol/address exists. A `mixed` result requires at least one row in each of `byte-exact` and `coordinate-mixed`/`byte-mismatch`.
- **Cheap discriminator:** bounded row-by-row comparison of only `size=1` rows against pinned ROM bytes and A2L declarations; no global alignment rerun and no broad ROM sweep.
- **Result:** **SUPPORTED — `mixed`.** All four classes are non-empty, satisfying the pre-registered support condition. The "predominantly byte-exact" phrasing holds only among Juke-resolved rows (745/1,461 = 51.0%); across all 2,025 rows the largest single class is `unresolved` (564, 27.9%). `byte-faithful` is rejected because 716 resolved rows are `coordinate-mixed`/`byte-mismatch`; `artifact-dominated` is rejected for the same reason WO65827 rejected it — a real byte-exact subset exists and `unresolved` is an absence-of-coordinate class, not an artifact.
