## Question

WO65907 found exactly one access to `U16[FFFFB552]` — the 16-bit read at `0x032E8E` — and no store. Does a producer exist at all, or is the cell read-only and permanently zero?

## Answer — the producer exists: a register-indirect indexed store at `0x074B82`

**Verdict: `PRODUCED`.** `sub_74A78` (`0x074A78`) stores a **ROM constant into `FFFFB552`** as part of a block initialisation of the `FFFFB4A8` structure.

```
0x074A86  mov.w word_74BCA,r0 ; h'FFFFA378
0x074A88  ldc   r0,gbr                       gbr = FFFFA378
0x074A8A  mov.w word_74BCC,r10 ; h'FFFFB4A8  r10 = FFFFB4A8   (base for the whole routine)
...
0x074B4E  mov.l off_74C14,r6 ; h'9170        r6 = 0x9170  (ROM)
0x074B7A  mov   #unk_FFFFFFAA,r0             r0 = 0xAA as a SIGNED byte
0x074B7C  mov.w @r6,r2                       r2 = U16[0x9170]
0x074B7E  extu.b r0,r0                       r0 = 0x00AA   <-- the displacement only becomes 0xAA here
0x074B80  mov.l off_74C18,r6 ; h'916C
0x074B82  mov.w r2,@(r0,r10)                 U16[FFFFB4A8+0xAA] = U16[FFFFB552] <- U16[0x9170]
0x074B84  mov   #unk_FFFFFFA8,r0             r0 = 0xA8
0x074B86  mov.w @r6,r2                       r2 = U16[0x916C]
0x074B88  extu.b r0,r0
0x074B8A  mov.l off_74C1C,r6 ; h'FFFF34C1
0x074B8C  mov.w r2,@(r0,r10)                 U16[FFFFB4A8+0xA8] = U16[FFFFB550] <- U16[0x916C]
```

ROM content at those sources (`0000916C 03 70 00 00 .data.l h'3700000`; `00009170 00 50 02 44 …`):

| Cell | Source | ROM value |
|---|---|---|
| `FFFFB550` (`+0xA8`) | `U16[0x916C]` | `0x0370` |
| `FFFFB552` (`+0xAA`) | `U16[0x9170]` | **`0x0050`** |

The same routine seeds neighbouring fields of the same structure with fixed defaults (`0xFFFF` at `+0x80`, `+0x82`, `+0x86`; `0xFF` at `+0xA6`; `0x7FFF`/`0x8000` into `FFFFA378`-based cells at `0x074B44`-`0x074B50`), so `FFFFB552` is one member of an initial-value block, not a computed result.

**Caller:** `0x028910` `jsr @r2 ; sub_74A78` (pointer-table entry at `0x028AD0`), inside the `0x0288xx`-`0x0289xx` initialiser band that WO65919's scope already named as part of the `FFFFB4A8` family.

**Consequence for consumers:** the field the `0x032E8E` read forwards into the five-byte `sub_32790` message is a **static ROM default of `0x0050`**, not a measurement. Every consumer must treat it as a fixed initial value; no located writer updates it from a computed or measured source. (This is the positive form of the WO's "constant zero" branch: the constant is `0x0050`, not `0x00`.)

## Why WO65907's census missed it

Three independent reasons, all of them the documented FND-000010 / FND-000012 blind spots:

1. **It is not a displacement store.** The address is `base register + 0xAA` (`@(r0,r10)` with `r10 = FFFFB4A8`), so a fixed-displacement `@(h'AA,gbr)` scan cannot see it — the same class of miss as WO65907's own `FFFFB552` read, which sits at `@(h'AA,gbr)` but reads a *different* base.
2. **The displacement is built by `extu.b`.** `mov #unk_FFFFFFAA,r0` assembles the byte `0xAA`, which the disassembler prints as a negative constant; only the `extu.b r0,r0` at `0x074B7E` turns it into the positive index `0xAA`. A reader that stops at the `mov` sees `-0x56` and discards the site.
3. **WO65907's search was for the cell, not for the base.** `FFFFB552` has no absolute literal anywhere in ROM, so the only way in is through a `FFFFB4A8` base register.
