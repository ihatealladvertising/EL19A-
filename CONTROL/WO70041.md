## 6. Bounded question 4 — implemented capabilities vs gaps

### 6.1 Implemented (with anchors)

- Address-space separation ROM vs RAM, RAM canonicalisation and a strict target grammar (§3.1).
- Literal-pool load resolution and pointer→dereference promotion with load-PC provenance (§3.2).
- GBR base tracking through `ldc`, loss at calls/returns, and one hand-written callee summary (§3.3).
- Linear register value + provenance tracking with label-level merge of identical states (§3.3).
- All common SH-2 load/store forms with direction, width and displacement (§3.4).
- PC/ROM byte concordance gating of every emitted row, with explicit unresolved reasons (§3.5).
- Full run identity header (ROM/listing/targets hashes, version, method limits, concordance) (§3.5).
- Deterministic graph serialisation, atomic write, and a strict graph contract with explicit
  unresolved-boundary and semantic-withholding rules (§3.5).
- In `build_static_indices.py`: catalogue-address-driven detection of inline table reads
  (`368-383`) and of helper calls where R4 matches a catalogue address (`385-391`), plus a bounded
  result taint `(table_addr, call_pc)` propagated through `mov`, `extu`/`exts`, `add`, `sub` and
  the group-4 shifts (`400-519`).

### 6.2 Gaps and heuristics (labelled, never silently trusted)

- **No control-flow graph.** A single linear pass in listing order with label-keyed state merging.
  There is no loop iteration, no back-edge fixpoint, no dominance and no path enumeration; merging
  requires exact agreement, otherwise the value is dropped.
- **Delay slots are approximated, not modelled.** The slot instruction is processed as an ordinary
  instruction and the branch state is applied at the end of the slot (`695-744`); a delay slot that
  writes a branch-relevant register is folded into the state captured at the branch, and
  `last_instruction_falls_through` is derived from the branch type (`741-744`), not from the actual
  successor.
- **Call effects are almost entirely unknown.** Only `sub_22E10` has a hard-coded summary
  (`700-713`: R0–R7 clobbered; GBR and R8–R14 preserved). Every other call wipes all registers,
  provenance, pointer tracking and GBR (`710-712`), so a table read whose base was set before a call
  becomes `UNRESOLVED` rather than wrong — safe, but very lossy.
- **Query/axis transforms are not reconstructed.** The indexer propagates only `add`/`sub`;
  `build_static_indices.py` propagates only the shift set at `460-467`. Query capture is a
  fixed-window heuristic: `reg_mem_src[5]`/`[6]` sampled at the delay slot after the call
  (`496-511`) with TTL counters 22/28/32 (`364`, `382`, `511`) — proximity, not dataflow.
- **Result-to-consumer linkage is heuristic.** The first tainted store is attributed exactly
  (`358-363`), but when no tainted store appears within the TTL the **first RAM write at all** is
  recorded as a `near` (non-tainted) destination (`364-366`) and still printed in the summary
  (`577-581`). Consumer conclusions drawn from a `near` row are leads only.
- **Two independent decoders.** `rom_access_indexer.run_indexer` and
  `build_static_indices.full_rom_analysis` each implement the same instruction families (848-line
  and 297-line passes) and already disagree: the indexer does not propagate group-4 shifts, the
  second tool does; the second tool has no pointer-promotion or unresolved-file concept. Mixing
  both in one consumer is a correctness risk.
- **Source/profile pinning is not parameterised.** ROM MD5, listing member and listing SHA-256 are
  module constants (`rom_access_indexer.py:16-18`, `build_static_indices.py:28-29`) checked before
  any work (`177-187`, `663-668`). Non-EL19A inputs cannot be analysed; the
  `tempfile`-and-restore-constant pattern in the tests is the only escape hatch and is test-only.
  `build_static_indices.run_wo65115_validation` also hard-codes POSIX `/tmp/...` paths (`113-115`).
- **Unusual lookup geometry is declared, not computed.** The indexer knows only the `sub_22E10`
  fixed-grid UBYTE convention (note text, `171`); grid step, point count, clamp and search behaviour
  are not modelled anywhere. `reader_trace_graph.py` carries an `axis_model` (`209-226`) and warns
  on an endpoint conflict, but evaluates no interpolation.
- **No data-model conformance.** Neither tool emits the `sh705x-datamodel-v1.0.0` envelope
  (`CONTROL/SH705X_DATA_MODEL_SPEC.md`); outputs are fixed positional tuples
  (`rom_access_indexer.py:442`, `452`) and TSV headers. There is no `run_id`, `deterministic_id`,
  `artifact_id`, file-offset vs EA distinction or duplicate-symbol identity, and the `# Run date:`
  header (`798`) defeats byte-determinism.
- **Two address text formats.** `parse_targets` emits `0x%X` (`82`) while `fmt_addr` emits `0x%05X`
  (`62`): one address, two canonical spellings across the two tools.
- **Minor dead code.** `full_rom_analysis(code_lines, rom, catalog_rows, mmio_addrs)` never uses
  `mmio_addrs`, and `main` passes `set()` (`225`, `683`).

## 7. Bounded question 5 — narrowest recommended adapter boundary

Recommendation: **one read-only evidence adapter plus direct reuse of the graph contract.** Do not
copy, fork or re-implement the SH-2 decoder, and do not let the Reader Trace engine acquire its own
instruction table.

1. **Static access provider** — wrap `rom_access_indexer.run_indexer`
   (`rom_access_indexer.py:175-826`) as the single decoder of record. The adapter takes
   `(rom_path, listing_path, targets, profile)`, performs the profile gate itself, and returns the
   existing 11-field resolved rows, 12-field unresolved rows and concordance metrics unchanged,
   with the declared `METHOD_LIMITS` string (`20`) travelling with the result. Pinned EL19A identity
   is the only supported profile today; any other profile must return an explicit
   `unavailable: pinned-profile-only` status rather than silently reusing EL19A constants.
2. **Reader-observation enricher** — wrap `build_static_indices.full_rom_analysis` (`225-521`) only
   for what it uniquely provides (per-call reader sites, query operand samples, destination stores,
   downstream readers). Call it with an empty semantics map: `build_semantics_map` (`158-222`) is
   EL19A OBD/Consult calibration knowledge and must not be pulled into a graph adapter. Destination
   rows flagged `near` (`364-366`) must emit edge basis `heuristic`; only `taint` rows may be
   `direct_observation`, and only when the same access also passed PC concordance.
3. **Graph contract** — call `reader_trace_graph.validate_trace_graph`, `canonical_json`,
   `trace_sha256` and `write_trace_graph` (`248-276`) directly. No wrapper is warranted: this module
   already *is* the boundary, and it correctly forces unresolved states to be declared (`193-207`)
   and withholds promotion when physical identity is unresolved (`243-244`).
4. **One shared address normaliser.** Adopt `fmt_addr`'s spelling (`0x%05X` ROM, `FFFF%04X` RAM,
   `build_static_indices.py:59-62`) because it is width-stable and consistent with keeping
   file-offset/EA/RAM distinct; `parse_targets` is the outlier. Unify once, in a separately
   authorised implementation WO, not inside the adapter.
5. **Boundary rule that keeps the graph honest.** `direct_observation` requires (a) PC/ROM byte
   concordance, (b) a profile-identity match and (c) an exactly tracked register or pointer
   provenance. Everything from the TTL fallback, the label-merge heuristic, the R8–R14 retention
   rule and the `sub_22E10` callee summary is `heuristic` at best; any unknown base must remain an
   `unresolved_boundary` with its `required_evidence`, never a silent omission.

Narrowest acceptable first step: items 1 and 3 only — resolved/unresolved access rows plus a
validated graph, with neither tool's decode logic touched, and the enricher (item 2) deferred until a
consumer actually needs per-call query/destination evidence.

## 8. Limitations of this audit

- Static reading only. No test suite was executed and no ROM/listing was supplied, so no runtime
  behaviour is claimed beyond what the source states: pass/fail status of the 44 tests is **not**
  asserted here.
- Line anchors refer to the pinned blob hashes in §2 and will drift if those files change.
- Instruction-family attribution follows the files' own decode branches and comments. Where listing
  comment text drives a decision (e.g. `sub_22E10`), the dependency is reported, not a correctness
  claim about the disassembly.
- Only the seven named files were read. Other tools (scanner, workbench, diagnostic rosetta) were
  deliberately not inspected even where the integration plan references them.
