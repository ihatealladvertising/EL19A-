## Bounded findings / closeout — 2026-11-17

### Direct access and copy results
- In the current Library LST `EL19A_Complete_Disassembly_ANNOTATED_V3_NEXT6_16_ALL_PENDING_ANNOTATIONS.lst`, the sole direct code reference to `FFFF85FC` is at `0x20BA8`; `0x20BAC` stores one byte read from `FFFF85FB` into `FFFF85FC`. This is not a complete longword vector write.
- The `sub_20DCE` state-copy sequence at `0x20FA0–0x20FB2` reads `FFFF85FE` and writes that byte to `FFFF85FD` at `0x20FB2`. It does not write `FFFF85FE` itself.
- At `0x20FB4–0x20FBE`, `sub_2245C` is called with source `FFFF8602`, destination `FFFF85FF`, and count 3; therefore bytes `FFFF8602–FFFF8604` are copied to `FFFF85FF–FFFF8601`. This supplies only the final byte of the candidate vector slot at `FFFF85FF`.
- The LST's only direct `FFFF85FE` code reference is its use as the source byte at `0x20FAE`; no direct store to `FFFF85FE` appears in the exact-literal matches. `FFFF85FD` is also read at `0x54328`, where bit7 is tested. `FFFF85FB` is read at `0x37BE4`, where bit7 is tested.
- The XREF CSV exact text searches for `85FD` and `85FE` returned no rows. This is corroborative only; it does not exclude indirect/indexed aliases or bulk/descriptor writes.
- The RAM-map listing renders `FFFF85F8–FFFF8601` as undefined/reserved bytes; that display is not evidence of their runtime initialization values.

### Conclusion
- **No complete runtime vector longword at `FFFF85FC–FFFF85FF` is established.** Observed byte operations are fragmented: `85FB→85FC`, `85FE→85FD`, and `8602→85FF`; `85FE` itself has no direct writer in the inspected literal-reference set. The byte at `85FE` therefore remains unresolved.
- The fragments occur in different routines/contexts; their execution order relative to TRAPA site `0x157E` is not established. No handler destination or link to `INT_TRAPA62` can be claimed.
- The reads of bit7 from `85FB` and `85FD` are consistent with nearby status-byte use, but do not prove the slot is not used as a vector under a special runtime state.
- **Stop condition met:** bounded direct-literal and identified copy-path audit found no complete vector. Indirect aliases, computed writes, unrepresented bulk/DMA/peripheral initialization, and live runtime values remain outside this pass. Do not infer fault/recovery behavior.

## Checkpoint 2 — alias-resolved slot fields and bounded handler disposition (2026-11-20)

### Source and method

- Source listing: `EL19A_Complete_Disassembly_ANNOTATED_V3_NEXT6_16_ALL_PENDING_ANNOTATIONS.lst`, 27,045,080 bytes; MD5 `99635224d16ab7705445e27bf233e549` (same read-only source identity used by WO65062/WO65063).

### A. Slot byte 0 (`FFFF85FC`) is copied status/data

- `sub_209A6` is called by `INT_ATU31_IMI3A` (`0x20854`); its local callback-loop path reaches `0x20B9C–0x20BAC`.
- `0x20B9C` loads pointer `R6=FFFF85FB`; `0x20BA6` reads `UBYTE[FFFF85FB]`; `0x20BA8` loads `R6=FFFF85FC`; `0x20BAC` stores that byte at `FFFF85FC`.
- The source byte `FFFF85FB` is itself modified in `sub_3723C`: base `R6/R2=FFFF85F4` and `0x3794A` stores at base+7=`FFFF85FB`. Its preceding paths form the byte by preserving or toggling bit7 (`OR #0x80` at `0x37940`, or `AND #0x7F` at `0x37944`).
- In the same `sub_3723C` sequence, `0x3794C–0x37964` reads/tests bit7 of both `FFFF85FB` and base+8=`FFFF85FC`, compares the two boolean states, and on mismatch sets bit5 in a separate byte at `@(1,R12)`. This is positive evidence that `FFFF85FC` is consumed as a status byte, not as an opaque 32-bit function pointer, in this path.

### B. Slot byte 1 (`FFFF85FD`) mirrors byte 2 (`FFFF85FE`)

- `sub_20DCE` is the state-update routine called by `INT_TRAPA62` (entry relationship documented in the source listing and earlier WO records).
- At `0x20FA8` it loads `R4=FFFF85FE`; `0x20FAE` reads `UBYTE[FFFF85FE]`; `0x20FAC` loads `R6=FFFF85FD`; `0x20FB2` writes that byte to `FFFF85FD`.
- `sub_3723C` also updates byte 2 directly: base `R5/R2=FFFF85F4` at `0x37732/0x3774C/0x37758`; `0x37738` reads base+0x0A=`FFFF85FE`; `0x3775A` writes back to base+0x0A. The branch paths change only bit7 (OR `0x80` at `0x37756`, or AND `0x7F` in the delay slot at `0x37750`), preserving the lower seven bits.
- `sub_3723C` is called at `0x371AA` from `loc_3719C`; a ROM pointer datum at `0x217E8` points to `loc_3719C`. The external scheduler/caller and its execution ordering versus `INT_TRAPA62` or the custom TRAPA path are not established.

### C. Slot byte 3 (`FFFF85FF`) is the head of a RAM block copy

- At `0x20FB4` R2 is loaded with destination `FFFF85FF`; `0x20FBA` supplies source `FFFF8602`, `0x20FBC` sets R1 to the destination `FFFF85FF`, and `0x20FBE` calls `sub_2245C` with length 3 in R0's delay slot. This copies `FFFF8602–FFFF8604` to `FFFF85FF–FFFF8601`.
- The preceding `0x20FB6` call copies three bytes from `FFFF85FF–FFFF8601` to `FFFF8605–FFFF8607`. Both are block-data movements, not a demonstrated handler-pointer installation.

### D. Combined interpretation and relationship to TRAPA site `0x157E`

- Reset initialization still establishes `FFFF85FC–FFFF85FF = 00 00 26 4C` before later writes, via the `sub_275C` 232-entry U32 fill documented in WO65062 Checkpoint 9.
- Later code has now positively established multiple byte-level state operations over all four slot bytes: `85FB→85FC` (`0x20BAC`), `85FE→85FD` (`0x20FB2`), conditional bit7 changes in `85FB` (`0x3794A`) and `85FE` (`0x3775A`), a bit7 comparison that reads `85FC` (`0x37958`), and a 3-byte block copy `8602→85FF` (`0x20FBE`).
- These sources describe a mutable, multi-field RAM record/snapshot that numerically overlaps the RAM TRAPA #0x3E vector slot. The operations do **not** provide one atomic or stable 32-bit handler installation. Because the source bytes and execution ordering are runtime/state dependent, they cannot be combined into a single proven value at the `0x157E` instant.
- `loc_154E` still explicitly sets `VBR=FFFF8504` at `0x157C` and executes `TRAPA #0x3E` at `0x157E`, selecting `FFFF85FC`. The local guard remains `sub_33FE()` result `0x40` plus `FFFF83D3==2`. No observed path in this bounded pass proves that the relevant field copies occur before or after this guarded TRAPA, nor establishes the live contents of the slot at that instant.
- The reset default `0x0000264C` points to `Poweron_Reset`, whose observed epilogue at `0x26D2` is RTS rather than RTE. This reset-default value is not accepted as the runtime TRAPA handler because the target slot is subsequently written as data and the timing/value at `0x157E` is not established.
