## Stage 3 — TEST results (2026-11-16)

### Reference comparison

**Juke A2L / ROM**
- Juke A2L declares `mTDSHPT` at `0x11D84) and `mTDSHPT0` at `0x11D94), each 16-point `REC_UBYTE_C), fixed 0–6000 RPM axis at 400 RPM/point, and data conversion raw ×2 L/min.
- Three Juke reconstructed ROMs 06/07/08 were inspected at both A2L addresses:
  - `mTDSHPT`: `00 18 18 18 14 10 0C 08 04 00 00 00 00 00 00 00` in all three.
  - `mTDSHPT0`: all 16 bytes zero in all three.
- EL19A E678 and E688 each contain `00 12 12 12 2F 2F 2F 19 03 00 00 00 00 00 00 00`. Each shares 8/16 positions with either Juke curve only because the common zero tail overlaps; the active first nine values differ. Neither is an exact Juke raw fingerprint.

**V6 A2L**
- The available `64811000p2_m.a2l` defines `mTDSHPTD` at `0xCFDA` and `mTDSHPTN` at `0xCFEA`, each a 16-point UBYTE curve; `COMP_0293` = raw ×2 L/min; fixed axis `COMP_0271_S` = raw ×400 RPM (0–6000). Both belong to `R301.26.Dashpot_DandN_1_0_2`.
- Related V6 scalar references `mDDSHPTD/N` are distinct UBYTE scalars at `0x83EB/0x83EC), `COMP_0211_S` = raw ×0.0078125 in `1/min/10`. Do not conflate these with the airflow curves or screenshot's single percentage scalar.
- Raw paired V6 HEX payload was **not** available for a fresh byte comparison in this pass. Existing project notes say target and V6 source curves differ, but that prior comparison was not independently revalidated here. Keep V6 raw payload equality UNTESTED in this checkpoint.

### Target geometry, payload and display evidence
- EL19A E678/E688 are two separate 16-byte UBYTE ROM objects and are byte-identical.
- Multiplying the target raw bytes by two yields `00 24 24 24 5E 5E 5E 32 06 00 00 00 00 00 00 00`; this matches the historical screenshot-value fingerprint recorded in the candidate inventory. This is a display/value correlation, not proof that runtime uses ×2.
- The newer target XML candidates `EL19A_RR036_PLUS_SIX_CANDIDATES_TEST_20261112.xml` and `EL19A_CF48D_BASE_TEST_20261112.xml` use a static **Raw Query Index** axis `0,16,...,240`, consistent with `sub_22E10)'s actual implicit grid. They do not establish a physical RPM axis.
- An older V45/V46 workbook note says RomRaider showed an RPM display. That conflicts with the later raw-query-index definitions and is not accompanied by independent target conversion evidence. Treat the RPM display as provisional/historical, not as a verified target RPM axis.

### Query / runtime factor / output
- The E678 and E688 calls use query `q = min(UWORD[FFFF85AE] >> 1, 255)`; `FFFF85AE` is populated from the timer-capture-derived `FFFF85D6) chain. No target-proven 25-RPM-per-query-count conversion or 400-RPM axis is present in these callsites.
- In `sub_403D8`, `FFFF1676 = FFFF1054+0x622` is formed from the bounded UWORD path using `FFFF33EC`, `FFFF227C` and ROM constants `UWORD[0x92C4]=0`, `UWORD[0x924E]=0x00FF`. Under the observed UWORD path it behaves as a binary byte factor: 0 when the bounded source is zero, otherwise 0xFF. It is not a raw ×2 L/min conversion.
- Each table result is multiplied by that factor and stored as UWORD at `FFFF1054+0x39C = FFFF13F0`. Subsequent selection/arithmetic in the same routine writes UWORD at `FFFF1000+0x18 = FFFF1018` (PC `0x4057C`). Ignore the stale inline annotation at that PC claiming `FFFF1030`; the effective displacement in the instruction is `0x18`.
- Branch selection uses target state including `FFFF860B.bit3`, `FFFF85F8.bit4`, `FFFF8600.bit6), and later `FFFF1E6E+5.bit7` / `FFFF860F.bit3`. Their specific named modes are not proven. The routine also reads paired ROM scalars `0x848A/0x848B` (both currently raw `0x43`) in the associated QDSPT calculation; do not automatically assign Drive/Neutral labels.
- Furthest supported endpoint from this bounded pass is the internal UWORD result `FFFF1018`. A physical airflow, RPM, throttle-angle or actuator endpoint is not established.
