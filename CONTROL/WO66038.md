## Question

Are the U16 vector at `0xFC40` and byte sequence at `0x83B6–0x83BD` genuine coolant-temperature axes/parameters, and does either participate in the same target-side temperature path?

## Why it has value

The user supplied the following candidate sequences:

- `0xFC40–0xFC4F`, 8 U16 BE values: `[50, 55, 60, 65, 70, 75, 80, 90]`.
- `0x83B6–0x83BD`, 8 UBYTE values: `[6, 10, 20, 24, 40, 75, 80, 110]`.

The byte sequence admits a possible raw-minus-40 temperature interpretation, yielding `[-34, -30, -20, -16, 0, 35, 40, 70] °C`; this is only a hypothesis and its 70°C upper value would not span the user's reported 76°C log maximum. The U16 sequence admits a possible direct 1°C temperature axis. Neither interpretation has reader evidence at WO creation.

The existing scalar alignment file also exposes competing donor matches at this region: `mCCSLVSPF` (“Speed digital filtering parameter”) has a donor-to-target alignment row at target `0x83B6`, while `mDBBTPH` (“Gasoline mixing quantity decrease upper limit TP”) has a donor address `0x83B6` aligned to target `0x846B`. These are alignment observations, not target-side semantic proof. The exact target reader and query conversion are the discriminators.

## Falsifiable hypothesis record

- **Hypothesis:** `0xFC40` and/or `0x83B6–0x83BD` encode coolant-temperature breakpoints or temperature-dependent control parameters.
- **Evidence:** User-supplied byte/word values above; `EVIDENCE/EL19A_scalar_alignment.tsv` contains the two distinct donor-alignment observations described above; WO65239/WO65724 distinguish direct OBD and derived query cells. The project identifies `FFFF84B8` as a rescaled NTC_AN27 coolant-temperature value; it must not be conflated with an unscaled OBD raw byte.
- **Prediction:** A temperature interpretation requires a decoded target reader and a query sourced from `FFFF84B8` or a fully traced temperature conversion, with the exact arithmetic, signedness and units consistent with the proposed breakpoints/values. A different query source or unrelated consumer weakens or rejects the temperature claim.
- **Cheap discriminator:** For each exact candidate, resolve only its code references, reader argument role and query source. For `0x83B6`, separately determine whether the bytes are actually consumed as a vector or as one/more scalar fields. Check the first result consumer; no donor-wide comparison.
- **Result:** UNRUN. Worker must mark supported, weakened, rejected or unresolved from the target trace.
- **Information gain:** Distinguishes a real temperature axis/parameter from a speed-filter or fuel/TP donor-address coincidence, and tests whether the two candidate regions belong to one function or unrelated objects.
