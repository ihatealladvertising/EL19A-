## Question

At `0x0A19AC`-`0x0A19B8` a routine clears a bit, sets bit5 with `or.b #h'20, @(r0,gbr)`, then reads `@(h'34,gbr)` and tests bit0. What is the target byte, what triggers the write, and does the resulting bit5 feed a named output?

## Answer on the address first (the premise needed correcting)

The `@(r0,gbr)` operations do **not** use offset `0x34`. At `0x0A1988` the routine loads `mov #unk_FFFFFFAA, r7` and `extu.b r7,r7` → r7 = `0xAA`; `0x0A1992` moves it to r0, and `0x0A19B4`/`0x0A19B6` reuse that same r0. The function is `sub_A14F0` (`0x0A14F0`), whose GBR base is `FFFF34B3` (`off_A1744` = `FF FF 34 B3` at `0x0A1744`, loaded at `0x0A14F8`).

- Write target: `FFFF34B3 + 0xAA` = **`FFFF355D`** (bit4 cleared at `0x0A19AC`, bit6 cleared at `0x0A19B4`, bit5 set at `0x0A19B6`).
- The adjacent read at `0x0A19B8` is `@(h'34,gbr)` = **`FFFF34E7`**, not `FFFF34E4` as recorded in WO65865 (that entry used the wrong function's base — WO65865's own 400-line window crossed an `rts` at `0x0A14A0`).

## Trigger and context

The write sits in a reset/qualification block:

```
0x0A1974..0x0A197E   read U16[FFFF2150+0xA10] and U16[0x983C], cmp/ge -> exit when below
0x0A1986..0x0A1990   clamp and rewrite U16[FFFF2150+0xA10]
0x0A1994             clear bit4 of FFFF355D
0x0A199A..0x0A19A2   clear bit5 of UBYTE[FFFF1D99+0x1C] = FFFF1DB5
0x0A19AC             clear bit4 of FFFF355D
0x0A19B0             U16[FFFF2150+0x54D] = 0
0x0A19B4/0x0A19B6    clear bit6, set bit5 of FFFF355D
0x0A19B8..0x0A19C2   read FFFF34E7.bit0 and UBYTE[FFFF34B3+0x98].bit7
0x0A19C4..0x0A19DA   U16[FFFF2150+0x16C] vs U16[FFFF84D4+0x20], call sub_9D26C, store to U16[FFFF2150+0x328]
0x0A19E8..0x0A19EA   clear bit0 of FFFF34E7
```

So bit5 is set exactly when the `FFFF2150+0xA10` counter has passed its `0x983C` threshold and the block runs to completion — a state/qualification latch in a reset path, not a value handed to a command.

## Consumers of `FFFF355D.bit5`

Two symbolic readers under the same base, both two-bit qualification ladders:

```
0x07EB14  mov.b @(0xAA,gbr),r0 / tst #h'30,r0 / bf -> else test UBYTE[FFFF34B5].bit5
0x0935C2  mov.b @(0xAA,gbr),r0 / tst #h'20,r0 / bt -> else test bit4 (0x10)
```

`FFFF355D` also appears as plain `@(h'AA,gbr)` at `0x027274`, `0x0275F8`, `0x02761C`, `0x02769A`, `0x0276A4`, `0x0278F4`, `0x0296BA` (and `mov.w` at `0x032E8E`) under bases not yet resolved — recorded as the follow-on question WO65889.

## Verdict

`FFFF355D.bit5` is set by a threshold-qualified reset block and read only through bit-mask ladders with bit4/bit6 of the same byte and bit5 of `FFFF34B5`. No torque, throttle, dashpot or actuator command is reached.

**Classification: INTERNAL STATE FLAG (reset/qualification latch, no named output).**

- **Old claim (WO65865):** `0x0A19B8` reads `FFFF34E4` under GBR = `FFFF34B0` (from `0x0A10A2`).
- **Corrected claim:** `0x0A19B8` is inside `sub_A14F0`, GBR = `FFFF34B3`, so it reads `FFFF34E7`; the same routine's `@(r0,gbr)` writes with r0 = `0xAA` target `FFFF355D`. `FFFF34E4` is referenced only in the `FFFF34C1`-based routine at `0x07DC8A`/`0x07DCE2`/`0x07DD02`.
