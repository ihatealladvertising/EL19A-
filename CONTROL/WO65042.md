## Verified mechanics

- Both callers read the same raw UBYTE query: `[FFFF84B4+4] = FFFF84B8`. No caller-side conversion or clamp is present at either F34E call.
- First caller: `loc_4F8AC`, call PC `0x4F8D2`. R13 is loaded with `FFFF84B4`; the query byte is loaded at `0x4F8CE`; R4 receives F34E at `0x4F8D0`; R14 holds `sub_22E10). The UBYTE result is zero-extended and retained in R11 (`0x4F8D4–0x4F8D6`), not directly stored to a RAM result field.
- In `loc_4F8AC`, R11 is used as a multiplicative operand at `0x4FA3C` (with the preceding `sub_22180` result in R0) and later as an upper bound at `0x4FB06–0x4FB0A`: if the candidate value in R2 exceeds F34E's result, R2 is replaced with R11. This establishes both arithmetic influence and a clamp role in the local calculation.
- Second caller: `loc_4FBC2`, call PC `0x4FC0C`. It independently loads the same raw query from `FFFF84B8` (`0x4FC0A`), passes R4=F34E (`0x4FC06`), and receives the UBYTE result in R6 (`0x4FC0E`).
- The second caller zero-extends UWORD `FFFF1054+0x2FA` (`FFFF134E`), multiplies it by the F34E result, multiplies by 100, then shifts right 14 bits (8+2+2+2). The result is capped at `0xFFFF` and stored at UWORD `FFFF1054+0x54E = FFFF15A2` (`0x4FC12–0x4FC32`).
- The same routine subsequently copies this staged UWORD from `FFFF1054+0x54E` into `FFFF1D12+0x4A` (`0x4FC90–0x4FC96`). This is a confirmed downstream RAM destination, not a physical actuator endpoint.
- The other three curves in the second caller are kept distinct: F33E feeds `FFFF1D12+0x46`; F35E feeds `FFFF1054+0x550` then `FFFF1D12+0x4C`; F36E feeds `FFFF1054+0x552` then `FFFF1D12+0x4E`.
