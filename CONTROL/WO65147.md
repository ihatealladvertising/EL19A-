### 2.1 Resolving the GBR block (the one gap in the tool output)

Five of the six relevant sites are GBR-displacement accesses and were logged `UNRESOLVED … unresolved
GBR register`. They are not genuinely unresolved: the routine that contains them installs its own
base pointer.

```
loc_37424:                              ; entry block, no global function label
00037436  4F 13        stc.l   gbr, @-r15
00037438  D0 88        mov.l   off_3765C, r0 ; h'FFFF180C
0003743A  40 1E        ldc     r0, gbr
```

`GBR = 0xFFFF180C` for the whole body `0x37424–0x379BC` (next base load is `0x379C2/0x379C4`,
`GBR = 0xFFFF1850`). Every displacement then lands on an object WO65128 named independently:

| PC | instruction | address | WO65128 object |
|---|---|---|---|
| `0x375A0` | `mov.w r0, @(h'3C,gbr)` | `FFFF1848` | `FFFF1848` ✔ |
| `0x375A8` | `mov.l r0, @(h'38,gbr)` | `FFFF1844` | `FFFF1844` ✔ |
| `0x375AA` | `mov.b @(h'D0,gbr), r0` | `FFFF18DC` | `FFFF18DC` ✔ |
| `0x37692` | `mov.w r0, @(2,gbr)` | `FFFF180E` | `FFFF180E` ✔ |
| `0x3792C` | `mov.w @(2,gbr), r0` | `FFFF180E` | `FFFF180E` ✔ |

Four independent displacements agreeing with addresses derived by a different route is the
confirmation; WO65128's `GBR` base was correct and needs no erratum.

**Tooling observation (no tool edit made, recommendation only):** the resolver attributes a
GBR-displacement site to the nearest preceding *global* function label, so a routine whose entry block
carries only a `loc_` label (`loc_37424`) falls back to the previous function (`sub_3723C`, whose own
`GBR = 0xFFFF8534` at `0x37246/0x37248`) and is reported "unresolved GBR register" even though `GBR` is
statically known at `0x37438`. Follow-up: teach the indexer to treat a `loc_` entry block that performs
`stc.l gbr / ldc r0,gbr` as a base-establishing entry.

## 3. Result — producers

### 3.1 `U8[FFFF18DC]` — one producer, one reader

**Producer (single, full-base resolution):**

```
loc_29258:
00029258  62 03        mov     r0, r2
0002925A  D5 89        mov.l   off_29480, r5 ; h'92E4
0002925C  66 03        mov     r0, r6
0002925E  E0 7C        mov     #h'7C, r0
00029260  01 24        mov.b   r2, @(r0,r1)      ; r1 = FFFF1860  →  FFFF18DC
```

* function `sub_28C36`; base register `r1 = FFFF1860` (literal load, resolver `base FFFF1860 / full`,
  non-stale), displacement `0x7C`; `0xFFFF1860 + 0x7C = 0xFFFF18DC`.
* stored value `r2` = `r0` at entry of `loc_29258`, i.e. the already-clamped return value of the
  preceding call in this block (`off_29254 = sub_22C78`, sibling entry `off_29244 = sub_22E60`;
  `r5` is loaded with ROM `0x92E4` on the same path). The byte is therefore a *post-computation*
  result, not a raw curve sample.
* no gate instruction sits between the call and the store; the enclosing block's branch entry is the
  only condition.
* **One producer and one reader in the whole ROM** (resolver: 1 write / 1 read for `FFFF18DC`).

**Reader `0x375AA` (C2 routine):**

```
000375AA  C4 D0        mov.b   @(h'D0,gbr), r0     ; U8[FFFF18DC]
000375AC  EE FF        mov     #h'FFFFFFFF, r14
000375B0  62 0C        extu.b  r0, r2
000375B2  02 67        mul.l   r6, r2              ; r6 = prior scaled result
000375B4  05 1A        sts     macl, r5
000375B6  45 09        shlr2   r5  (×3)  /  45 01 shlr r5   ; ÷128
000375BE  35 E6        cmp/hi  r14, r5             ; clamp to 0xFFFF
```

So `FFFF18DC` is a **multiplier** applied to the routine's curve result, then `>>7` with a `0xFFFF`
saturation — matching WO65128 §"`0x375CC` stores the clamped scaled product … the multiplier
`U8[FFFF18DC]` and `>>7` clamp are part of the field's value". Independent confirmation.

### 3.2 `UWORD[FFFF180E]` — two producers, one reader, self-owned counter

**Producer A — C1 seed (`sub_28C36`), full-base resolution:**

```
loc_292C4:
000292C4  DD 72        mov.l   off_29490, r13 ; h'FFFF180C
000292CE  81 D1        mov.w   r0, @(2,r13)   ; → FFFF180E
```

* literal base `r13 = FFFF180C` (`off_29490`), displacement `2` → `FFFF180E`.
* value `r0 = r6` = the clamp `min(4·N, r4)` computed at `0x292B8–0x292C2`
  (`cmp/hi r4,r5`, `mov r5,r6` / `mov r4,r6`) — exactly the `min(4·N,0xFFFF)` family WO65128 recorded
  for `FFFF180E`/`FFFF181E`/`FFFF180C`/`FFFF181C`.
* same block also writes `FFFF1840` (`0x29268`, `@(0x34,r13)`), `FFFF180E` (`0x292CE`),
  `FFFF181E` (`0x292DC`, base `FFFF181C`), `FFFF180C` (`0x292E6`, `mov.w r6,@r13`),
  `FFFF181C` (`0x292F0`).

**Producer B — C2 clear (the ordering answer):**

0003768C  E6 00        mov     #IVECT1, r6        ; r6 = 0

00037692  C1 01        mov.w   r0, @(2,gbr)      ; FFFF180E ← 0

**Reader — `0x3792C` (same routine, `GBR = FFFF180C`):**

```
loc_37922:
00037922  60 63        mov     r6, r0
00037924  81 A1        mov.w   r0, @(2,r10)       ; r10 = FFFFB2DC → FFFF B2DE  (NOT FFFF180E)
00037926  60 6D        extu.w  r6, r0
00037928  40 19        shlr8   r0
0003792A  80 A1        mov.b   r0, @(1,r10)       ; → FFFF B2DD
0003792C  C5 01        mov.w   @(2,gbr), r0       ; r0 = UWORD[FFFF180E]
0003792E  66 0D        extu.w  r0, r6
00037930  85 8C        mov.w   @(h'18,r8), r0     ; r8 = FFFF8494 → UWORD[FFFF84AC]
00037932  64 0D        extu.w  r0, r4
00037934  44 08        shll2   r4
00037936  34 62        cmp/hs  r6, r4             ; 4·UWORD[FFFF84AC] >= UWORD[FFFF180E] ?
00037938  89 03        bt      loc_37942
```

**Ordering conclusion.** Within `0x37424–0x379BC` the only two touches of `FFFF180E` are the clear at
`0x37692` (address-early) and the read at `0x3792C` (address-late). `FFFF180E` is therefore a
**routine-owned comparison word, not a C1-owned input on the C2 path**: any pass that executes both
sites overwrites the `0x292CE` seed before `0x37936` can see it, and the comparison at `0x37936` can
only ever observe `0` (seed destroyed) on such a pass. The observable C2 decision at `0x37936` is
`4·UWORD[FFFF84AC] >= UWORD[FFFF180E]`, i.e. the threshold `FFFF180E` is consumed as a value the same
routine owns.

Naming correction for the record: the counter pair `0x37924`/`0x3792A` writes `FFFFB2DE`/`FFFFB2DD`
(`r10 = FFFFB2DC`, loaded at `0x378DE` and `0x378EE`) — **not** `FFFF180E`/`FFFF180D`. WO65128 line
"the C2 routine can also write it at `0x37692`" is correct; no other `FFFF180E` write exists.

## 4. What the C2 flag outcome represents — bounded answer

The comparison at `0x37936` is a **scaled threshold test**: `4 × UWORD[FFFF84AC]` (from the
`FFFF8494` query block whose base is loaded at `0x375C4`, `word_37658 = h'FFFF8494`) against the
routine-owned word `FFFF180E`, with the branch taken when the scaled value is ≥ the word. The
"outcome" recorded at `FFFF85FB`/`FFFF85FC`/`FFFF1E40` (WO65128) is therefore the result of a
query-threshold comparison, not a direct physical measurement.

Per the WO65128 stop condition, **no physical semantics are assigned**: `FFFF18DC` is proven to be a
post-computation byte multiplier on this path only, and `FFFF180E` a routine-owned threshold word.
Their physical identity remains open and must come from a writer/axis trace of `sub_22C78` and of the
`FFFF8494` query context, not from this WO.

## 5. Residual unknowns (explicit, not silently closed)

1. **Path exhaustiveness at `0x37692`.** Whether every execution that reaches `0x3792C` passes
   through the clear at `0x37692` was not proven by exhaustive branch evaluation; the ordering
   statement in §3.2 is proven for any pass that executes both sites. If an entry/branch reaches
   `loc_37922` while skipping `loc_3768C`, the C1 seed survives and the comparison is C1-driven.
   Next discriminator: dominator check of `0x37692` over `0x3792C` inside `0x37424–0x379BC`.
2. **`sub_22C78` provenance.** The value written to `FFFF18DC` is that callee's return; its inputs,
   axis and units are not traced here (and are outside this WO's authorisation).
3. **`FFFF1860` block role.** The base `r1 = FFFF1860` is proven, but the block's ownership
   (which routine initialises it) is not established.
