## Question

Two facts did not agree: the descriptor at `0x13B10` bounds the buffer as `FFFFA074`-`FFFFA323`, i.e. 687 bytes = **229** three-byte entries (WO65904), while WO65877 records a loop over **198** entries whose all-bit3-set condition gates `FFFF34F5.bit5`. Which bound does the loop actually use, and what writes entries into the buffer after `sub_24166` zeroes it?

## Answer 1 — the bound is a compile-time immediate of 198, and 229 is the allocation capacity

The loop in `sub_8AD7C` (`0x08B330`-`0x08B360`), read instruction by instruction:

```
0x08B330  mov.w word_8B358,r5   ; r5 = h'FFFFA074      entry pointer
0x08B332  mov   #h'7C,r0                              stack slot for the pointer
0x08B334  mov   #IVECT1,r7      ; r7 = 0                "found a set bit3" flag
0x08B336  mov.l r5,@(h'7C,r15)
0x08B338  mov   #unk_FFFFFF80,r0 / 0x08B33A extu.b     r0 = 0x80 (flag slot)
0x08B33C  mov   #unk_FFFFFFC6,r6                      r6 = 0xC6
0x08B33E  mov.b r7,@(h'80,r15)
0x08B340  extu.b r6,r6          ; r6 = 198              loop counter
loc_8B342:
0x08B342  mov.b @(2,r5),r0      ; entry byte2
0x08B344  tst   #8,r0           ; bit3
0x08B346  bt    loc_8B35A       ; bit3 CLEAR -> next entry
0x08B348  mov   #unk_FFFFFF80,r0 / 0x08B34A mov #1,r7
0x08B34E  bra   loc_8B364       ; bit3 SET -> exit with r7 = 1
0x08B350  mov.b r7,@(h'80,r15)  ; (delay slot)
loc_8B35A:
0x08B35A  add   #3,r5           ; stride = 3 bytes
0x08B35C  mov   #h'7C,r0
0x08B35E  dt    r6              ; counter -= 1
0x08B360  bf/s  loc_8B342       ; loop while counter != 0
0x08B362  mov.l r5,@(h'7C,r15)  ; (delay slot)
loc_8B364:
0x08B364  extu.b r7,r7 / 0x08B366 tst r7,r7 / 0x08B368 bf loc_8B388
```

- The counter is the **immediate `0xC6` = 198** loaded at `0x08B33C` (the disassembler prints it as `unk_FFFFFFC6` because the byte has bit7 set; `extu.b` at `0x08B340` makes it 198). There is no pool word and no descriptor field: it is a firmware compile-time constant.
- Stride is 3 (`add #3,r5` at `0x08B35A`), so the evaluated range is `FFFFA074` … `FFFFA074 + 3*197 = FFFFA2C5`, i.e. entries 0-197.
- The descriptor range `FFFFA074`-`FFFFA323` is 687 bytes = 229 × 3, ending at `FFFFA322` with the next structure at `FFFFA324` (WO65904). The loop therefore covers **198 of 229** entries: the tail `FFFFA2C6`-`FFFFA322` (31 entries, 93 bytes) is never inspected by this gate.

**The same 198 appears independently in four further sweeps**, which is what settles the question — this is a firmware-wide entry count, not a loop-local quirk:

| PC range | Counter | Operation | Stride |
|---|---|---|---|
| `0x08B33C` | `#unk_FFFFFFC6` → 0xC6 = 198 | bit3 gate (this WO) | `add #3` |
| `0x07437A` | `#unk_FFFFFFC6` = 198 | clear byte1 bit2 (`and #h'FB`), byte2 bit2, byte2 bit1 | `add #3` (`0x074396`) |
| `0x075DD4` | `#unk_FFFFFFC6` = 198 | set byte2 bit2 (`or #4`) when byte2 bit4 set and byte0 < 0x28 | `add #3` |
| `0x075E9C` | `#unk_FFFFFFE5`…`extu.b` = 198 | byte0 := 0, byte1 &= 0xC2 | `add #2`/`add #1` walk (byte-wise) |
| `0x0800A2` | `#unk_FFFFFFC6` = 198 | byte1 &= 0x7F | `add #3` in the delay slot at `0x0800B0` |

**Classification of the bound: `198-ENTRY`.** 229 is the descriptor's capacity, 198 the live count; the two numbers measure different things and neither is an error. WO65877's 198 is upheld and WO65904's 229 is qualified as capacity, not count.

## Answer 2 — the populate path exists: per-entry, index-addressed flag setters

WO65904 recorded "NO SUCH PATH WAS LOCATED" for entry population. A pointer-register census over all 93 `mov.w word_…,rN ; h'FFFFA074` load sites (each followed up to 20 instructions, stopping when the base register is reloaded) found 13 store sites through an `FFFFA074`-based register. Three of them are genuine **per-entry writers**, all reached from the `0x0724xx`-`0x0728xx` diagnostic callers:

| Routine | PC | Address arithmetic | Writes |
|---|---|---|---|
| `sub_8081C` | `0x08081C`-`0x08083A` | `r5 = r4*2; r5 += r4` → `3*index`; entry = `FFFFA074 + 3*index` | **byte2 bit3 SET** (`or #8` at `0x08082E`, store `0x080830`) and **byte1 bit5 SET** (`or #h'20` at `0x080838`, store `0x08083A`); also `mov.b r2,@(h'7E,FFFFB4A8)` = `FFFFB526` := 1 |
| `sub_8085E` | `0x08085E`-`0x08087A` | identical 3-byte indexing | **byte2 bit3 SET** (`or #8` at `0x08086E`) and **byte2 bit6 SET** (`or #h'40` at `0x080878`) |
| `sub_80884` | `0x080884`-`0x08089C` | `r2 = r4*2; r2 += r4` → `3*index` | **byte2 bit4 SET** (`or #h'10` at `0x080894`) |

Callers: `0x072430`/`0x072436`, `0x072642`/`0x072648`, `0x07284A`/`0x072850`, `0x0728C6`/`0x0728DA`, `0x072B2E`/`0x072B38`, with `r4 = r14` = the monitor/test index that the same block already uses to index the pointer table at `0x13780` (`0x072424`–`0x07242A`). `sub_8081C` is called conditionally on a test-status bit7, `sub_80884` unconditionally.

The remaining ten store sites are **single-field flag ops at fixed byte offsets**, not population: `0x0718EA` (byte `+0x1C6`), `0x0786D0` and `0x078B20` (byte `+0x1F`), `0x078CBA` (`+0x1F`), `0x0830CA` (`+0x146`), `0x0952BC` (`+0x19A`), plus the four sweep loops listed above.

**No routine loads entry content from ROM or from a measured RAM source.** Byte0 is only ever compared (`0x075DE4`) or zeroed (`0x075EA2`); byte1/byte2 carry flags only. The buffer is a **status/flag table**, and `sub_24166`'s zero-fill is its initial state.

**Classification of population: `POPULATED`** — at entry-flag granularity, by index, from the diagnostic monitor path.

## Answer 3 — the `FFFF34F5.bit5` gate polarity in WO65877 is inverted

The loop's `tst #8,r0` sets T when the tested bit is **zero**, and `bt loc_8B35A` continues the loop on T. Therefore:

- an entry whose **byte2 bit3 is SET** exits the loop early with `r7 = 1`, and `bf loc_8B388` at `0x08B368` skips the body;
- the body that sets `FFFF34F5.bit5` (`mov r4,r0; or #h'20,r0; mov.b r0,@(h'34,gbr)` at `0x08B36A`-`0x08B36E`, `gbr = FFFF34C1` → `FFFF34F5`) executes **only when all 198 evaluated entries have byte2 bit3 CLEAR**.

WO65877 states the gate as "sets ... when all 198 entries of the 3-byte table at `FFFF A074` have bit3 set". The mechanics are the opposite: the latch sets when **no** entry has bit3 set. Given that `sub_8081C`/`sub_8085E` *set* bit3 as a per-entry monitor result, the latch is an "all results clear" condition — an all-clear/reset indication — not an "all tests ran" condition. See `REC-000017`.

(The saturating counter `U16[FFFFB4A8+0x116]` incremented and clamped at `0x08B372`-`0x08B380` is as WO65877 described and is not re-derived here.)

## Reconciliation (additive — WO65877 and WO65904 unedited)

- **WO65877 said:** `FFFF34F5.bit5` is set when all 198 entries of the `FFFF A074` table have bit3 set. **Corrected:** set when all 198 evaluated entries have byte2 bit3 **clear**; a single set bit3 aborts the sweep. The "198" count itself is upheld.
- **WO65904 said:** the descriptor bounds 687 bytes = 229 entries, and "AFTER `sub_24166` EVERY ENTRY BYTE1 IS 0x00 SO bit3/bit7 ARE CLEAR THROUGHOUT UNTIL A POPULATE PATH WRITES ENTRIES, AND NO SUCH PATH WAS LOCATED". **Corrected:** the live count is 198 (the descriptor's 687 bytes is capacity), the populate path is located (`sub_8081C`/`sub_8085E`/`sub_80884`), and the gate's bit3 lives in **byte2**, not byte1.
- **Confidence:** HIGH for the counter, stride, polarity and the three setter routines (each read at its PCs). **Limit:** the tail `FFFFA2C6`-`FFFFA322` is not touched by any of the five 198-entry sweeps, so whether those 31 entries exist as reserved capacity or as an unexercised extension is unresolved; and the ten single-field sites are characterised only as "not population".
