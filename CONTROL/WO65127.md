## Mandatory discrepancy audit

### 1. E904 dynamic address / GBR distinction — RESOLVED (bases unresolved)

**r13 vs GBR at 0x87C68:** The write at `0x87C68` (`mov.b r6,@(r0,r5)` where r0=r13, r5=stack[0x50]+0x5C5) uses **r13 as base**, not GBR. r13 and GBR are distinct registers; no inference between them is valid. The effective address `[r13 + stack[0x50] + 0x5C5]` is computed from dynamic caller state and cannot be statically resolved beyond this expression.

**GBR at 0x87CE0:** The flag write `or.b #8,@(r0,gbr)` where r0=h'73 targets `GBR+0x73.bit3`. Nearby literal pool references (off_87D24=FFFF1054, off_87D28=FFFF2150) suggest GBR may be FFFF1054 or FFFF2150 in this region, but no `ldc` or `stc` instruction at 0x87CE0 establishes GBR. GBR base remains unresolved.

**First consumer of GBR+0x73.bit3:** Not found in bounded search. Stop at the flag write.

### 2. E914 flag chronology and threshold — RESOLVED (chronology; GBR base unresolved)

**Chronology:** The flag is **set** at `0x882B2` (`or.b #h'10,@(r0,gbr)`, GBR+0x72.bit4) but **read/tested** at `0x880F4–0x880F8` (`mov.b @(h'72,gbr),r0` / `tst #h'10,r0` / `bt loc_880FE`). The read PC (0x880F4) is earlier than the set PC (0x882B2), so the read is a **prior-state / previous-pass gate**, not a consumer of the current write. The current write's consumer is the gate chain at `loc_880FE` on the next invocation. WO65125 correctly identified this but the register summary characterized it ambiguously; corrected here.

**GBR base:** GBR at both 0x880F4 and 0x882B2 is unresolved. Nearby literals (FFFF1054/FFFF2150) are candidates only; no `ldc`/`stc` establishes GBR at either PC. Do not assume the same base without proof.

**Threshold:** WORD[0x905C] = 0x00F0 = 240 confirmed as the compare constant at 0x88292. The pointer address (0x905C) is distinct from the dereferenced value (240), consistent with WO65125.

**First valid consumer:** The gate chain at loc_88160 (reached when GBR+0x72.bit4 is set and all gate checks pass) is the first downstream action, but it is the shared curve-processing entry point, not an E914-specific consumer.

### 3. E934 query and destination corrections — PARTIALLY RESOLVED

**0x3A06A loads r0, not r6:** Confirmed. `mov.w @(h'14,r2), r0` at 0x3A06A loads UWORD[FFFFA324+0x14] into r0, not r6. The WO65126 lead stating "query passed in r6 to sub_3A178" requires correction: r6 at the `bsr sub_3A178` call (0x3A072) comes from `mov r13,r6` at 0x39FE4 (r6=r13), then `extu.b r6,r6` at 0x3A01E (zero-extended low byte). The actual query value is caller-state-dependent; r0 from 0x3A06A is used elsewhere in sub_39FC8 (e.g., passed to sub_22F80 as axis-index base).

**sub_39FC8 entry GBR:** Set by `ldc r0, gbr` at sub_39FC8 entry from caller's r0 — unresolved from disassembly alone. WO65058's reported `GBR=FFFF86D4` could not be independently verified; the caller's r0 value is not shown in the bounded listing excerpt. Do not retain "unresolved" without checking — checked, still unresolved.

**FFFF2718 vs FFFF86EF:** `FFFF2150+0x5C8 = FFFF2718` confirmed as E934 output store at 0x3A1B4 (`mov.b r2,@(r0,r14)` where r14=FFFF2150, r0=h'5C8). `FFFF86D4+0x1B = FFFF86EF` is NOT found as a store destination in sub_39FC8 or sub_3A178. sub_22F80 results are stored at [GBR+0] and [GBR+4] (sub_39FC8 GBR, unresolved); neither equals FFFF86EF. FFFF86EF is a false association / unresolved lead.

**r14 at 0x45E18–0x45E4E:** r14 is not FFFF2150 in this context (that was sub_3A178's local). At 0x45E18 (`mov.b r2,@(r0,r14)` where r0=h'5C8), r14's value is caller-state-dependent; this writes 0 to [r14+0x5C8], likely a reset of the E934 output cell. At 0x45E4E (`mov.b @(r0,r14),r2` where r0=h'5C9), reads BYTE[r14+0x5C9] = adjacent cell. Without r14's base, these are reset/read of adjacent storage, not proven E934 semantic consumers.

### 4. Cross-path synthesis — RESOLVED

**Shared mechanics (E904/E914 only):**
- Same reader `sub_22FD8` (two callsites: 0x87C4E and 0x8822C)
- Same axis search `sub_2340C` (UWORD BE, ascending scan)
- Same interpolation `sub_231C8`
- Same multiplier cell `[r13+FFFF2150+0x28C]`
- Same cap cell `[r13+FFFF1054+0x102]`
- Same compare-then-flag pattern (compare result vs constant, set flag bit)
- Both flag bits feed a shared gate chain to `loc_88160`

**E934 is distinct:**
- Different reader `sub_22F28` (single callsite 0x3A1AA via sub_3A178)
- Different axis search `sub_233CC` (UBYTE, descending scan) vs `sub_2340C` (UWORD BE, ascending)
- Different axis width (UBYTE vs UWORD BE)
- Different query source (UWORD[FFFFA324+0x14] vs dynamic RAM / computed product)
- No flag output
- Two-stage `sub_22F80` follow-on lookup (table h'102FC, axis h'112CA), outside the 0x0E9xx calibration region

**Shared sub_231C8 alone does not prove a common calibration function.** E904/E914 are a paired software mechanism (shared reader, axis search, gate chain); E934 is a separate path sharing only the interpolation helper. All three are co-located in ROM (0x0E9xx region) but that is physical adjacency, not functional sharing.

**Catalogue/WO65058/WO64842 reconciliation:** No contradictions found requiring silent resolution. WO65058's GBR=FFFF86D4 claim for sub_39FC8 could not be verified from the listing; retained as unresolved. WO64842's field distinction (FFFF1848 vs other outputs) is preserved and not contradicted by this cluster.
