## 1. Discrepancy audit

### 1.1 E904 dynamic address / GBR distinction — CORRECTED / BOUNDED

**WO65124 statement:** store at `0x87C68` to `[r13 + stack[0x50] + 0x5C5]`; GBR base at `0x87CE0` not independently verified.

**Reconciliation:**

- **GBR base for `0x87CE0` is resolved.** `sub_86D9C` establishes `GBR = FFFF3454` at `0x86DB0/0x86DB2` (`mov.l off_86FFC,r0; ldc r0,gbr`, `off_86FFC = FFFF3454`); WO65116 records `sub_86D9C 00086D9C–00088510 established_full FFFF3454`. The E904/E914 cluster lives inside this function range (0x87C20/0x880F4/0x882B2 all < 0x88510). Therefore `GBR+0x73.bit3` at `0x87CE0` is `FFFF3454+0x73 = FFFF34C7.bit3` (structural EA), and `GBR+0x72.bit4` at `0x880F4/0x882B2` is `FFFF3454+0x72 = FFFF34C6.bit4`.
- **`r13` is not GBR.** `r13` is loaded from stack `mov.l @r15,r13` at `0x87ADA` and compared/branched at `0x87ADC,0x87AEA,0x87B02,0x87B16,0x87B24,0x87B3C,...`; it is used as a selector/index (tests for 0/1 and as base addend). It is distinct from GBR throughout this region.
- **E904 store EA at `0x87C68` is only partially resolved.** Instruction sequence: `r7 = stack[0x50]` (0x87C58), `r2 = stack[0x60]=0x5D4` (0x87C5C), `r0=r13` (0x87C5E), `r5=r7` (0x87C60), `r2 += -0xF => 0x5C5` (0x87C62), `r5 += r2` (0x87C64), `r2=r7` (0x87C66), `mov.b r6,@(r0,r5)` (0x87C68). **Proven:** byte store target is `r13 + stack[0x50] + 0x5C5`. **Not proven in this bounded pass:** the runtime value of `r13` and `stack[0x50]` at this callsite, so the absolute RAM cell is unresolved. WO65124’s dynamic-address description is correct as an expression but not an absolute address.
- **First consumer:** no absolute post-store first reader established for the dynamic E904 store within this bounded reconciliation. The store is followed by threshold math and `sub_71F74` (`0x87CDA`) then flag set; downstream of `sub_71F74` not traced. **Bounded stop.**

### 1.2 E914 flag chronology and threshold — CORRECTED

**WO65124/WO65125 statements:** flag set at `0x882B2`; WO65125 called `0x880F4` a first consumer.

**Reconciliation:**

- **Chronology correction:** `0x880F4` (`mov.b @(h'72,gbr),r0; tst #h'10,r0; bt loc_880FE`) occurs **earlier in file/order** than `0x882B2` (`or.b #h'10,@(r0,gbr)`) in the same function `sub_86D9C`. It is a **prior-state/entry gate**, not a post-write first consumer. Control reaches `loc_88160` and later the E914 computation path only when the gate passes (and other gates pass); the flag set at `0x882B2` happens after E914 compare succeeds. No post-write reader of `FFFF34C6.bit4` within the traced E914 path was established in this bounded pass; any post-write consumer remains unresolved.
- **Same GBR, proven:** both PCs are inside `sub_86D9C`, which establishes `GBR=FFFF3454` at entry (`0x86DB2`). No adjacent-literal inference required.
- **Threshold corrected:** `0x8828E mov.l off_88310,r2; 0x88292 mov.w @r2,r6` loads `r2 = h'905C` (pointer address) and reads `WORD[0x905C] = 0x00F0 = 240`. Compare at `0x88296 cmp/ge r6,r2` with `bt loc_8829E` means branch when `r6(240) >= r2(clamped result)` i.e. **clamped result <= 240** continues to flag set; `>240` branches to `loc_883AA`. WO65125’s numeric value was right; pointer address vs dereferenced value must be kept distinct.
- **Query/cap/path verified:** query `((UBYTE[FFFF85A9] * UWORD[FFFF8494]) >> 4)` saturated to `0xFFFF` (`0x881C4–0x881E4`); capped against `WORD[r13<<1 + FFFF2150 + 0x80E]` (`0x881E6–0x88206`); helper `sub_22FD8` at `0x8822C` with table `0xE914`, axis `0xFA82`; result stored to `byte[r13 + FFFF2150 + 0x5C6]` (`0x88240`); multiplier `WORD[r13<<1 + FFFF2150 + 0x28C]` (`0x88250`); `sub_223FC` + signed clamp; compare `<=240`; `sub_71F74` called before flag set (`0x882AC`, arg `0x47` if `r13!=0` else `-1`).

### 1.3 E934 query and destination corrections — CORRECTED / BOUNDED

**WO65126 statements:** query at `0x3A06A` read UWORD/“high byte” of `FFFFA338`; GBR “unresolved”; `FFFF86EF` unresolved destination; `0x45E18`/`0x45E4E` as first consumer/reset.

**Reconciliation:**

- **`0x3A06A` does not load r6.** Actual instruction is `mov.w @(h'14,r2), r0` at `0x3A06A` with `r2=h'FFFFA324` set at `0x3A064`; it reads `UWORD[FFFFA338]` into **r0**. The call at `0x3A072` is `bsr sub_3A178` with delay slot `mov r0,r6` (`0x3A074`) — so **r6 at sub_3A178 entry is r0 as it was before 0x3A06A executes its destination effect?** No: delay slot executes before branch takes effect architecturally in SH; here delay slot is `mov r0,r6` at 0x3A074, which copies the then-current r0 (loaded by 0x3A06A) into r6. Therefore the query passed to `sub_3A178` is `UWORD[FFFFA338]` (zero/sign handling by `sub_3A178`’s `extu.w r6,r8` at 0x3A190). WO65126’s “high byte” wording and “r6 loaded by 0x3A06A” are both incorrect; the effective query source is still `FFFFA338`, passed via r0->r6 delay slot.
- **`sub_39FC8` GBR is resolved by local evidence.** `sub_39FC8` is reached via `loc_39FB4` (bra/nop to `loc_39FB8`); `loc_39FB8` starts at `0x39FB8` and sets `GBR=FFFF86D4` at `0x39FC6/0x39FC8` (`mov.w word_3A10C,r0; ldc r0,gbr`). WO65116 maps `sub_39E7A` as `established_full FFFF1860` over 0x39E7A–0x3A178, but the actual local `ldc` for this region is at 0x39FC8; this is a resolver boundary granularity caveat, not evidence against the local GBR. **Use local proof:** sub_39FC8’s GBR is `FFFF86D4`.
- **sub_3A178 has its own GBR.** At `0x3A18A/0x3A18C` it sets `GBR=FFFF86F0` (`word_3A206=h'FFFF86F0`) and restores GBR from stack on exit (`0x3A4C0 ldc.l @r15+,gbr` per normal epilogue pattern; WO65116 records `sub_3A178` established_full `FFFF34C1`? — caution: WO65116 row shows `sub_3A178 0003A178 0003A4C4 ... ffff34c1 0003A40E`, indicating a later GBR establishment inside same labeled range; local inspection shows `0x3A18C` sets `FFFF86F0` early and `0x3A40E` may set another GBR later. The E934 lookup/store happens before the later re-establishment: `sub_22F28` call at `0x3A1AA`, store to `WORD[h'5C8]+r14` at `0x3A1B4` with `r14=FFFF2150` loaded at `0x3A1A8`. Thus E934 result store `FFFF2150+0x5C8=FFFF2718` is proven regardless of later GBR changes inside sub_3A178.)
- **`FFFF2718` vs `FFFF86EF` are distinct.** `FFFF2718 = FFFF2150 + 0x5C8` is the fixed E934 byte store at `0x3A1B4` (proven). `FFFF86EF = FFFF86D4 + 0x1B` is a separate byte; sub_39FC8 stores sub_22F80 results at `@(0,gbr)` and `@(4,gbr)` (GBR=FFFF86D4 => `FFFF86D4`, `FFFF86D8`) and does not store to `GBR+0x1B` in the traced path. WO65118 xref had no hit for FFFF2718/86EF in the quick grep; I did not find a write to `FFFF86EF` in this bounded trace. **Treat `FFFF86EF` as unproven/unrelated in this WO; do not associate with E934 output.**
- **`0x45E18–0x45E4E` are not proven E934 semantic consumers.** At `0x45E18` the code loads `r14` from context not established in this snippet (function around 0x45Bxx/0x45E..; WO65116 shows nearby function `sub_45AB6 00045AB6–0004619A GBR=FFFF1054` but r14 is dynamic). The sequence stores `0` to `@(r0,r14)` where `r0=0x5C8` (0x45E1C), then later reads `@(r0,r14)` where `r0=0x5C9` (0x45E4E) and stores into `0x5C8` again (0x45E54). This proves a clear/reset/copy pattern on `r14+0x5C8/0x5C9` *if r14==FFFF2150*, but **r14 base is not proven in this bounded pass**. Therefore `0x45E18` is a **candidate clear**, not a confirmed E934 semantic consumer; `0x45E4E` adjacent-byte read is not a confirmed E934 consumer. Bounded unresolved.

## 6. Shared vs distinct mechanism

- **Shared helper primitive:** all three use `sub_231C8` interpolation endpoint math. This is **not** sufficient to claim same calibration function.
- **E904/E914:** same reader family `sub_22FD8` + UWORD BE axis search `sub_2340C`; same enclosing `sub_86D9C` (GBR=FFFF3454); adjacent result offsets (`+0x5C5/+0x5C6` relative to dynamic base expression) and adjacent flag bits (`+0x73.bit3/+0x72.bit4` in GBR space); different tables/axes/queries/threshold constants. **Software-role:** closely related sibling paths in same control region; not identical path.
- **E934:** different reader `sub_22F28` + UBYTE descending axis search `sub_233CC`; different caller/base (`sub_39FC8` GBR=FFFF86D4, `sub_3A178` fixed output base FFFF2150); no flag-bit output; followed by two-stage `sub_22F80` on different table/axis (`0x102FC/0x112CA`). **Software-role:** adjacent ROM calibration object family by address proximity only; execution path distinct.
- **Physical-domain:** no shared or distinct physical meaning established for any of the three.
