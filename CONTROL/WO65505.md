## Falsifiable hypothesis record

- **Identity layer advanced:** provenance of the whole `FFFF1800` RAM block.
- **Hypothesis:** the block is filled by a **block copy** (computed source and destination), so a writer exists but is invisible to the literal/displacement index.
- **Evidence:** WO65493 §3 (no store, one `jsr` target, literal `0x4D54` = `FF FF 18 20`); WO65118 header `method_limits`.
- **Prediction:** a copy routine with a destination in `FFFF1800`–`FFFF1840` computed in a register, a ROM source and a length constant; failing that, the overlay explanation stands.
- **Cheap discriminator:** enumerate `movca.l`, then all loops writing through a register-held destination derived from a literal in `FFFF17D0`–`FFFF1900`.
- **Result:** **REJECTED for the block-copy form.** `movca.l` occurs **zero** times in the ROM, and no copy/fill routine writes the range. The block's normal-operation writes are ordinary field-level stores — but the WO65118-style literal/displacement scan had missed a whole addressing form, because this block is reached **GBR-relative with `GBR = FFFF17D0` and `GBR = FFFF180C`**. The census below closes that gap and still leaves the four cells writerless.
- **Information gain:** replaces "no writer because the index is incomplete" with "no writer in any addressing form", and identifies `FFFF1800`–`FFFF1840` as a dual-use region: data fields during running, RAM code staging during flash programming.

## 1. `movca.l` — zero occurrences

`grep -ci movca` over the full listing returns **0**. The unmodelled-store transport is excluded outright, and no further `movca.l` work is needed by any future WO.

## 2. The addressing form the index did not model: GBR = `FFFF17D0` and `FFFF180C`

The block is reached through **GBR** with two different bases, so accesses are printed as symbol expressions rather than plain displacements:

- `0x35E96 mov.l off_35F34, r0 ; h'FFFF17D0` — GBR base `FFFF17D0`
- `0x36A3A / 0x36A72 / 0x370B8 mov.w @((word_FFFF1840 - h'FFFF180C),gbr), r0` — GBR base `FFFF180C`
- `0x36E58 mov.w @((word_FFFF1820 - h'FFFF180C),gbr), r0`

A displacement-only scan (or an `address`-column index such as WO65118) sees the *resolved* address here but never the base identity, which is why WO65493 could not decide the transport.

**Census of all GBR-relative accesses resolving into `FFFF17D0`–`FFFF18FF`: 91 total — 46 stores, 45 loads.**

## 3. The one write into the range from a different path — and what it reveals

`0x4B34` is a prologue (`mov.l r10..r14,@-r15; sts.l pr`) whose body is a flash-programming entry:

| PC | Instruction | Effect |
|---|---|---|
| `0x4B42` | `mov.l off_4D48, r12 ; h'FFFF83AE` | peripheral flag byte (`bit 0x40`, `bit 8`-access) |
| `0x4B44`–`0x4B46` | `mov #-0x18, r13; shll8 r13` | `r13 = FFFF E800` |
| `0x4B48` | `mov.l off_4D4C, r14 ; h'FFFF1800` | **block base** |
| `0x4B56`/`0x4B5A`/`0x4B5E` | `mov.b r0, @(2,r13)`, `@(1,r13)=1`, `@(6,r13)=3` | writes `FFFFE802`, `FFFFE801`, `FFFFE806` |
| `0x4B60` | `mov.b r6, @r14` with `r6 = 0xFF` | **`U8[FFFF1800] = 0xFF`** |
| `0x4B6E`–`0x4B74` | `and #h'FFFFFF0F, r0; or #h'F0, r0; ldc r0, sr` | interrupt mask → 0xF |
| `0x4B76`–`0x4B78` | `stc vbr, r11; ldc r10, vbr` (`r10 = 0`) | **VBR → 0** |
| `0x4B7A`–`0x4B80` | `add #-0x5A, r6` (0xFF→0xA5), `mov.b r0, @(4,r13)` | writes `FFFFE804 = 0xA5` |
| `0x4B82`–`0x4B86` | `mov.b @r13, r0; or #1; mov.b r0, @r13` | sets bit 0 of `FFFFE800` |
| `0x4B96`–`0x4B9A` | `mov.b @r14, r2; tst r2,r2; bt` | **polls back `U8[FFFF1800]`** |
| `0x4BAA`–`0x4BB2` | `mov #h'FA0, r4; mov #0, r5; mov.l off_4D54, r6 ; h'FFFF1820; jsr @r6` | **calls `FFFF1820` as code** with `r4 = 0xFA0`, `r5 = 0` |

Reading: `0xFFFFE800`–`0xFFFFE807` is a byte-programmed control block with a set-bit-then-poll sequence, `EBR`-like block-number write (`0xA5`), interrupt masking and VBR relocation — the shape of an SH7058 **flash erase/program prologue**. The layout match (FLMCR1/FLMCR2/EBR1/EBR2 at `FFFFE800`/`E802`/`E804`/`E806`) is **inference from the register layout**, not from a datasheet in this repository, and is flagged as such.

Two consequences:

1. The only write into the range from this path is the single byte `U8[FFFF1800] = 0xFF` — a handshake flag, not a transport.
2. `FFFF1820` is invoked as **code** during flash programming. So the region is **dual-use**: data fields during normal running, RAM-resident code during a flash session. That is exactly a RAM overlay, and it explains why a data writer for `FFFF1820`/`FFFF1830`/`FFFF1838`/`FFFF1840` was never found — the staging is done by code that is not in this image, or by the flash session itself.

## 4. Verdicts

| Question | Result | Confidence |
|---|---|---|
| Does a block copy fill the range? | **no** — no copy/fill routine has this destination; `movca.l` count is **0** | **HIGH** |
| Are `FFFF1820`/`1830`/`1838`/`1840` written anywhere? | **no** — zero stores in literal, displacement, GBR and register-indexed forms | **HIGH** |
| Is the literal/displacement index the reason? | **partly** — the block is GBR-relative (`FFFF17D0`, `FFFF180C`), which the address-column index cannot express; correcting for it changes nothing for the four cells | **HIGH** |
| Is `FFFF1820`'s `jsr` target code? | **yes** — reached from a flash-programming prologue that masks interrupts, zeroes VBR and writes flash-control registers | **HIGH** |
| Is the block a RAM overlay? | **supported** — the region is demonstrably used for two incompatible roles | **MEDIUM-HIGH** |
| Is the staging mechanism proven? | **no** — nothing in this image writes the code that `FFFF1820` executes | **HIGH** (negative) |
| Does `sub_36E02`'s error term read a level? | **not supported**; the address is dual-use and cannot be named a level | **MEDIUM** |

**Verdict: transport NOT FOUND; overlay SUPPORTED but unproven.** Neither "block copy" nor "ordinary data block" survives intact: the block is ordinary data *and* a code-staging area.
