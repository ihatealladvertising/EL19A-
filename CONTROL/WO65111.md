## (a) `0x12844` block boundary and schema

`0x12844` is a **contiguous 0x54-byte configuration/scalar block spanning `0x12844–0x12897`**, immediately followed by four zero bytes (`0x12898–0x1289B`) and then a separate array family starting at `0x1289C`:

| Region | Extent | Evidence |
|---|---|---|
| Scalar/config block | `0x12844–0x12897` (84 bytes) | 230 code sites load `0x12844` as a base; the largest immediate index applied to that base is `0x53` (83), i.e. `0x12844+0x53 = 0x12897`; no access at a higher offset from this base was found |
| Gap | `0x12898–0x1289B` | four zero bytes; no reference found |
| Array family | from `0x1289C` | accessed through a different base, `h'128AE` (`0x692CC`), with negative displacements such as `dword_1289C+0x12` and `+0x21`; `0x1289C` opens with the 18-byte byte ramp `00 00 10 20 30 40 50 60 70 80 90 A0 B0 C0 D0 E0 F0 FF` |

The densest clusters are `0x18`, `0x1B`, `0x25`, `0x36` and `0x3D`.

**Interpretation:** the block is a heterogeneous scalar/configuration record (byte fields plus a mixed UWORD/LONG region at `0x12850–0x1286B`: `003F 0007 | 00000010 | 00000030 | 3F00 00FF | 00000010 | BB0F 2020 | E6CF 9000`). It is **not** a single calibration table with row/column geometry, consistent with WO65082's correction. Field semantics, units and grouping remain unassigned.

## (b) `0x8405` provenance

- **Access form: direct ROM.** All 21 load sites use `mov.l off_<table>, rN ; h'8405` followed by `mov.b @rN`, i.e. an absolute pointer to ROM `0x8405`. No RAM-resident copy of `0x8405` exists in the listing, so there is **no writer** to find — the byte is immutable calibration data. This resolves the "who writes it" question as a bounded negative on the RAM-copy hypothesis.
- **Bits tested** across the 21 sites: bit 0 ×12, bit 1 ×4, bit 2 ×1 (`0x2BF24`, `tst #4`), bit 5 ×1 (`0x5B6A8`, `tst #0x20`), bit 6 ×1 (`0x6F606`, `and #0x40`), bit 7 ×2 (`0x6F6B4`, `0x6F93A`, `tst #0x80`). **Bits 3 and 4 are never tested in any mask**, confirming WO65084's open item.
- **Shipped value `0x0C`:** bit 2 is set and therefore the `0x2BF24` branch is active; bit 3 is set but read nowhere in the listing, so it is inert in this calibration.
- The single-site bits remain single-site: bit 2 gates only `0x2BF24` (a GBR bit-`0x20` publish), bit 5 only `0x5B6A8`, bit 6 only `0x6F606`. No cross-site identity beyond the already-known 1000/800 bit-0 pair.

## (c) Writers of the three cells

| Cell | Result |
|---|---|
| `FFFF34C8` bit 2 | **Writer found:** `0x6CFDC` in `sub_6CF94`, `mov.b r0, @((byte_FFFF34C8 - h'FFFF34C1),gbr)` with GBR = `FFFF34C1`. Gate: bit 2 is **set** only when `FFFF99F4+0xC` bit 0 is clear, `0x8405` bit 0 is clear, and `FFFF9860+8 ≠ 1`; otherwise the same store **clears** it (`0x6CFD8`). This replaces WO65086's read-site reference (`0x6CFC6` tests bit 0 of `0x8405`; the actual bit-2 store is `0x6CFDC`). |
| `FFFF35C8+0x53` bit 2 | **Same byte as the next row.** `0x35C8+0x53 = 0x361B`, so WO65086's "two override cells" are one address. |
| `FFFF3616+5` bit 2 | **`FFFF361B` — no writer found.** Six references total: four reads (`0x362D6`, `0x65194` with `and #4`, `0x84002`, `0xAD164`) and the two equivalent expressions above. Every `@(h'53,gbr)` store in the listing belongs to routines whose GBR base is not `FFFF35C8` (e.g. `0x9DEB2` runs under GBR `FFFF34C1`, where `+0x53` is `FFFF3514`). Bounded negative: the byte is read but never statically written; a computed-index or block-copy writer, or a default-zero value, remains possible. |

**Correction to WO65086:** the "two override cells" are a single byte, `FFFF361B`. Its bit 2 is tested at `0x65194` and `0x362D6`, so the override reading remains valid, but any future writer search need only cover one cell.
