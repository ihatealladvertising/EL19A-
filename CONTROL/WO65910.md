## Question

`sub_7E8B2` publishes the six-condition conjunction into **bit4 of `FFFF3579`**. Does anything read that bit, or does the chain that runs `FFFF355D.bit5` → `FFFF34B5.bit5` → six-conjunct aggregate → `FFFF3579.bit4` terminate in internal state?

## Answer

**Nothing reads bit4.** `FFFF3579` has exactly five accesses in the whole ROM: one read that loads the old value, two writes that together form the bit4 publication, one reader that tests **bit7**, and one reader that tests **bit0**. The bit this lane has been chasing is published and never consumed — the chain terminates in a status byte whose other bits are consumed elsewhere.

### 1. Complete access census (five sites, three bases)

`h'FFFF3579` has **zero** pool literals, so every access is GBR-relative. Three sites use the linker-resolved symbol form, two use `FFFF34B3` as the base:

| PC | Form | Role |
|---|---|---|
| `0x07E8E0` | `mov.b @((byte_FFFF3579 - h'FFFF34B3),gbr),r0` → `mov r0,r9` at `0x07E8E2` | loads the old value into `r9` |
| `0x07EBBE` / `0x07EBD0` | `or #h'10` (delay slot) / `and #h'EF` | set / clear sides of bit4 |
| `0x07EBD2` | `mov.b r0,@((byte_FFFF3579 - h'FFFF34B3),gbr)` | the bit4 store |
| `0x07EC46` | `mov.b r0,@((byte_FFFF3579 - h'FFFF34B3),gbr)` | second store, `r0 = r14 & #h'FB`, clears **bit2** |
| `0x05461E` | `mov.b @(h'C6,gbr),r0` under base `FFFF34B3` | **reader — tests bit7** |
| `0x078C0A` | `mov.b @(h'B8,gbr),r0` under base `FFFF34C1` | **reader — tests bit0** |

The two bases are `FFFF34B3` (symbol form, `+0xC6`) and `FFFF34C1` (`+0xB8`); both resolve to `FFFF3579`, which is exactly the multi-base addressing pattern WO65898 recorded for `FFFF34B5`.

### 2. The bit4 publication, with its set side in a delay slot

The publication is not a plain store — it merges two paths at `0x07EBD2`:

```
0x07EBB4  mov.b @((byte_FFFF3575 - h'FFFF34B3),gbr),r0
0x07EBB6  tst   #2,r0
0x07EBB8  bf    loc_7EBCE
0x07EBBA  mov   r9,r0
0x07EBBC  bra   loc_7EBD2
0x07EBBE  or    #h'10,r0        ; DELAY SLOT -> sets bit4 on the conjunction-true path
loc_7EBCE mov   r9,r0
0x07EBD0  and   #h'EF,r0        ; conjunction-false path clears bit4
loc_7EBD2 mov.b r0,@((byte_FFFF3579 - h'FFFF34B3),gbr)
0x07EBD8  tst   #h'10,r0        ; reads the value just written
0x07EBE2  bt/s  loc_7EC36       ; clear -> the 0x7EC36 path, set -> fall through
```

WO65898's statement that `0x07EBD2` publishes the conjunction is **confirmed**, and the exact set-side mechanism is now recorded as `FND-000013`: the `or #h'10` that sets the bit sits in the `bra` delay slot, so the single store carries both polarities.

### 3. Bit4 has no consumer; the byte's live bits are bit7 and bit0

- `0x05461E` (`sub_…` at `0x054614`): `tst #h'80` on `FFFF3579`, gated by `FFFF3578.bit5` (`@(h'C5,gbr)` + `tst #h'20`), `FFFF3578.bit3` (`tst #8` on the stack copy) and `FFFF3572.bit2` (`@(h'BF,gbr)` + `tst #4`), feeding a four-condition gate that ends at the `0x054644`/`0x05465E` output path.
- `0x078C0A`: `tst #1` on `FFFF3579` builds a bitmask in `r13` (1, then `or 2`, `or 4`, `or 8` from `r12` bits 7/6/5), and stores it to **`FFFF2150 + 0x6FE` = `FFFF284E`** (`word_78CF0 = h'6FE`) gated by `FFFF34E2.bit4` (`@(h'2F,gbr)` + `tst #h'10`).

Neither reader tests bit4, and no site combines the byte into a mask or copies it wholesale before testing. **0 of 5 accesses read bit4.**

## Terminal

**`INTERNAL STATE FLAG`** with an empty consumer set. Bit4 is set by the six-condition conjunction and cleared otherwise, written twice per evaluation cycle, and read by nothing in this ROM. The byte itself is *not* dead — bit7 gates a four-condition output path and bit0 feeds the `FFFF284E` status bitmask — but the bit this lane's chain publishes is a terminus.

## Classification

`INTERNAL STATE FLAG` — terminal is the byte's own write, no consumer.

## Findings disposition

**PROMOTED — `FND-000013`**, additive index entry included. The reusable element is not the address (already covered by WO65898) but the method: a status-bit publication can be split across a branch delay slot, so a store preceded by `and #h'~mask` may still be the SET path. That rule nearly produced a false "WO65898 is wrong" conclusion during this WO, which is precisely the kind of reader error worth capturing. The bit4 consumer question itself needs no record: "no consumer" is a census result, and WO65910 is its anchor.

## Confidence

**HIGH** that bit4 has no reader: the census is exhaustive by three independent routes — zero pool literals for `h'FFFF3579`, three symbol-form references (all accounted for), and a fixed-displacement GBR census that resolved both remaining sites to the cell.
**HIGH** for the delay-slot merge (the `tst #h'10` after the store is only meaningful if both polarities are possible).
**MEDIUM** for the completeness of the "no consumer" conclusion in one specific sense: a reader that copies the whole byte through a pointer chain would not appear in any of the three routes.

## Reconciliation
