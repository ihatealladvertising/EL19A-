# SH705x ROM Tool — Architecture Charter and Development Plan

**Status:** IMPLEMENTATION DIRECTION APPROVED v0.3 — read-only tool development authorized; architecture reconciliation remains the interface gate  
**Date:** 2026-11-26  
**Repository:** `ihatealladvertising/EL19A-` · branch `main`

## 1. Purpose

Develop an extensible, deterministic, read-only ROM engineering toolkit for SH705x firmware, initially supporting SH7055 and SH7058 and designed to expand to additional processor and ROM families. The toolkit is the primary engineering deliverable. The existing Nissan EL19A project is its first end-to-end validation corpus; completion of the EL19A RomRaider definition is a generated byproduct of the generic discovery, structural verification and symbol-cross-reference pipeline, not a competing standalone workstream. Keep ECU-specific assumptions in profiles and evidence adapters, never in the shared core.

The intended user experience is a set of small, independently executable Python command-line scripts backed by one shared library. A unified launcher may be added later, but no command should require that launcher to run.

## 2. User-directed architecture

The confirmed starting direction is:

- Modular, individual Python scripts rather than one monolithic application.
- A shared core for common ROM/address/data handling.
- Reusable support for SH705x ROMs and potential expansion beyond SH705x.
- Existing EL19A tools should be reused and migrated incrementally where practical.

The following are planning defaults to validate during architecture work, not immutable decisions:

- Python 3, standard-library-first; optional third-party adapters only where justified.
- Command-line interface first; graphical interface deferred.
- Versioned JSON for machine-to-machine interchange; CSV/TSV for review and spreadsheet work.
- BIN support first; DAT and PDX only through independently validated format adapters.
- RomRaider XML as the first definition import/export target.
- Read-only ROM analysis as the initial operating mode.

## 3. Proposed component boundaries

| Component | Responsibility |
|---|---|
| `tools/` | Independently executable commands: identify, inspect, compare, scan, trace, parse and export |
| `lib/romtool/` | Shared ROM image, address, byte-reading, hashing, geometry, evidence and serialization logic |
| `formats/` | Container and metadata adapters: BIN, DAT, PDX, A2L and RomRaider XML |
| `processors/` | CPU-family behavior: SH7055, SH7058 and future processor backends |
| `profiles/` | ECU/ROM-family-specific fingerprints, memory layouts and calibration profile data |
| `tests/` | Synthetic fixtures, regression tests, format fixtures and integration tests |
| `CONTROL/` | Architecture decisions, specifications, work orders and project governance |

Exact package names and module boundaries remain subject to WO70020–WO70022.

## 4. Canonical conceptual objects

The shared model must account for at least:

- **ROM artifact/image:** original file identity, byte size, hashes, container identity, reconstructed image identity and source provenance.
- **Processor profile:** CPU family/model, endianness, address width, vector conventions and supported analysis capabilities.
- **Address space / memory region:** distinct file offsets, ROM effective addresses, RAM addresses, mapped ranges and translation rules.
- **Symbol:** name, namespace, type, address references, duplicate declarations and source provenance.
- **Calibration object:** storage address, element type, dimensions, extent, axes, record/layout information and conversion references.
- **Reader / lookup:** function and call-site identity, arguments, query derivation, interpolation/search/clamp mechanics and observed consumers.
- **Evidence / provenance:** source hash, source location, extraction method, observation, confidence, status and links to findings/reconciliation records.

A2L donor metadata, XML declarations, exact payload matches and EL19A target-side reader evidence must remain separate evidence classes. Unknown values and unresolved relationships must be represented explicitly rather than guessed.

## 5. Proposed command families

Initial commands are candidates, not a commitment to create one file per row if the architecture work identifies a better boundary:

1. `rom_identify.py` — identify format, CPU, ROM family, size and known signatures.
2. `rom_info.py` — report hashes, image layout, memory regions and identification confidence.
3. `rom_compare.py` — compare images, identical/changed regions and revisions.
4. `rom_extract.py` — extract and verify recognized container payloads.
5. `rom_scan_tables.py` / `rom_inspect_table.py` — discover and inspect calibration candidates.
6. `rom_find_references.py` / `rom_trace_readers.py` — inspect references, readers, lookups and consumers.
7. `rom_parse_a2l.py` / `rom_parse_xml.py` — import donor metadata and existing definitions.
8. `rom_compare_calibrations.py` — compare objects and evidence across ROMs.
9. `rom_generate_xml.py` / `rom_validate_xml.py` — generate and validate definition output.

## 6. Evidence, safety and compatibility rules

- Source ROMs are read-only by default; analysis outputs are written separately.
- Every machine-generated result records source file hashes, tool/version identity and relevant command parameters.
- Deterministic inputs/options should produce deterministic outputs.
- No ECU-specific calibration semantics in generic processor or format code.
- A donor name, unit, axis or conversion is not target-ROM proof.
- Target storage geometry, reader mechanics, query behavior and consumer paths remain distinct from hypotheses.
- Unknown blocks, unsupported format fields, duplicate declarations and unresolved references are retained and reported, not silently discarded.
- Existing proven tools are migrated incrementally; do not begin with a wholesale rewrite.
- ROM editing, patching, checksum modification and flashing are outside the initial read-only scope. They require separate explicit authorization and their own safety design.
- Definition-file generation is an offline output function and does not authorize ROM modification or flashing.

## 7. Phased roadmap and gates

### Gate 1 — Architecture definition
- WO70020: inventory current tools and migration boundaries.
- WO70021: define canonical shared data model and interchange contracts.
- WO70022: audit runtime compatibility, dependencies, tests and CI.
- Integrator consolidates their results into an implementation-ready architecture. No source-code migration is part of these WOs.

### Gate 2 — First tested vertical slice
- Establish synthetic regression fixtures and the versioned shared model/JSON interchange before refactoring existing tools.
- Implement or adapt shared ROM identity, address-space mapping and format loading without duplicating proven loader behavior.
- Reuse the existing per-call helper/call exporter and emit a deterministic per-address calibration-candidate catalogue, preserving all calls, unresolved fields and conflicting geometry.
- Produce a complete run manifest with original/container and decoded-image hashes, tool/source identity, runtime, arguments, execution status, logs and every output hash.
- Deliver a working BIN-first pipeline on a known SH7058 ROM before widening input formats.

### Gate 3 — Structural discovery and symbol cross-reference
- Integrate SH7055/SH7058 processor backends and explicit memory-layout/profile handling.
- Build relational A2L indexes for CHARACTERISTIC, AXIS_PTS, MEASUREMENT, COMPU_METHOD / COMPU_TAB / COMPU_VTAB, RECORD_LAYOUT, FUNCTION and GROUP, retaining raw unsupported metadata and source hashes.
- Cross-reference target candidate addresses, axes, reader/helper/function context and payload/geometry against donor A2L, XML, catalogues and reference ROMs. Keep every match typed by basis and source; donor matches remain hypotheses.
- Add optional, hash-validated EL19A access-index, GBR, diagnostic and variant evidence providers without making them prerequisites for generic commands.

### Gate 4 — Calibration reconciliation and definition output
- Emit one canonical record per isolated target calibration address, with target structural facts separated from symbol hypotheses; derive review-friendly CSV/TSV from lossless JSONL.
- Reconcile candidate structures against existing XML and scope sources without silently overwriting conflicts or owner presentation decisions.
- Generate and validate conservative RomRaider XML as the first definition output. An EL19A build must be reconciled against the Findings index and accompanied by a build manifest; preserve the existing baseline until a separately verified release integration.

### Gate 5 — Expansion
- Add HEX/S-record support and format-specific Nissan DAT/PDX adapters only after each container/decoder is independently validated. Preserve original-container and decoded-image hashes and decoder provenance.
- Add further SH705x variants and, later, other processor families through backends and profiles.
- Consider optional database and graphical interface only after the CLI and interchange contracts stabilize.
- ROM editing, patching, checksum modification and flashing remain outside this programme and require separate explicit authorization and safety design.

## 9. Implementation authorization and protected boundaries

The user has explicitly moved the project from planning into implementation direction. After WO70020–WO70022 are completed and reconciled, bounded implementation WOs may authorize read-only tool modules, shared libraries, tests, schemas, CLI entry points, documentation and reproducible analysis outputs. The implementation sequence must follow the reconciled architecture and shared data model; do not start a competing interface or duplicate existing scanner behavior.

This authorization does not permit modification of source ROMs, LSTs, A2Ls, donor files or other protected evidence. Existing calibration XMLs, workbooks, catalogues, scope matrices and Findings records remain protected inputs unless a separate WO explicitly authorizes a specific edit. New generated XML outputs are permitted as tool products only after the Findings/build-manifest gate; do not overwrite the current release baseline or claim a release without validation/readback. Keep Python standard-library-first; do not install dependencies or alter environments without a concrete implementation requirement and explicit approval. ROM patching, checksum modification and flashing remain excluded and require separate authorization.


## 10. Existing workbench reuse and integration priorities

The existing workbench should be extended by connecting proven modules and generated datasets, not by recreating their analysis logic inside one increasingly large script. The user-approved five improvement areas and their source-level findings are recorded in [SH705X_WORKBENCH_INTEGRATION_PLAN.md](SH705X_WORKBENCH_INTEGRATION_PLAN.md).

The integration sequence is:

1. Establish dedicated synthetic workbench regression fixtures.
2. Reuse `sh7058_cross_rom_scanner.py`'s existing `build_scan_export()` and `write_machine_exports()` from workbench `scan`/`audit`; complete the external run manifest and satisfy WO70006's attributable raw-output gate. Do not build a duplicate per-call exporter.
3. Add optional, hash-validated adapters for `rom_access_indexer.py`, `build_static_indices.py`, and their existing GBR/consumer datasets.
4. Reconcile all selected calibration XMLs, both scope-matrix variants, the discovered-table catalogue and candidate register as distinct sources, preserving conflicts and owner-directed display choices.
5. Add diagnostic-rosetta and variant-difference providers as optional, provenance-labelled candidate context.

The existing scanner exporter is useful but not a complete semantic trace: caller boundaries are heuristic candidates, register arguments come from a bounded linear window, and query provenance, full transforms, interpolation/clamp behavior, result registers and downstream consumers remain unresolved unless separately traced. These limits must survive export and user-interface presentation.

The existing access indexer, static-index builder, diagnostic rosetta and EL19A/EL13A diff script are pinned to particular EL19A ROM/listing identities and assumptions. Reuse them as EL19A evidence providers first; do not treat them as generic SH705x backends until their profile boundaries, inputs and integrity checks are deliberately redesigned and regression-tested.

WO70020–WO70022 remain unchanged and retain their FIFO positions. Their outputs should be reconciled before creating implementation WOs. This plan update does not authorize source-code, test, workflow, dependency, ROM, LST, A2L, calibration, workbook, Findings or release-artifact changes.


## 11. Primary deliverable: per-address calibration discovery and cross-reference

The first usable product is a read-only SH705x scan pipeline that, for a supported ROM, emits a deterministic catalogue of calibration candidates grouped by target address. Each record must keep independently sourced layers separate:

- **Target ROM facts:** ROM/image identity; address-space and memory-region identity; candidate base and exact checked extent; storage type/width/endianness; dimensions/strides/layout where established; axis references; helper and lookup kind; all associated call PCs; caller/function identity with its actual confidence; query/axis argument observations; and reader/consumer status.
- **Unresolved target fields:** explicit null/unresolved values for unproven query source, transforms, interpolation, clamp, signedness, axis geometry, result register or consumer. Preserve competing observations and conflicting geometry instead of selecting a convenient winner.
- **Repository object links:** source-by-source links to current calibration XML objects, catalogues, scope matrices and findings, retaining source hashes and conflicts.
- **Symbol hypotheses:** separate cross-reference entries for A2L CHARACTERISTIC, AXIS_PTS, MEASUREMENT, conversion/record-layout and function/group context, plus optional donor-ROM evidence. Each hit identifies source file/hash, symbol kind/name/address, match basis (for example exact address, axis link, function/helper context, payload/shape or subsystem neighbor), confidence tier and an explicit unverified-donor status where appropriate.

The canonical interchange is versioned JSON/JSONL with lossless nested matches and provenance. CSV/TSV is a derived summary, never the only record. Every run emits a manifest with input/container/decoded hashes, tool and source identity, runtime, command arguments, execution status, captured logs and hashes for all output artifacts. Deterministic serialization and stable record IDs must be tested.

The initial supported path is BIN → normalized address space → helper/call discovery → per-address structural candidates → A2L/XML/catalogue cross-reference → JSONL/CSV/TSV + manifest. Do not claim exhaustive table discovery or complete semantic proof: report scanner coverage and every unresolved boundary.

The proposed standalone modules in the user-approved direction (ROM loader, table isolator, A2L symbol table, symbol cross-reference, calibration exporter and pipeline CLI) are logical capability boundaries, not mandatory filenames. WO70020 and WO70021 outputs plus tests determine the final package/API layout. The shared implementation must remain reusable by small standalone command scripts.

## 12. EL19A definition as first generated validation output

EL19A is the first target profile and acceptance corpus, not the boundary of the generic tool. The RomRaider definition should be generated from the tool's verified target-side structural records, Findings/Reconciliation state and explicit owner presentation decisions. Donor A2L names, exact payload matches, screenshots and variant similarities remain separate leads and cannot overwrite target facts.

The first EL19A pipeline acceptance requires: exact input ROM identity and reproducible source/output manifests; per-address structure and complete byte-extent checks with conflicting/truncated candidates surfaced; reader/call evidence linked to each supported candidate; cross-referenced Nissan symbol hypotheses with source hashes and match basis; a reconciliation report against the current XML, catalogue, scope and Findings sources; and a conservative generated RomRaider XML plus validation report and build manifest, with unresolved physical names/units/conversions left raw or provisional.

The tool is considered useful before all physical semantics are solved. A structurally correct raw/provisional definition is preferable to a confidently named but unsupported one.
