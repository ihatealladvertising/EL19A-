## Decision question

Can the false aliases and corrected claims that have repeatedly cost rework be published once as a machine-readable register — with each row carrying its evidence level, the negative-search method behind it, its source WO, and a mechanical re-verification status against the pinned ROM/listing — so a worker can check a suspected alias in one lookup instead of re-deriving the trap?

WO65115/65116/65117/65118 publish structural indexes, not curated trap facts. No overlap.
- This WO does not re-run any closed search as a new technical claim. It curates already-documented results, re-verifies the mechanically checkable subset, and marks the rest as documented-only.

## Method (bounded)

1. Parse concordant listing CODE lines; verify raw bytes at every cited PC against the ROM; report full concordance.
2. `ROM_BYTE` checks: read the exact bytes at the cited ROM address and compare with the documented value.
3. `LISTING_PC` checks: resolve the cited PC in the concordant listing and assert the instruction text/annotation carries the documented token (e.g. `h'FFFF86DF` pool annotation, `0x5F4` base displacement, `FFFF8234` context).
4. `ARITHMETIC` checks: recompute `base + offset` mod 2^32 and compare with the false and correct addresses; explicitly test the `0x55xxx` over-reach non-derivation.
5. `DOCUMENTED` rows: copied with source WO and negative-search method; `verification_status = NOT_RECHECKED`; never promoted by this generator.
6. Any failed mechanical check is recorded as `FAIL` in both TSVs; the WO is not cited as complete if a check intended as a hard anchor fails. Hard anchors: FA001 (no stale-GBR `FFFFF770` hit), FA002 (ROM `0x85DF` bytes), FA003 (over-reach non-derivation), FA004 (`FFFF2744` arithmetic). The remaining rows are reported, not gated.

## Acceptance / stop condition

- ROM/listing hashes verified; concordance reported; both TSVs are the generator's direct output.
- FA001–FA004 hard anchors pass; any failure reported verbatim and the WO not cited complete.
