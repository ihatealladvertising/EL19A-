## Closeout — 2026-11-22

**Result:** `0x0AF72` and `0x0ADF2` are **two channels that share one row axis and both query inputs but have different column axes**. One call sequence evaluates both every time it runs, and each result goes to its own UBYTE (`FFFF1707` / `FFFF1708`). They are not alternate inputs chosen by a gate. Downstream, the two values are used together as the upper and lower endpoints of a selection/interpolation on `FFFF84BA` (WO65037). This WO adds two new results: the **second query input** (missed by WO65037) and **confirmation of the base pointer** for WO65037's open `0x466A8` consumer. No physical meaning is assigned.

### 1. Object reconfirmation (catalogue reuse)

- Catalogue row: `0x0AF72,0x0AF72-0x0AFB1,8x8,UBYTE,sub_22C00 @ 0xAE928,explicit U8,explicit U8,…,Reader-Verified,WO65060,Paired with 0x0ADF2 @ 0xAE918 (WO65037)`.
- ROM axes (bytes read from pinned ROM):
  - Row axis, shared: `0xF4AE` = `18 28 38 40 48 50 58 68`.
  - Column axis for ADF2: `0xF4CA` = `19 1F 26 2D 3C 4C 60 78`.
  - Column axis for AF72: `0xF50A` = `19 1F 26 3C 4C 60 79 80`.
- The two maps differ only in their column axis and payload. The payload was not re-decoded, per the exclusions.

### 2. Helper contract (`sub_22C00`, `0x22C00–0x22C2E`)

```text
22C04 extu.b r7,r7         ; query-1 (UBYTE)
22C06 mov r5,r0 / mov r7,r5 ; axis-1 pointer = caller r5
22C0C jsr sub_233CC (r4=7)  ; search axis-1
22C14 mov r6,r0             ; axis-2 pointer = caller r6
22C16 mov.l @(0x10+arg_0,r15),r5 ; query-2 = caller stack longword @r15
22C18 extu.b r5,r5
22C1A jsr sub_233CC (r4=7)  ; search axis-2
22C2C jmp loc_231F8 (r5=8)  ; 8-column interpolation
```

So `r5`/`r7` give the row axis and its query, and `r6` plus the caller's stack byte give the column axis and its query.

### 3. Caller `sub_AE8CE` — new second-query provenance (`0xAE8DA–0xAE930`)


- **Query 1 (row axis `0xF4AE`):** `UBYTE[FFFF85A4]`, the same for both maps (WO65037). A UWORD writer of `FFFF85A4` is indexed at `sub_36012` `0x3605C` (WO65118); it was not traced here.
- **Query 2 (column axes `0xF4CA` / `0xF50A`), new:** `q2 = (FFFF1D81.bit5 && ROM[0x86CC].bit0) ? 0xFF : (UWORD[FFFF8494] >> 8)`. ROM `0x86CC = 0x81`, so bit 0 is set in this ROM. Whenever `FFFF1D81.bit5 = 1`, the column query is therefore forced to `0xFF`, which is above both axis maxima (`0x78` / `0x80`) and clamps to the last column. `FFFF8494` is the UWORD runtime multiplier already noted (producer unresolved) in WO64869/WO64894.
- **Gate polarity:** neither map call is conditional. Both run on every pass. The only condition is how query 2 is built.

### 4. `FFFF1D81.bit5` direct producer (bounded)

`sub_4E24C` (`0x4E266–0x4E29A`) sets bit 5 using the same hysteresis pattern as WO65183:

```text
4E26A/4E270  r2 = sub_22E10(0xE810, UBYTE[FFFF859C+0xD] = FFFF85A9) ; stored FFFF1054+0x1C2 (4E27A)
4E280        r5 = UBYTE[FFFF2150+0xAAC]
4E282..8C    if prior FFFF1D81.bit5: r5 += 8
```

- **Set:** `UBYTE[FFFF2150+0xAAC] >= E810(FFFF85A9)`.
- **Hold:** the same comparison with an extra 8, so bit 5 stays set until the value drops 8 below the curve.
- `sub_3648C` (`0x365F2`/`0x36614`) writes **bit 7** only, so it does not affect this gate.
- `sub_5FA70` `0x63CEE` writes the whole byte from a stack value. That writer was not traced (boundary).

### 5. WO65037 open item resolved — `0x466A8` consumer base

`sub_464B6` (called from `sub_46744` at `0x46848`, per WO65120) loads `r12 = FFFF1054` at `0x46536`. The calls in between follow the callee-saved register convention (r8–r14), and no later `r12` write occurs before `0x466A8`. The function also loads `r13 = FFFF1D99` (`0x464C4`), `r11 = FFFF84B4` (`0x464C2`) and `r14 = 0x8FB9` (ROM, `0x46580`). The `0x6B3`/`0x6B4` reads are therefore **`FFFF1707`/`FFFF1708`**. Output is the UBYTE store at `0x46734`: `FFFF1054+0x686 = FFFF16DA`.

```text
46694  r0 = sub_228F0(r4=-1)
 r0 != 0 (loc_466F8): T = UBYTE[FFFF84BA], x = UBYTE[0x8F0A]=0x6E
     T > x : (1707 != 0x80) ? ROM[0x8FB9] : 0x40
     T <= x: (1708 != 0x80) ? ROM[0x8FBA] : 0x40
 r0 == 0:
     FFFF1E2F.bit1 == 0 && 1707 != 0x80 -> ROM[0x8FB9]
     else FFFF1E30.bit3 == 0 && 1708 != 0x80 -> ROM[0x8FBA]
     else clamp(UBYTE[FFFF1709] + UBYTE[FFFF16F5] - 0x40, 0, 0xFF)
 -> mov.b r2 -> FFFF16DA (0x46734)
```

- In this ROM, `0x8FB9 = 0x8FBA = 0x40`. Every non-fallback path therefore writes `0x40`, and a channel equal to `0x80` (the WO65037 sentinel/init-related value) blocks its selection.
- This consumer uses the AF72/ADF2 outputs **only as `0x80`-validity tests**. It does not read their magnitudes.
- It applies the same split on `FFFF84BA` against `0x8F0A` as the `sub_AE9EA` interpolation (WO65037): AF72's channel goes with `T > x`, ADF2's channel with `T <= x`.
- `FFFF16F5` is the `sub_22DE0` (`0xF4BE` curve) result stored at `0x465F4`.
