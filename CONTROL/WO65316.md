## Falsifiable hypothesis record

- **Identity layer advanced:** output identity and function identity.
- **Hypothesis (from the WO):** one or both F3D6 result stages (`FFFF1630`, `FFFF1632`) may feed a later consumer through a register-indexed, GBR-relative or computed-base alias that the earlier exact-address searches could not see.
- **Prediction:** the existing EA/GBR/RAM indexes would contain at least one resolvable access whose effective address lands in `FFFF1630–FFFF1633`.
- **Cheap discriminator:** enumerate only index entries that can alias the four bytes, through known base roots, then verify each against the listing.
- **Result:** **REJECTED within the supplied indexes — bounded negative.** No entry in the effective-address dictionary, GBR map or RAM byte/bit cross-reference resolves to `FFFF162C–FFFF1633`. No overlapping word/long access into the range exists. The only consumers remain the two direct `FFFF1054+0x5DC` reads already known.
- **Information gain:** converts "aliases unexamined" into "no alias path exists in the audited index stack", and localises the remaining possibility to unprovable dynamic bases, which is a different (and much more expensive) search.

## Separate conclusion per branch

- **F3D6 table-result branch (`0x0F712` → `FFFF1630`/`FFFF1632`):** the two stages are consumed only by the direct `FFFF1054+0x5DC` readers above; within the audited indexes there is **no alias consumer**. The stage values are therefore *not* dead — they feed a further 32-point lookup and a divide-based scaling — but they are not read through any second address form.
- **Alternate arithmetic branch (`0x68914–0x68958` → `FFFF10CC`):** not reopened. WO65223's separation is preserved; its `FFFF10CC` chain is unaffected by this search, and no `FFFF1630`-range alias touches it.
