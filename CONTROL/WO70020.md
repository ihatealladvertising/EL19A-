# WO70020 — Inventory existing ROM tools and define migration boundaries

## Objective

Audit the repository's existing ROM-analysis scripts and reusable components. Produce an evidence-backed inventory showing what can be retained, wrapped, modularized or deferred in the proposed independently executable Python-tool architecture.

This is an inventory and migration-boundary task, not an implementation task.

## Inputs to inspect

At minimum:

- `tools/nissan_sh705x_workbench.py`
- `tools/sh7058_cross_rom_scanner.py`
- `tools/sh7058_cross_rom_scanner.md`
- `tools/a2l_structural_matcher.py`
- `tools/a2l_structural_matcher.md`
- `tools/test_sh7058_cross_rom_scanner.py`
- `.github/workflows/sh7058-scanner-tests.yml`
- Other files under `tools/` that directly implement ROM loading, parsing, identification, table discovery, disassembly integration or definition conversion.
- `CONTROL/WO70017_DONOR_METADATA.tsv` as an example of an existing structured metadata artifact.

Use current main-branch contents. Do not assume historical summaries describe the current source.

## Required work

1. Inventory each relevant script/module: purpose, entry points/CLI, inputs, outputs, dependencies, platform assumptions and current tests.
2. Identify reusable functions/classes versus duplicated logic, especially ROM loading, endian-aware reads, address translation, checksums, A2L parsing, table geometry and cross-ROM comparison.
3. Identify hard-coded ECU/ROM assumptions (paths, addresses, FIDs, calibration labels, memory layout, CPU assumptions) and classify whether each belongs in a shared core, processor backend, format adapter or ECU profile.
4. Record actual data interchange formats currently emitted or consumed (JSON, TSV/CSV, XML, text, binary); note schema drift and missing provenance.
5. Classify each component: RETAIN, WRAP, REFACTOR, REPLACE, DEFER or NOT REUSABLE. Give a concrete reason and cite file/function/line anchors where practical.
6. Propose a migration sequence that preserves existing proven behavior and does not block current EL19A investigation.
7. Identify gaps and risks, but do not invent a complete architecture where WO70021's canonical data model is the relevant authority.

## Outputs

Create:

- `CONTROL/WO70020.md` — concise report with inventory summary, findings, migration boundaries and no-repeat notes.
- `CONTROL/SH705X_TOOL_INVENTORY.tsv` — one row per relevant script/module or separable capability.

Required TSV columns:

`path, component_or_function, purpose, entry_point, inputs, outputs, dependencies, python_or_platform_assumptions, existing_tests, reusable_logic, hard_coded_assumptions, proposed_layer, disposition, source_anchor, notes`.

## Evidence and quality rules

- Inspect current source, not only comments or prior reports.
- Separate observed implementation from proposed destination.
- Do not infer behavior from a filename or docstring where source inspection is possible.
- Preserve uncertainties and untested capabilities explicitly.
- Identify which components have regression coverage and which do not.
- Do not label an output complete when required input files or tools were unavailable.

## Acceptance criteria

- All relevant current `tools/` components have an explicit disposition or an explanation for exclusion.
- Shared logic and duplication are identified with specific source anchors.
- ECU-specific assumptions are distinguished from SH705x processor behavior and generic format behavior.
- The migration sequence is incremental and compatible with the charter.
- Findings disposition is stated. Architecture inventory alone should be NOT REQUIRED unless a material EL19A calibration claim is actually corrected.

Authorized new outputs only: `CONTROL/WO70020.md` and `CONTROL/SH705X_TOOL_INVENTORY.tsv`.

Do not install dependencies or run broad ROM scans. Follow `CONTROL/WORKER_PROTOCOL.md`, including publication-gate and Worker 1 FIFO rules.
