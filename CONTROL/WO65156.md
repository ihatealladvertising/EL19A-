| Object | Start | End (excl.) | Width | Shape | SHA-256 of object |
|---|---|---|---|---|---|

| `0x91A1` | `0x91A1` | `0x91B1` | UBYTE | 4 rows × 4 cols | `1b44afdd0dd3e0e17c7ce4f180c5ae9eaf32d99f7e8a88cb9d5aae02bd3d1671` |

| axis 2 | `0xB2D5` | `0xB2D9` | UBYTE | 4 points `10 20 40 70` | — |

How the extent is proven, for both maps independently of the 0x10 spacing:

- Both readers are thin front-ends over the same two axis searchers and the same interpolation chunk `loc_74B8`.
- `sub_7680` (`0x7680`) is a **UBYTE** axis walker: `mov.b @(r0,r4)` with `extu.b`, stepping `add #-1, r4` down to 0 (`loc_76B0`). Entered with `r4 = 3` it compares exactly **4 points** at byte offsets 3,2,1,0.
- `sub_7700` (`0x7700`) is the same walker with a ×4 query scaling: it compares `axis_byte << 2` against the query.
- `loc_74B8` is the shared **UBYTE** bilinear stage: `mulu r5, r0` with `r5 = 4` (`mov #4, r5` in each front-end's delay slot), then `mov.b @r4`, `mov.b @(1,r4)`, `mov.b @r5`, `mov.b @(1,r5)` (`0x74D2–0x74E8`). Four columns of byte elements ⇒ a 4×4 map = 16 bytes, which is exactly the distance to the next declared object.
- The pointer pool confirms the starts literally: `off_2F1FC: .data.l dword_9190+1` = `0x9191`; `off_23444: .data.l` = `0x91A1`.

Payloads (row-major, 4 UBYTE per row):

- `0x9191`: `11 1A 28 3A` / `19 27 3C 55` / `1B 2A 42 5E` / `1D 2D 46 64` (monotone in both dimensions)
- `0x91A1`: `6C 6C 67 64` / `64 64 6E 7F` / `84 84 8D A0` / `76 76 8E 9C`

## 2. Instruction-anchored trace — `0x9191` (only literal reader)

Reader: `sub_6E94`, called once with this base at `0x2EF9E` inside `sub_2EEEA` (`0x2EEEA`, caller `0x30E96`). (`sub_6E94` has further callers, e.g. `sub_36164+0x54`, but none loads `0x9191`.)

| PC | Effect | Note |
|---|---|---|
| `0x2EF80` | `r9 = FFFF85DC` | query record base |
| `0x2EF8A` | `r7 = FFFF846E` | second query record base |
| `0x2EF8E` | `r0 = byte[FFFF846E]` → staged at `0x2EF92` to `sp+3` | becomes the stacked argument (read as the low byte of the word at call-site `sp+0`) |
| `0x2EF90` | `r6 = 0xB2D5` | second axis |
| `0x2EF94` | `r0 = byte[FFFF85DC+5]` | first query |
| `0x2EF98` | `r4 = off_2F1FC` = `0x9191` | **map base** |
| `0x2EF9A` | `add #4, r5` (from `0xB2D5`) | first axis = `0xB2D9` |
| `0x2EFA0` | `extu.b r7` (delay slot) | first query = `byte[FFFF85DC+5]` |
| `0x6EA0`/`0x6EAE` | `jsr sub_7680` twice, `r4=3` | 4-point UBYTE searches on `0xB2D9` then `0xB2D5`; **raw byte compare, no ×4 scaling** |
| `0x6EC0` | `jmp loc_74B8` with `mov #4, r5` | 4-column UBYTE bilinear map read |
| `0x2EFA0–0x2EFA6` | `r0 → byte[FFFF10B4+0x2CB]` | **result latched**, `r10 = FFFF10B4` set at `0x2EF06` |
| `0x2EFAC–0x2EFC0` | `byte[FFFF10B4+0x2C7] × byte[FFFF10B4+0x2CC] × result`, `shlr8`/`shlr2`×3 | product chain; the map result is one multiplicand |
| `0x2EFD2` | `byte[FFFF10B4+0x2CA] = clamped product` | first derived value |
| `0x2EFD8` | `r5 = byte[FFFF84C8+0x47]` | next multiplier — a *different* base from the fresh-air result cell |

Both queries are raw bytes and the map element is a byte: `0x9191` is consumed entirely as an unsigned-byte correction factor, with no sign handling anywhere in the block.

## 3. Instruction-anchored trace — `0x91A1`

`sub_6F0C` has two callsites. The one loading `0x91A1` is `0x233CC` inside `sub_22752` (`0x22752`, `gbr = FFFF8548`, caller `0x226A2`); the other (`0x230D6`) loads `0x9151` with axes `0xB277`/`0xB27B`, so that site is a **different map of the same family** and is out of this WO's scope.

| PC | Effect | Note |
|---|---|---|
| `0x233A6` | `r4 = 0x9471` | 16×16 UBYTE map read first |
| `0x233AA` | `r7 = r12` | query for the `0x9471` read |
| `0x233B2` | `jsr sub_6FE4` | axes `0xB4AE`/`0xB50A` |
| `0x233B4` | `sp+3 = result byte` | staged, then **overwritten** before the `0x91A1` call |
| `0x233BC` | `byte[FFFF8548+0xAC] = result` | `0x9471` result preserved here |
| `0x233BE` | `r0 = byte[FFFF847E]` → `sp+3` at `0x233C2` | effective stacked argument (second query) |
| `0x233C0` | `r4 = off_23444` = `0x91A1` | **map base** |
| `0x233C4` | `r0 = UWORD[FFFF8614+0x14]` | first query (`r10 = FFFF8614` set at `0x2320C`) |
| `0x233C6`/`0x233C8` | `r5 = 0xB2D9`, `r6 = 0xB2D5` | **same axis pair as `0x9191`** |
| `0x233CE` | `extu.w r7` (delay slot) | first query, word-wide |
| `0x6F18` | `jsr sub_7700`, `r4=3` | 4-point search on `0xB2D9` with **×4 query scaling** |
| `0x6F28` | `jsr sub_7680`, `r4=3` | 4-point search on `0xB2D5`, raw byte compare |
| `0x6F3A` | `jmp loc_74B8` with `mov #4, r5` | 4-column UBYTE bilinear map read |
| `0x233D2–0x233D4` | `byte[FFFF8548+0x47] = result` | **result latched** at `FFFF858F` |

Observable asymmetry worth keeping: for `0x9191` **both** axis searches use the raw-byte comparator, while for `0x91A1` the first axis uses the ×4 comparator and the second the raw one. That is a difference in query scaling between the two readers, not a data difference — the axis bytes themselves are shared.

## 4. Interaction test

The WO asks whether the two output paths meet in a common combustion/fueling calculation. Tested three ways, all negative for a direct join:

1. **Different consumers.** `0x9191` → `byte[FFFF10B4+0x2CB]`, multiplied into a product chain that lands at `FFFF10B4+0x2CA`. `0x91A1` → `byte[FFFF8548+0x47]` (`FFFF858F`).
2. **No cross-read.** A scoped scan of `sub_2EEEA` (`0x2EEEA–0x2F0C2` region) finds no reference to `FFFF8548` or `FFFF858F`; its neighbouring reads use `FFFF84C8`, `FFFF85DC` and `FFFF846E`. A scoped scan of `sub_22752` finds exactly one `FFFF10B4` reference (`0x22790`, offset `0xA2` → `FFFF1156`), which is **not** the MBT result cells `+0x2CB`/`+0x2CA`.
3. **The only chained dependency found is elsewhere.** `0x91A1`'s second-axis query is a RAM byte (`FFFF847E`), and the immediately preceding read in the same block is the `0x9471` 16×16 map whose result is cached at `FFFF85F4`. So the fresh-air map is fed from the `0x9471` map's *input domain* rather than from the MBT map's output. This is an observed scheduling/adjacency fact only; no arithmetic join between `FFFF85F4` and `FFFF858F` was traced.

Therefore: the two maps are geometry twins (same 4×4 UBYTE shape, same shared axes, same helper tail) with **independent output paths**. Twin geometry is not evidence of a coupled calculation.

## 5. Unresolved edges (explicit stop boundary)

1. **Physical identity, units, direction and scaling** of either map — nothing in the readers encodes a physical unit; both are unsigned-byte correction factors clamped and multiplied downstream.
2. **Query producers** — `FFFF85DC+5`, `FFFF846E`, `FFFF8628`, `FFFF847E` are RAM reads of untraced origin.
3. **First real consumer of `FFFF858F`** — no literal reference exists; readers would have to appear as `gbr`-relative `@(0x47,gbr)` accesses, and attributing those requires resolving each candidate function's `gbr` base (`0x1520C`, `0x2033E`, `0x20514`, `0x27122`, `0x27A3A`, `0x3F06A`, `0x3F1DE`, `0x51334`, `0x5134C`, `0x54862`). Not done here.
4. **The product chain after `FFFF10B4+0x2CA`** — the chain continues through `sub_38A8` and `sub_3784`; its physical meaning and eventual destination were not closed.
5. **`sub_2EEEA`'s gating** — the block is entered through `byte[FFFF84A0+7]`/`FFFF10B4+0x7CC` comparisons (`0x2EF16–0x2EF2A`); the enabling conditions were not traced. Likewise `sub_22752`'s `0x2332E–0x23350` flag gate.
6. **The `0x91xx` map family** — `0x9151` is read with a different axis pair (`0xB277`/`0xB27B`); the remaining 16-byte members were not enumerated (out of scope, no broad census).
7. **Computed-address readers** — the census is literal/pool-reference based; an indirect reader through a computed base is not excluded.
