## Decision question

Can the validated instruction-level reference method produce a trustworthy, method-bounded RAM access slice for two small target ranges, with sufficient per-function/per-region GBR provenance to prevent stale-register aliases?

## Scope and target ranges

1. **RAM bytes `FFFF85C4–FFFF85FF`** — include the corrected three-reader inventory for `FFFF85DF`.
2. **RAM bytes `FFFF860B–FFFF860F`** — include bit-level accesses, particularly bits 3 and 5 where present; distinguish every byte and bit.

For each access record:

- effective RAM address (byte-level);
- PC and enclosing function/entry context;
- read/write and access width;
- bit mask / set / clear / test / read-modify-write operation, where applicable;
- addressing form: literal, PC-relative pool, GBR-relative, base+displacement, base+index, pointer-mediated, or copy/DMA;
- defining PC(s) and register provenance, including `r0`, sign/zero extension, `GBR`, calls/returns, branch paths and delay slots;
- evidence level and unresolved reason.

Produce a compact local function/GBR map only for functions that actually contribute accesses to these ranges. GBR is recorded by control-flow region and instruction context, not asserted as one constant per function unless demonstrated.

## Hop budget and methods

- Search direct address/pool references and all relevant access forms: literal; PC-relative literal pool; GBR + actual runtime base; base + displacement; base + `r0`/other index; pointer dereference; block copy/helper and DMA where a concrete lead identifies them.
- Follow up to **3 register-definition/dataflow hops** per access and **1 call/return boundary** when needed to establish or invalidate register state. Extend only with a concrete dependency.
- Track unresolved base/index/register states explicitly. Never infer an address from an IDA symbol label alone.
- Treat `rte`, function returns, non-preserved registers, calls that alter GBR, and unsupported control-flow joins as state boundaries until preservation is proven.
- No blanket negative findings. State exactly which methods were applied to each address family.

## Mandatory regression controls

- `FFFF85DF`: `0x46BDE`, `0x47014` (base+index) and `0x59CA2` (GBR-relative); ROM `0x85DF` remains distinct.
- `0x55846`: caller GBR `FFFF8A34` gives `FFFF8AE4`; stale callee GBR `FFFF8A40` would falsely give `FFFF8AF0`.
- `INT_ATU11_IMI1AC`: PKIOR_W pointer loads at `0x2869A`, `0x286A4`, `0x286E4`, `0x2870E`, `0x28738`; restore/RTE boundary at `0x2878C/0x28790`.
- `extu.b` destination update; signed `mov.w` loads; branch delay slots (`bt/s`, `bra`, `rts`, not plain `bt`).

## Dependencies and exclusions

- **DEPENDS_ON:** WO65061 bounded pilot (closed); exact ROM/listing byte-integrity preflight.
- **UNLOCKS:** reusable small-slice RAM access index; subsequent expansion to adjacent RAM pages only after review.
- **Excluded:** whole-ROM GBR census, whole-ROM RAM xref, scalar/limiter sweep, semantic naming, XML/workbook changes, IDB or source edits, worker dispatch, Library uploads, persistent resolver/index-generator creation.
- Keep all scratch calculations read-only. Do not modify or replace existing scripts. Do not create a new shared tool or persistent index artifact without explicit approval.

## Stop condition

Stop at the first access whose effective address depends on unproven register provenance, an unsupported branch join, a helper that may alter state without a proven restore, or an indirect/copy/DMA boundary lacking a concrete source. Report it as unresolved with the exact method gap. Do not compensate by widening a blind instruction window.

## Expected closeout

- Compact local GBR/function-context table.
- Regression results and method coverage per target.
- Findings/corrections and bounded negatives with exact scope.
- No claim that the slice is exhaustive outside these two address ranges and tested methods.

### C. Bit-level and copy interpretation

- `sub_24740` (`GBR=FFFF2F00`) is a verified **bit5 read/modify/write producer** for both `FFFF860D` and `FFFF860B`. For selected state values 2, 3, or 4, it ORs `0x20` into both bytes (`0x248B2` and `0x248B8`). For other selected states, it ANDs `0xDF` to clear bit5 (`0x248A6` and `0x248B8`). Other bits are preserved by these masks.
- `sub_20DCE` whole-byte propagation is distinct from an independent bit writer: it copies `860B/860C` into `860F/8610` at `0x20FD0/0x20FD2`, then copies `860D/860E` into `860B/860C` at `0x20FDC/0x20FE0`. This can propagate the value of bit3 as part of a byte, but it is not an independent bit3 set/clear operation.
- `WO65059`'s bounded producer audit remains applicable: `sub_B119A` changes bits 0,1,2,4 of `860D` and preserves/skips bit3; `sub_B12A6` changes bit6 and preserves bit3. Within the methods and search boundary documented there, no independent bit3 writer for `860D` or `860B` was found. Do not turn this into a universal no-writer claim.
- `FFFF860F` is demonstrably written as a whole byte from `FFFF860B` at `0x20FD0`, and later tested at the reader PCs above. These findings do not establish an independent `860F` bit3/bit5 producer.

### D. Unresolved sites and coverage limits

- The current annotated LST contains approximately 113 textual `FFFF85C4` pointer-load/comment occurrences. This is a **search lead count**, not an access count; many refer to the same literal pool or to base definitions that have not yet been followed to their actual memory operations.
- Dynamic indexed accesses through a `FFFF85C4` base remain unassigned until `r0` and the base register are established at the actual instruction. Do not assign them to an offset merely because the base pointer is loaded.
- Other direct bases / structure pointers into `FFFF85xx` may overlap the target slice without using the `FFFF85C4` base. A full direct+pointer+GBR census for this region has not been completed.
- `FFFF860C` has indexed references (e.g. sites around `0x36826`/`0x36980`) whose `r0` value must be resolved before assigning the effective address. They remain unresolved in this checkpoint.
- Reader lists for `860B`, `860D`, and `860F` above are selected examples from the bounded listing review, not complete per-byte inventories. `860E` is positively observed as a source byte at `0x20FDA`; absence of other uses is not claimed.
- `FFFF85E4` writers at `0x271F2`, `0x29034`, and `0x85A26` have been identified as instruction PCs, but their producing paths are not yet traced end-to-end. Their values must not be semantically merged with `sub_257AC`'s timer-difference path.
- `FFFF85F8` is read in the `sub_403D8` selection path at `0x4048C`; `FFFF85FF+1` (`FFFF8600`) is read at `0x40494`. The latter is outside WO65062's specified range.

**Checkpoint disposition:** partial positive inventory completed for both target ranges; unresolved computed/indexed/direct-base sites remain. WO65062 stays ACTIVE. No exhaustive coverage claim, no semantic naming, and no persistent index or generator created.

## Correction 1c — indexed references formerly attributed to `FFFF860C` (2026-11-20)

The earlier unresolved-site note identifying `0x36826` and `0x36980` as potentially unresolved indexed accesses to `FFFF860C` is superseded by exact immediate-index resolution:

- The corresponding branch at `0x36856` loads the same `R6=FFFF860C` and `R0=0x13` at `0x36858`; read at `0x3685A` also accesses **`FFFF861F`**.

- Current positively established `FFFF860C` operations in this slice remain the whole-byte read at `0x20FCE` and write at `0x20FE0` in `sub_20DCE`.

**Effect:** remove these sites from the target-range unresolved list; do not count their base-register setup instructions as accesses to `FFFF860C`.
